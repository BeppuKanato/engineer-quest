# 穴掘り法「動きの確認問題」

- 目的・適用範囲: Issue #259の連結2問を単品で最後まで操作する。状態: 現行。最終確認日: 2026-11-18。2026-11-17 の判断基準（問題数ではなく「アルゴリズムの流れを理解できていると判断するに足るか」）で監査し、6問（タップ3・選択肢3）へ拡充した。
- 正本: [穴掘り法基準データ§3](../../../../../../docs/concept/maze-digging-unit-baseline.md)、[教材指針](../../../../../../docs/concept/learning-materials-guideline.md)、[プレイヤーUI定義](../../../../../../docs/concept/learning-player-ui.md)。
- 実装・検証・指針との留保: [実施記録](../../../../../../docs/maze-digging-phase3-259.md)。

`front`で`npm run dev`を実行して http://localhost:3000/learning-preview/maze-digging-check を開く。認証・DBは不要。

場面はすべてフェーズ2のステップをステップIDで参照し、壁を複製しない。設問はトレースの時間順（最初の掘削 → 掘削3回目まで進んだ場面 → 行き止まり → 完成）に並ぶ。

| 設問 | 形式 | 場面 | 内容 | 正解 |
| --- | --- | --- | --- | --- |
| first-dig-room | タップ | `dig-start` | (1, 1) から右へ掘ります。掘られる部屋はどれですか（候補は右 (1, 3)・下 (3, 1)） | (1, 3) |
| next-room | タップ | `dig-3` | (3, 5) から右へ掘ります。掘られる部屋はどれですか（候補は上 (1, 5)・右 (3, 7)・下 (5, 5)） | (3, 7) |
| between-wall | タップ | `dig-3` | そのとき通路になる、間の壁マスはどれですか（候補は (2, 5)・(3, 6)・(4, 5)） | (3, 6) |
| candidate-count | 選択肢 | `dig-3` | (3, 5) から掘れる部屋は、いくつありますか | 3つ |
| dead-end-next | 選択肢 | `dig-6` | 行き止まりの (1, 5) では、この後どうなりますか | 掘れる部屋がある (3, 7) まで戻って、そこから掘り直す |
| completion-count | 選択肢 | `complete` | スタートの部屋 (1, 1) は最初に掘ってあります。それ以外の部屋を掘った回数は、全部で何回ですか | 15回 |

（座標の表示は Issue #326 で (y, x) の順に統一。セルキー自体は "x,y" のまま。）

- 場面は全問とも場面ステップの canvas そのもの。棒倒し法フェーズ3と違い、前提設問の正解で処理中マスが移ることはないため、場面の差し替えはしない。
- 方向はタップ設問の問題文の中で提示する（基準データ §6-6）。穴掘り法は次の行き先が乱数（choices）で決まるため、方向を与えないと正解が一意に定まらない。与えた上でも「2マス先の部屋」と「間の壁」を特定する学習は成立する。棒倒し法のような独立した方向フィールド／表示行は持たない。
- タップ設問の回答対象は、アルゴリズムが実際に集める候補そのもの（現在マスから2マス先が盤内で、まだ壁のままの部屋）。掘削済みの部屋（例: dig-3 場面の左 (3, 3)）は候補に入らない。between-wall の回答対象は候補方向それぞれの間の壁マスで、掘削で通路になるのはこの範囲だけ。
- 選択肢設問は、タップでは問えない流れの理解（候補の数、行き止まりの後の戻りと再開、掘った回数 = 部屋の数 − 1）を確認するために使う。ChoiceQuestion は requires を持てないため、連動は場面と問題文で表す。next-room → between-wall の連結だけ従来どおり requires で表す。
- 正解はすべて `../mazeDiggingMaze.ts` の組み立て済みトレース（掘削列と、掘削列から導くバックトラック）から導き、基準データ§3の確定事項（1回目: (1, 1) から右へ (3, 1)、4回目: セルキー "5,3" から右へ "7,3"・間の壁 "6,3"、候補は3つ、最初のバックトラックは (5, 1)・(7, 1) を戻って (7, 3) から再開、掘削は全15回）と一致することをモジュール読み込み時に検証する。
- 場面の検証は単元側の `validateMazeDiggingCanvas`（processing は通路側の現在マス）で行う。共有の `validateMazeGridCanvas` は棒倒し法の前提のため使わない。

回答形式は共通エンジン（`../../assessment/assessment.ts`）の `concept-check` を使い、タップ設問と文章選択肢の設問を混在させる。タップの回答はノードIDの代わりにセルキー（`"x,y"`）を渡すグリッド版とする。新規の判定・進行は作らない。

- 進行は全形式統一の現行仕様（PR #170）: 回答では進まず、「次の問題へ／結果を見る」を押して進む。正解していなくても進める（ソフトゲート）。完了条件は「最後まで進み、全問に1回以上回答したこと」で、結果と要約は初回回答のみから導く。
- 正解した設問は入力をロックする（ボタン無効化＋送信側でも正解済み設問への追加試行を弾く）。
- 誤答後は「該当ステップの動きを確認する」で復習モーダルを任意に開ける。復習はフェーズ2の元ステップを参照のまま再生し、回答記録は変えない。
- 回答ボタンはマスの中心に重ねる HTML ボタン（`MazeDiggingCheckCanvas`）。共通の `answerCueSx`（破線リング＋タップアイコン）で回答可能だと示し、`aria-label` は「○列目、○行目のマスを選ぶ」。画面上で44px未満になる場合は中心から広げて最低限の大きさを保つ。選択肢設問では盤面は表示のみとし、文章の選択肢ボタンを盤面の下に置く。

ファイル:

- `check.content.ts`: 設問・正解・依存条件・表示ステップID・復習ID・論点タグ・完了文と、場面の解決（`getMazeDiggingCheckScene`）。
- `check.types.ts`: 共通 concept-check 形式の設問型・コンテンツ型と、単元接続用の要約型。
- `MazeDiggingCheckCanvas.tsx`: 共通グリッド描画＋セル単位の回答ボタン。
- `MazeDiggingCheckPreview.tsx`: アセスメント画面。BFSフェーズ3と同じく embedded / onComplete（要約通知）を持つ。

検証: `npm run verify:maze-digging-check`。単元フローへの接続・進捗保存は後続Issueの対象で、このモジュールは保存処理を持たない。
