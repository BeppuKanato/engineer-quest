## 確認方法

`front` で `npm ci` → `npm run dev` を実行し、`http://localhost:3000/learning-preview/bfs-execution` を開く。
ログイン・DB・バックエンドは不要。アプリの入口導線は追加していない。
production build では `npm run build` → `node node_modules/next/dist/bin/next start --hostname 127.0.0.1 --port 3000`。

前へ・次へ・スライダー・← / → / Home / End で全19コマを確認する。
再生は3500ms間隔で進み、一時停止・手動移動で停止する。末尾は19の原文キャプションで締め、遷移ボタンやリザルトを出さない。
末尾の再生ボタンは先頭から再生する。
3・4・7・8・14は追加した辺・ノード・キュー項目を同期強調する。
10は2歩先より先に1歩先のCを取り出し、11はC–Eを青い破線で示してキューを変えない。
16はFより先にEを取り出し、17は追加せず完了、19ですべてグレーになる。

## 確定するデータ契約 v1

`execution.types.ts` の `BfsExecutionCanvasState` と、共通の `LearningStep` / `LearningContent` を使う。
`execution.content.ts` はデータ、`BfsExecutionCanvas.tsx` は描画、共通 `LearningPlayer` は再生制御のみを担当する。
入力境界は型付きTSモジュールであり、外部JSONを型アサーションで読み込む形式ではない。

| 項目 | 意味と利用方法 |
| --- | --- |
| `step.id` | 安定した意味ID。復習・設問・コード対応から番号ではなくIDで参照する |
| `caption` | レビュー済み原文1文。19ステップの追加・分割・統合はしない |
| `canvas.data.graph` | 無向辺、600×300座標、距離層のノード集合・縦帯の位置。全コマで同じ対象データ |
| `state.nodes` | 各点の状態、発見済み最短距離（未発見はnull）、初発見時の親（出発点・未発見はnull） |
| `state.queue` | 先頭→末尾の順序付きノードIDと距離。追加時に発見済みとして扱う |
| `state.current` | 処理中の点。取り出し後からその点の完了まで保持、完了コマはnull |
| `state.activeDistance` | 今調べている距離の帯。追加先の距離ではなく処理元の距離、最終コマはnull |
| `state.operation` | initialize / dequeue / discover / skip-discovered / complete と対象ID、必要な辺・処理元。コードの行番号に依存しない |
| `highlights` | ノード、キュー項目、辺への参照。辺は実線／破線を区別する |

全項目は**操作直後の完全なスナップショット**で、前ステップのイベントを再実行せずに表示できる。
フェーズ3は、例えば `dequeue-c` の前の `complete-b` をそのまま問いの図に、`dequeue-c` / `skip-e` を解答後や復習に参照できる。
フェーズ4は同じ `steps` / `canvas` / renderer を読み、意味IDとoperationに対するコード行の対応表を別途持つ。
コード行番号や設問・回答状態はこのデータへ埋め込まない。
指針が要求する制御・宣言行の追加表示は、既存スナップショットを保持するコード側のフレームとして後続Issueで構成できる。19ステップを複製・書き換える必要はない。

逆送り・シーク時も、選択されたスナップショットへ600msで遷移する。
キュー項目はノードの位置から出現し、先頭から取り出すと図へ戻り、残った要素は左へ詰まる。
OSの「動きを減らす」設定では動きを省略する。
色は共通プレイヤーの局所トークンを参照し、処理中=青、待機=ベージュ、完了=グレー、未発見=白、層=交互のグレーとする。
図・キュー・距離の文字は黒、青い処理中要素の上だけ白。現在の層は帯の不透明度を上げ、淡く光らせる。

## 共通描画（#91）

`player/GraphDrawing.tsx` の `GraphViewport` / `GraphEdges` / `GraphNodes` でフェーズ1・土台と同じノード・辺を描く。
値は `graphGeometry.ts`（半径30・枠線2・辺2/5・破線リング半径37/線幅3・ラベル24）に集約する。
ノード座標は `graphs/searchGraph.ts` を直接使い、画面幅への横方向の引き伸ばしや固定pxのノードは廃止した。
600×450のSVG全体を `xMidYMid meet` で均等拡縮するため、キューとの出入りも同一座標内で動く。
距離帯・距離表示・キューは教材固有レイヤーとして維持し、辺の「追加=実線／既発見=破線」の意味も維持する。
フェーズ3の `renderNodeOverlay(nodeId, radius)` は変更せず、共通描画のノード中心と半径30を受け取って常時リング・タップ領域を重ねる。
19ステップのデータ・キャプション、共有グラフの正本、確認画面の仕組みは変更しない。

## レビュー判断点と対象外

フェーズ1の用語対応表を引き継ぎ、このフェーズで初めて示す用語は以下とする。

| 概念 | 日常語 | 専門用語 | 初出コマ |
| --- | --- | --- | --- |
| 先に入れた場所を先に取り出すデータ構造 | 待ち行列 | キュー | 1 (`enqueue-start`) |

- グラフのノード・辺は #88 で `../../graphs/searchGraph.ts` の共有モジュールを正本として統一した（本サンプルの AB / AC / BD / BE / CE / DF / EF、配置も同一）。`bfsExecutionGraph.ts` は共有のノード・辺にフェーズ2固有の距離層を足すだけになった。フェーズ1も同じモジュールを参照するため、フェーズ境界で図の辺・配置は一致する。
- 今回は同じグラフ・同じ課題の19コマを維持し、クッションを追加しない。フェーズ間接続は作らない。
- サンプルは既発見点の確認すべてを独立表示しない。C→Eのみ11で示し、E→F等は「隣を調べ終えました」に含む。19ステップ原文を優先する。フェーズ4の制御行は上記のコード側フレームとして同じ状態に重ねる必要がある。
- キュー名は初出で「待ち行列（キュー）」、以後は指針の専門用語への移行に合わせ「キュー」。キャプションは指示どおり行列／待ち行列を含む原文を維持する。
- 共通プレイヤーには100%表示、300msトークン、最低350msの下限、長いスライダーが残る（#83）。本教材は600ms・3500msだが、共通プレイヤー全体のUI定義一致は対象外。短い高さでは縦スクロールが発生しうる。
- DB・API・保存・ログ・アプリ組み込み・他フェーズ・フェーズ間遷移・リザルトは対象外、DB適用不要。

## 検証

`npm run lint` / `npm run typecheck` / `npm run build` / `npm run verify:bfs-execution`。
回帰確認に `npm run verify:learning-player` / `npm run verify:bfs-motivation`。
新verifyは正しい辺集合・配置・19原文を照合し、独立BFS実行と全スナップショット（FIFO、距離、親、発見済み、処理中・完了、層）を比較する。
加えて強調の実線／破線、単独復元、誤ったキュー順序・距離・再追加・親・辺・層の拒否を確認する。
ブラウザでは19コマ、追加・取り出し・破線、前後・シーク・再生停止・末尾、狭い画面を確認する。

2026-11-04 の実施結果: 上記6コマンドは成功。production build の Chrome で全19コマのキャプション・処理状態・キュー、11の破線と再追加なし、キーボードによる逆送り・シーク、再生・一時停止、末尾停止・先頭再生を確認した。
1366×768 と390×844で横スクロールなし、最大3要素のキューと距離の表示も確認した。console error / warn なし。
既存の複数lockfileによる workspace root 警告と ESLint設定の module type 警告は残るが、コマンドは exit 0。build は既存 next/font のフォント取得のためネットワーク可能な環境で実行した。
DB・外部API・他フェーズの接続の検証は対象外。

#91 の同一画面幅での比較・実施結果は [描画統一の検証記録](../../../../../../docs/graph-unify-91.md) を参照。
