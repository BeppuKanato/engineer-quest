# 穴掘り法 フェーズ7 視覚デバッグ（Issue #264）

目的: 穴掘り法フェーズ7に、BFS フェーズ7（Issue #76）・棒倒し法フェーズ7（Issue #213）と同じ段階適用の視覚デバッグを実装する。学習者のコードを表示用D1（9×9、主教材の choices）で実行し、掘削過程（バックトラックを含む）をフェーズ2と同じ盤面再生でステップ表示する。想定解法に沿ったコードはトレース再現し、対応できない実行は停止位置＋最終状態のみに留める（教材指針 §7-3、基準データ §3 フェーズ7）。最終確認日: 2026-11-07。

## 実装内容

- `front/src/features/learning/maze-digging/trace/` を棒倒し法の `wall-extension/trace/` と同じ構成で新設（`acquireTrace` / `convertTrace` / `MazeDiggingTraceDialog` / `trace.content` / `trace.types` / README）。ボタン文言は単元の内容に合わせ「盤面で掘る様子を見る」とした。
  - 取得: 前の採点用入力を持ち込まず、毎回新しい Worker へ D1 の関数名と引数だけを送る。判定用ケース・期待値は送らない。イベント上限は1000件（下記「判断」参照）。
  - 変換: イベント列の `grid` スナップショットから、フェーズ2と同じ検証器（`validateMazeDiggingExecutionCanvas`）を通る完全スナップショットを組み立てる。掘削は間の壁と部屋の2マスが掘れて初めて1コマにし（間の壁だけの中間状態は保留）、掘った部屋を処理中（青）、掘れた2マスを highlight、キャプションは現在マス＋方向で組み立てる。完成時は戻り値の盤面からフェーズ2の完成ステップと同じ旗＋一本道のコマを足す。正しい迷路を再実行して差し替える処理はなく、誤った盤面（間の壁の掘り残し等）もそのまま表示する。
  - スタックの導出: 共有トレース基盤は `stack` を取得しないため、現在マスと経路は盤面から導出する。掘削途中では開いたマスが木をなすため、開始マスから現在マスへの経路は一意で、スタックの経路と一致する。バックトラックは盤面が変わらないので、次の掘削の開始マスが前回の掘削先と異なることから検出し、盤面を変えず現在位置と経路だけを移すコマを挟む。フェーズ2の正準フレーム列（盤面・処理中・経路・highlight・旗の21コマ）と再生が完全一致することを検証で固定している。
  - 段階適用: 盤面として描けない状態が末尾に残る場合は描けたところまでを部分再生として明示する。部屋まで掘り切らずに止まった場合は保留中の掘削を最後のコマとして出す。`grid` のスナップショットが取れない構造（盤面を補助関数の中だけで作る等）・変換できた状態がない場合・形の候補が曖昧な場合は、戻り値の盤面による最終状態だけを表示する。エラーは停止行と種別だけを示し、生の例外本文は返さない。
  - 表示: モーダルは棒倒し法と同じ 84vw × 84dvh、既存 LearningPlayer の再生制御、フェーズ2の `MazeDiggingExecutionCanvas` をそのまま使う。下部に観測行と `size`・`choices`・壁の数を表示する。
- 画面接続: `MazeDiggingImplementationPreview` に「盤面で掘る様子を見る」を追加（エディタのパネルと全通過後の完了表示の両方。棒倒し法フェーズ7と同じ配置）。あわせて単元フロー接続用の `active` prop（任意・既定 true）を追加した。取得中は編集・採点・試しに実行・ヒントを無効化し、トレースは採点回数・ヒント回数・完了判定を変更しない。
- フェーズ7検証のピン更新: `verifyMazeDiggingImplementation.cjs` の「視覚デバッグは #264 の対象で含めない」という #263 時点のピンを、接続済みであることの確認へ差し替えた。
- 共通基盤（`front/public/python-trace-harness.mjs`）は変更していない。grid 検出・size / choices の受け渡し・種類別曖昧判定（ambiguousKinds）をそのまま使っている。

## 判断

- イベント上限を1000件とした。BFS・棒倒し法は500件だが、穴掘り法は掘削ごとに候補収集ループ（方向4つ×複数行）を回すため、参照コードでも D1 で662件のイベントが発生し、500では正準の再生自体が打ち切られてしまう。実測に基づき、この単元の定数として1000に設定した（ハーネス側の上限2000以内）。

## 検証

- `npm run verify:maze-digging-trace`（新規）: 同じハーネスを CPython で実行し、参照コードの再生がフェーズ2の正準フレーム列（盤面・処理中・経路・highlight・旗の21コマ）と完全一致すること、バックトラックが3コマ独立すること、スナップショットのコピー性、盤面変数の改名（`board`）での形検出、間の壁を掘らない誤りの忠実な再生、途中エラー（停止行＝参照コードの `dig-room` 行）と例外本文の秘匿、補助関数内で作る盤面の最終状態表示、構文エラー、形の候補が複数の場合の曖昧判定、末尾だけ描けない盤面の部分再生、打ち切り、実描画（81マス・壁セルの数）、D1限定・新規Worker・キャンセルの取得経路、画面接続のピンを確認。
- 回帰: front の全 verify 通過。`lint` / `typecheck` / `build` 通過（詳細は PR 本文）。
- DB・シードの変更はない。

## 留保（判断が必要な点）

- 現在マス・スタック経路・バックトラックは盤面からの導出（推定）であり、学習者のコードが想定と違う構造（部屋同士を直接つなぐ、木にならない掘り方等）をした場合は、経路が実際のスタックと異なる可能性がある。盤面（壁の集合）そのものは常に実値どおりであり、推定が外れるのは現在位置と経路の表示だけに限る。厳密にやるには `stack` を基盤の取得対象へ足す拡張が要るが、共有基盤への影響を避けるため本 Issue では行わない。
- バックトラックのコマの観測行は、検出に使った次の掘削のイベントの行を示す（戻り自体の行ではない）。盤面と現在位置は実値どおり。
- ブラウザ上の実 Pyodide での目視確認はこの環境では行っていない（CPython ハーネスでの検証と build まで）。マージ後に単品プレビューで「盤面で掘る様子を見る」を押す確認をお願いしたい。

## 確認方法

1. `front/` で `npm run dev` を起動し、`http://localhost:3000/learning-preview/maze-digging-implementation` を開く（ログイン・DB不要）。
2. 初期コード（テンプレート）のままでは掘削が進まないため、参照コード相当の完成コードを貼り付けて「盤面で掘る様子を見る」を押す。モーダルで用意→開始マスの掘削→15回の掘削（途中に3回のバックトラック）→完成（旗＋一本道）がフェーズ2と同じ盤面で再生され、変数欄に観測行・size・choices・壁の数が並ぶことを確認する。
3. 間の壁を掘らない誤りを入れたコードで再度開き、誤った盤面のまま再生される（正しい迷路に差し替わらない）ことを確認する。
4. 全テスト通過後の完了表示からも「盤面で掘る様子を見る」が開けることを確認する。
