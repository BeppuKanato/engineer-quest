# 大目標のLLM生成と達成条件別の進捗（B案）

## 設計
- 大目標の型・パラメータ・推薦方向は LLM が提案する。提示候補は各回最大3件。
- コードは事前に「計測できる型・パラメータの組合せ」を列挙し、LLMの出力を完全一致で検証する。未知の型・対象ID・閾値・複合条件は拒否し、勝手に修復しない。
- 達成条件の正確な表示文はコードが生成し、LLMが生成する動機づけの一言を後続に付記する。**LLMの言い回しが達成条件を変更してはならない**。
- PERSONALIZEDのみHEXADの6スコアと特性説明をLLMに渡す。STANDARDではHEXAD入力を含めない。
- 候補の適合度と推薦理由はLLMが生成。最終推薦はコード側で最大スコアを選択し、同点は出力順。
- 学習者による明示的な目標確定と、その後の達成判定は既存のDB・ロジックを利用する。

## 達成条件の扱い
- 到達型: 単元完了と、その目標に含まれる挑戦条件を独立したチェック項目として保存する。
- 実績型: 指定実績の獲得有無。
- 応用型: 関連する「作る」課題の完了数。
- 統合型・共有型・定着型: 計測機構がないため、生成候補に含めない。
- 複合達成条件のある到達型は、フェーズ7/7だけで「大目標100%」と表さない。達成時以外の進捗率はnullとし、条件別の状態を表示する。
- 未観測と未達成は別状態で記録する。必要な計測が欠ける場合は成功/失敗を推測せずNOT_INSTRUMENTEDにする。
- 7フェーズの現在位置図は大目標とは独立して維持する。
- フェーズ完了・単元完了によって閉じた大目標は、その完了イベントに対応するフィードバック分析へ渡す（同時刻付近の終了記録で対応）。

## 安全性と限界
- 型・パラメータの機械的検証ができても、LLMの動機づけ文・推薦理由の意味内容を完全に検証することはできない。
- 目標候補のバリエーションは、既存の実績・単元・作るの活動と記録可能な挑戦条件に限定される。Socialiser/Philanthropist向けの共有・交流目標は、達成計測を追加するまで推薦できない。
- 目標を提案するLLMがエラーや無効条件を返した場合は、検証失敗としてFAILEDにし、ログを保存する。偽の目標に自動フォールバックしない。
- 既存のDBレコード（旧プロンプトで生成済みの結果）を書き換えない。新しい提案イベントから生成方式が変わる。
- 進捗UIは既存のevaluation.requirementsが無い旧レコードでも動作するよう後方互換を維持する。
- 大目標のLLM生成方式を研究で評価する場合は、従来の「候補採点のみ」とは方式が異なることを明示し、実験時のプロンプト版・コミットIDを保存する。

## 検証
```bash
cd back
npm ci
npm run typecheck
npm run verify:big-goal
npm run verify:big-goal-proposal
npm run verify:big-goal-generation

cd ../front
npm ci
npm run typecheck
npm run build
```

実機では、(1) 二分探索の単元開始時に異なる型・挑戦条件の大目標が提案されること、
(2) 目標を選択して学習を進めたとき評価結果が変化すること、
(3) 未観測の挑戦は未観測と表示されること、
(4) 失敗した挑戦を単元完了率100%と誤表示しないこと、
(5) 単元完了時のフィードバックが達成済みの目標を正しく説明することを確認する。
