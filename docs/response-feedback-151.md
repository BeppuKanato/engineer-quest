# テーマ4（遷移・保存のレスポンス）実装報告（Issue #151）

- 目的: 実機レビュー #138・#140・#142 で挙がった「画面遷移に約2秒」「フェーズ遷移時に無反応」「保存レスポンスが小さい文字のみ」の構造要因を取り除く。
- 適用範囲: フロントエンドの画面遷移（ホーム／コース一覧／ヘッダー）と、学習画面（入口・フェーズ完了保存）。
- 最終確認日: 2026-11-06
- 正本へのリンク: 調査の全文は Issue #138・#140・#142 のコメント。本書は実装内容の記録。

## 調査で特定した要因（要約）

- ヘッダーのナビクリックで全画面オーバーレイが出て、次画面のスケルトンと二重に遮断していた。
- ホーム／コース一覧は毎回スケルトンから描き直し（コース一覧は取得時に一覧を空にする）、前回データの保持表示がなかった。キャッシュは staleTime がホーム15秒／コース30秒と短く、学習系の変更で無効化されるため再訪時にほぼ効かなかった。
- 両ページとも UserSessionProvider を使わず、ページごとに onAuthStateChanged＋getIdToken を待っていた。
- フェーズ完了時は画面全体が inert になり、反応は「進捗を保存しています。」の1行のみ。画面遷移は保存 POST（カードがある回は段階演出の全編も）の完了を待つ構造。
- 学習画面の入り口も開始記録の POST 完了まで描画を止めていた。

## 実装内容

### 画面遷移（#138）
- N1: ホーム／コース一覧は `useUserSession` のトークンで取得し、ページ独自の認証購読を廃止。
- N2: 両ページとも初期表示を `clientQueryCache` の前回データ（新規 `peekClientQueryData`）で種付けし、再取得は裏で走らせる。スケルトンは初回だけ。取得失敗時も前回データを保持する（ホームは警告表示、コース一覧は一覧を消さない）。コース一覧の `setCourses([])` を廃止。
- N3: `home`／`courses` の staleTime を 300 秒に延長。鮮度は学習・作成・プロフィール等の変更時に走る既存のタグ無効化で担保する。
- N4: `appHeader` から `PageTransitionOverlay` を廃止（部品自体はログイン等の送信フロー用に残置）。
- N5: `getLearningProgress` を `fetchClientQuery` 化（キー `learning-progress:<courseId>`、staleTime 30 秒、courses タグ連動で学習系変更時に無効化）。

### フェーズ遷移・保存（#140・#142）
- P1: `BfsUnitPreview` の保存中 inert を廃止（保存失敗時のみ維持）。保存表示はスピナー付きの浮動ピル（`role="status"`、pointerEvents なし、zIndex 1250 でカード提示ダイアログの下）に変更。二重完了は従来どおり busy ガードで防ぐ。
- P3: `LearningScreen` は開始記録の POST を待たずに描画する。開始記録は裏で送り、失敗時は学習を止めず警告＋再試行として出す。`unit_view`／`unit_start` のログ送信タイミングは従来どおり開始記録の完了後。

## 対象外（意図的にやらなかったこと）

- P2（保存と演出の分離）: 演出の置き場は論点4の設計事項であり、#147（テーマ1）で提示形態ごと作り直すため対象外とした。本 Issue では保存待ちの見え方（P1）まで。
- サーバ側の高速化（Cloud Run／Neon のコールド要因）。API の絶対時間はコードから測れないため、実測比較はユーザ環境で行う。

## 検証

- 静的検証 `verify:response-feedback`（`front/scripts/verifyResponseFeedback.cjs`）を新設し、上記の構造（オーバーレイ廃止、セッショントークン化、保持表示、staleTime、進捗キャッシュ、inert 廃止、入り口の非ゲート化）を固定した。
- lint／typecheck／build と既存 verify 群の結果は PR に記載する。
- DB 変更なし。画面の実測（遷移時間の前後比較）はユーザ環境での確認事項。
