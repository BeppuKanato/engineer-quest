### 0.3 正解コードの形式に関する決定（2026-11-06 確定）

正解コードは**スタック形（反復）**を採用する（§7）。2026-11-06 のユーザー決定による。根拠は次の通り。

- **BFS との対比をコードまで貫通させる**: BFS の `bfs_distances` との差分が「キュー→スタック、`popleft`→`pop`、追加時の約束事」に絞られ、「保持するデータ構造を替えたら探索の性格が変わる」という単元間対比の中心命題が、コードレベルでもそのまま成立する。
- フェーズ2で表示する「スタック」が、学習者がフェーズ7で実際に書く**変数そのもの**になる。再帰形では、表示していたのは可視化専用の概念（呼び出しの積み重なり）であり、学習者の書くコードには現れなかった。
- フェーズ7の視覚的デバッグ（自分のコードのトレース再生）が、BFS と同じ変数検出方式（queue / distances に対する stack / visited / order）の延長で対応できる。再帰形は既存トレース基盤の対応範囲外だった（§9-7 は本決定により解消）。
- 再帰の学習自体は、将来の他単元（マージソート等）が担う位置づけとする（決定時のユーザーの付言）。

**出自についての注記**: 旧 DFS コースの正解コード（アーカイブ `archive/legacy-flow-2026-11-05` の `back/prisma/seedData/depthFirstSearchCourseSeed.ts` の `depthFirstSearchAnswerCode`）は再帰形だった。本設計は対比の一貫性のためスタック形に**書き換えた**ものであり、BFS 単元で確立した「正解コードは旧シード原文をそのまま契約化する」先例からの意図的な逸脱である。理由は本決定（本節）に記録する。なお訪問順（A → B → D → F → E → C）は、「入れる時点で発見済みにする（mark-at-push）」と「隣は逆順に入れる」という2つの約束事（§7.1）により、再帰形・旧教材の訪問順と一致させた。

## 1. グラフ設計

### 1.1 採用グラフ: BFS と完全に同一

ノード・座標・辺・隣接順序のすべてを BFS の正本（`front/src/features/learning/bfs/bfsGraph.ts`）と同一にする。新しい座標や辺は作らない。

**ノードと座標**（共通描画の論理座標 600×450、ノード半径30は `learning-player-ui.md` §2.3 の定義通り）

| ノード | x | y |
| --- | --- | --- |
| A | 70 | 150 |
| B | 220 | 80 |
| C | 220 | 230 |
| D | 380 | 80 |
| E | 380 | 230 |
| F | 530 | 150 |

**辺**（無向、ID は BFS と同一）: ab（A-B）, ac（A-C）, bd（B-D）, be（B-E）, ce（C-E）, df（D-F）, ef（E-F）

**隣接リスト**（コード・テストで使う辞書。BFS 単元の実装テストで使われたものと同一）

```python
{ "A": ["B", "C"], "B": ["A", "D", "E"], "C": ["A", "E"],
  "D": ["B", "F"], "E": ["B", "C", "F"], "F": ["D", "E"] }
```

隣接リストの並び順が DFS の訪問順を決めるため、この順序自体が基準データの一部である（実装側で並び替えてはならない）。

### 1.2 同一グラフを採用する理由

- 指針 §1「ビジュアル表現の統一」: 2つの単元で同じ図を使うことで、「同じ図を、違う順序で調べる」という BFS↔DFS の対比そのものが教材になる。旧 DFS コースも同じ図を使い、「BFSと同じ図を、違う順番で調べる」と明示していた。
- 共通描画基盤（`GraphDrawing.tsx` / `graphGeometry.ts`）と BFS の座標がそのまま使え、描画の再検証が不要。
- 距離層（○歩）の帯は DFS には存在しないため使わない（`layers` は空）。代わりに下部領域へ「スタック」と「訪問順」を表示する（§2.1）。

### 1.3 このグラフで DFS の違いが見えること

実行検証済みの訪問順対比（出発点 A）:

| 手法 | 訪問順 |
| --- | --- |
| BFS | A → B → C → D → E → F（近い順） |
| DFS | A → B → D → F → E → C（1本の道を奥へ） |

違いが際立つ点:

- **深く潜る**: A→B→D→F→E→C と、取り出すたびに奥の場所へ進んでいく。「深さ優先」が訪問順そのものに現れる。
- **A の隣なのに最後**: C は A の直接の隣だが、DFS では最後に訪れる。BFS では2番目だった場所との対比が最も劇的で、「近い順ではない」ことを示す中心場面になる。しかも C は最初にスタックへ入れた場所であり、最初から最後までスタックの底に残り続ける。後入れ先出し（LIFO）が目に見える形で現れる。
- **入る順と調べる順のずれ**: E は B を調べた時点でスタックに入るが、取り出されるのは F の後である。「スタックに入った順」と「調べる順」が一致しないことが、mark-at-push の動きとして見える。
- **行き止まりで戻る**: F を取り出すと、隣はすべて発見済みで何も追加されない（行き止まり）。次に取り出されるのは、スタックに残っていた E である。「戻る」がスタックの残りを取り出す動きとして現れる。

### 1.4 このグラフの代償（明示）

基本例では、行き止まり（F）のあとに取り出される E には、まだ調べていない隣が残っていない（すべて発見済み）。つまり「行き止まりのあと、残っていた場所を取り出して、そこから新しい隣へ潜り直す」場面（分岐の再開）は基本例には出ない。この不足はフェーズ6の転移グラフ（ツリー型、§6 問2。J の行き止まりのあと K が取り出される）で補う設計とした。十分かどうかは §9-3 の判断事項。

## 2. フェーズ2 実行トレース

### 2.1 状態仕様（BFS の `BfsExecutionCanvasState` に対応する DFS 版の案）

各ステップは、その時点の完全な状態（スナップショット）を持つ（BFS と同じ原則）。

- `operation`: ステップの種別。`push-start`（出発点をスタックに入れる）/ `pop`（スタックの末尾から取り出す。nodeId を持つ）/ `push`（未発見の隣をスタックの末尾に追加する。from・nodeId・edgeId を持つ）/ `skip-visited`（発見済みの隣を追加しない。from・nodeId・edgeId を持ち、辺は破線で強調）/ `no-add`（隣がすべて発見済みで、この取り出しでは何も追加されなかった。nodeId を持つ。行き止まりを含む）/ `finish`（スタックが空になり、すべて調べ終えた）
- `current`: 処理中のノード（なければ null）
- `stack`: スタックの中身。下（最初に入れた側）→上（末尾＝次に取り出す側）の順の配列。表示は左→右に並べ、右端が末尾
- `order`: 訪問順（取り出して記録した順の配列、その時点までの部分）
- `nodes`: 各ノードの `status`（未処理 / 処理中 / スタック内（追加済み・まだ取り出していない）/ 完了（取り出して調べ終えた））
- 色対応（プレイヤー UI 定義 §2.1 をそのまま適用）: 処理中＝青、スタック内＝ベージュ（同定義の「データ構造の中に保持されている要素」に文字通り当たる）、完了＝グレー、未処理＝白。距離層の帯は使わない
- ラベル: スタック表示のラベルは「スタック」（ステップ1で導入）。訪問順の表示ラベルは「訪問順」
- 配置: 上部にグラフ（600×360 相当）、下部にスタックと訪問順の2行（BFS のキュー表示位置に対応）
- 再生間隔: BFS と同じ 3500ms を想定（プレイヤーの下限 2.5 秒を上回る）

キャプションの言葉づかい: スタック内のノードへの言及は「すでにスタックに入っているので」、完了したノードへの言及は「すでに調べ終えているので」と書き分ける。状態の区別を言葉でも正確に伝えるため。

ステップ化の粒度: BFS の先例に倣い、発見済みチェックのすべてをステップにしない。初出のチェック（B→A）と D→B は独立ステップ（skip-visited）とし、それ以外は no-add ステップ（F・E）に畳む（§2.3 注記）。追加（push）は BFS のキュー追加と同様に、すべて独立ステップとする。

### 2.3 トレース設計の注記

- チェックの畳み方: F の隣チェック（E はスタック内、D は完了）はステップ13（no-add）に、E の隣チェック（F・B は完了、C はスタック内）はステップ15（no-add）に、C の隣チェックはステップ17の前提として、それぞれ畳んだ（BFS がフェーズ2で発見済みチェックの大半を畳んだ先例に倣う）。独立ステップとして残した skip-visited は B→A（初出チェック）と D→B の2件。
- コード側のチェック順序は逆順（§7）だが、フェーズ2のキャプション列は「起きた出来事」の順に並べている。push の順序（例: A の処理では C の次に B）が、コードの `reversed` の見た目そのものである点は §9-12 の教え方の論点に残す。
- ステップ13（行き止まり）とステップ14（残っていた E の取り出し）の組が、DFS の「戻る」を表す中心場面である。明示的な「戻る」動作は存在せず、行き止まりのあとにスタックの残りを取り出すことで戻る、という形をキャプションでも一貫させる。
- 冒頭にクッションを置く案: ステップ1の前に、単元間の橋渡しとして「幅優先探索で調べたのと同じ図を、今度は1本の道を奥まで進んで調べます。」の1コマを置くかどうかは、BFS 単元との接続（#77 の単元フロー側）の設計と合わせて決める。少なくとも単元導入かフェーズ2冒頭のどちらかでこの一文を置くことを推奨する。

### 2.4 フェーズ4への対応（operation とコード行の対応表）

フェーズ4は、このトレースに §7 のコード行対応を付加して再生する（BFS と同じ方式）。対応の骨格は次の通り。フレーム単位の詳細設計（BFS では62フレーム）は実装段階の作業とする。

| トレースの出来事 | 主に対応するコード行（§7 の意味ID） |
| --- | --- |
| 単元開始前（コード全体の提示） | define-function / initialize-visited / initialize-order / initialize-stack |
| push-start-a | initialize-visited → initialize-stack |
| pop（各回） | while-stack → pop-node → append-order |
| push（各回） | for-neighbor-reversed → if-unvisited → mark-visited → append-stack |
| skip-visited（各回） | for-neighbor-reversed → if-unvisited（条件が成り立たない） |
| no-add（各回） | for-neighbor-reversed を最後まで回し、if-unvisited が一度も成り立たない |
| finish-all | while-stack の終了 → return-order |

注意: コードは BFS と同じフラットなループであり、行が入れ子の深さごとに繰り返されることはない（旧・再帰形設計で必要だった「呼び出しの深さ」の表現は不要になった、§9-4）。フェーズ4の変数表示は、現在の `node` に加えて `stack` と `order` を表示する想定。`visited` は集合のため、表示形式（並び順の扱い）は実装段階で決める。

## 3. フェーズ1 動機づけの場面構成案

### 3.1 モチーフ

BFS のフェーズ1が「最少手数でゴールに着く」問いだったのに対し、DFS は**「場所が分からない宝を、漏れなく探し出す」**問いにする。DFS が保証するのは最短ではなく「漏れなく・重複なく調べ尽くすこと」であり、動機づけの問いもそちらに合わせる（指針 1-2 の留意事項: アルゴリズムが保証する条件に適合する例を提示する）。

題材は BFS と同じ迷路（2行×3列: 上段 A B D / 下段 C E F）を使い、宝は C に隠れている設定にする。C はフェーズ2の DFS で最後に訪れる場所であり、フェーズ1の歩行（A→B→D→F→E→C）がフェーズ2の実行順と一致する。

### 3.2 場面列（案、18場面）

- **隣は逆順に入れる**: スタックは末尾から取り出すため、隣接リストの順序（＝調べる順序）を保つには、隣を逆順に回して入れる。結果として「最初に調べたい隣が最後に入り、最初に取り出される」。この2点により、訪問順が再帰形・旧教材と一致する（A → B → D → F → E → C、実行検証済み）。

### 7.2 返す値の仕様: 訪問順リスト（距離ではない）

`dfs_order(graph, start)` は、**出発点から届く場所を、初めて訪れた順に並べたリスト**を返す。理由:

- DFS は最短距離を保証しない。仮に「最初にたどり着いた道の長さ」を距離として返すと誤った値になる。基本グラフの C は A から1辺だが、DFS の到達経路は A→B→D→F→E→C の5辺であり、これを「距離」と呼ぶと BFS 単元で学んだ距離の概念と矛盾する誤概念を作る。
- 旧 DFS コースの学習目標も「到達できる場所を初めて訪れた順に並べる」であり、正解コード・試験問題とも訪問順リストを返す仕様だった（この仕様自体は形式変更後もそのまま引き継ぐ）。
- 関数名 `dfs_order`（順序）もこの仕様と整合する。

- トークン（案）: `visited` / `order` / `stack` / `graph` / `start` / `node` / `neighbor` / `set()` / `append()` / `pop()` / `add()` / `reversed()` / `while` / `for` / `if` / `not in` / `return`（再帰関連のトークンは含まない）
- **レベル2（処理の流れ）**（コードは見せない）
1. 発見済みを記録する集合と、訪問順を記録するリストと、スタックを用意し、出発点を発見済みに記録してスタックに入れる
2. スタックが空でなければ、末尾から1つ取り出して、訪問順へ記録する
3. 取り出した場所の隣を逆順に見て、まだ発見済みでない隣があれば、発見済みに記録してスタックの末尾に入れる
4. スタックが空になったら、完成した訪問順を返す
- **レベル3（条件とループの骨格）**: 正解コードから制御行だけを元のインデントで引用する。対象の意味ID: `while-stack` / `for-neighbor-reversed` / `if-unvisited`（`while stack:` / `for neighbor in reversed(graph.get(node, [])):` / `if neighbor not in visited:`）
- **レベル4（並び替え前のコード）**: フェーズ6問5の Parsons 盤面を練習モード（採点なし）で提示する（BFS と同方式）

### 7.6 完了時

- 完了定義: 全テスト（表示用・判定用）通過で完全クリア（ハードゲート、BFS と同じ）
- 全達成リザルトの称号（案）: 「深さ優先探索（DFS）マスター！」
- 締め文（案）: 「深さ優先探索のコードを完成させ、基本ケースと境界ケースのすべてのテストを通過しました。この単元の学習は完了です。」

## 9. 未決事項・リスク一覧

### 9-1 フェーズ7のタイピングの崖（判断未確定、BFS 単元からの持ち越し）

フェーズ1〜6にコードのタイピングがなく、フェーズ7で自由記述に跳ぶ「崖」の問題は、BFS 単元でも未判定のままである（通し確認後に判断する方針）。**スタック形の採用により、DFS 側の追加負荷は解消した**: 内側の関数定義と再帰呼び出しが不要になり、フェーズ7で書くものは while / for / if とリスト・集合の操作で、BFS と同程度の負荷に下がった。本設計は現行の7フェーズ型のまま書いたが、BFS 側で崖対策（フェーズ6の構成変更、タイピング穴埋め形式の追加等）が決まった場合は、DFS もそれに追随して見直す必要がある。DFS 単元の実装着手は、BFS の通し確認と崖の判断を待つのが安全である。

### 9-2 コード形式（再帰形 vs 反復形）

スタック形（反復）で確定した。理由は §0.3 の通り（BFS との対比をコードまで貫通させる／フェーズ2のスタックが学習者の書く変数そのものになる／トレース基盤と同型になる／再帰の学習は将来の他単元が担う）。旧設計が挙げていた反復形の複雑さ（逆順に積む必要があり規則と見た目がずれる、発見済みの記録時点が分岐する）については、約束事として §7.1 に明記し、訪問順を再帰形と一致させることで処理した。残る課題はその約束事の教え方であり、§9-12 に移した。再帰形へ戻す場合はフェーズ2・4・5・6・7のほぼ全ての再設計が必要になるため、本項は記録として残す。

### 9-3 フェーズ2トレースの形（単一の潜行が全体を覆う）

基本例のトレースは「取り出すたびに奥へ進み、行き止まりのあとはスタックの残りを順に取り出す」形になる（§1.4）。「取り出した場所に、まだ調べていない隣が残っていて、そこへ潜り直す」動きはフェーズ6問2のツリー型グラフで補う設計だが、フェーズ2の時点でこの動きを見せなくてよいかはレビュー判断が要る。代替案として、基本グラフの隣接順序を変えて分岐再開を基本例に含めることも可能だが、その場合は BFS との隣接リスト同一性が崩れる。

### 9-4 フェーズ4のフレーム設計

旧設計では、再帰の呼び出しの深さごとに同じ行が繰り返し現れることへの表現（現在の呼び出し元・深さの表示）が課題だった。スタック形の採用によりこの課題は解消し、フレームモデルは BFS と同じフラットなループで足りる。残る軽微な事項として、フェーズ4の変数表示に `visited`（集合）をどう見せるかがあり、これは実装段階で決める。

### 9-5 Parsons の採点許容範囲

初期化の3行（initialize-visited / initialize-order / initialize-stack）は、§6 の通り相互に順不同を許容対象とした。残る判断事項は `mark-visited`（10行目）と `append-stack`（11行目）の扱いである。2行は if の中で連続し、「入れる時点で発見済みにする」という約束事の範囲内では、入れ替えても動作は変わらない。一方、この2行の順序自体が約束事の体現（記録してから入れる）でもあるため、「動作上等価な並びを不正解とするか」は判断が要る。含める場合は interchangeableLineGroups に `[mark-visited, append-stack]` を追加する。

### 9-6 フェーズ7の結果表示（リスト型の返り値）

BFS の結果表示部品（距離の辞書を前提にした差分表示）は、リスト型の返り値には流用できない。順序の誤りをどう見せるか（不足した要素・余分な要素・順序の入れ違いの区別）は実装段階の設計事項。表示用テストの図（D1・D2 のグラフ表示）は BFS と同じ仕組みで足りる。

### 9-7 フェーズ7の視覚的デバッグ（自分のコードのトレース再生）

旧設計では、再帰呼び出しのトレース取得が既存基盤で対応できるか未確認だった。スタック形の採用により、学習者のコードは `stack`（リスト）/ `visited`（集合）/ `order`（リスト）の変数で書かれ、BFS の queue / distances 検出と同型の方式でトレース変換できる。再帰への対応は不要になった。残るのは検出の具体仕様（変数名によらない検出範囲等）であり、実装段階の事項とする。

### 9-8 プレイヤーの状態名と色の一般化

プレイヤー UI 定義 §2.1 でベージュの状態は「キュー待ち」という名称だが、その意味は「データ構造の中に保持されている要素」と定義されている。DFS ではこの色を「スタック内」に使うが、表示対象が実在のスタック変数の中身であるため、定義の意味とは文字通り一致する。残るのは、実装時にプレイヤー側の状態名・型（BFS の `queued` 等）を一般化するか、DFS 側で読み替えるかという実装判断のみ。色そのものは変更しない。

### 9-9 単元の順序と BFS 対比の前提

本設計のフェーズ1・2は「BFS と同じ図」という対比を一部前提に含む（§2.3 のクッション案など）。学習者が DFS 単元を先に受けた場合、その対比は弱まる。コース内での単元順を BFS→DFS に固定/推奨するかは、単元接続側の判断事項。

### 9-10 フェーズ3問2の形式差

§4 の通り、問2を BFS の「新しく入るもの」型から「行き止まりのあとに取り出すもの」型へ変えた。指針の連動パターンには沿うが、BFS と形式が異なる意図的な差分である。指針側に「データ構造への追加が起きない場面では、直後の変化として次の取り出しを問うてよい」という一般化を書くかどうかは、指針改訂の判断事項。

### 9-11 「スタック」という用語の誤解リスク

旧設計では、フェーズ2で表示するものが再帰の呼び出しの積み重なり（実在しない変数）であり、「スタックという変数がある」という誤解のリスクを挙げていた。スタック形の採用により、表示するスタックは学習者がフェーズ7で書く実在の変数そのものになったため、このリスクは解消した。知識カード2（リストで作るスタック）は、この変数そのものを接続先とする位置づけに更新した（§8）。

### 9-12（新規）約束事（mark-at-push と逆順投入）をフェーズ4でどう教えるか

スタック形の正解コードは、2つの約束事の上に成り立っている（§7.1）: (a) 隣は逆順に入れる、(b) 発見済みの記録は入れる時点で済ませる。フェーズ2では、この約束事は「入れる順序」と「記録のタイミング」の見た目として現れるが、理由づけはまだ与えられていない。フェーズ4でコードと対応づける際に、少なくとも次を教える必要がある。

- 逆順の理由: 末尾から取り出すので、最初に調べたい隣が最後に入るようにする。フェーズ2の push の順序（例: A の処理で C の次に B が入り、B が先に取り出される）と結びつけて説明する。
- mark-at-push の理由: 取り出す時点で記録する方式では、同じ場所が別の隣から二重にスタックへ入り、二度取り出される。具体例（例: E は B からも C からも隣接している）で示すのが有効と考えられるが、基本例のトレース内で二重投入が起きる場面はないため、説明用の場面を別に用意するか、キャプションの言葉で済ませるかは未決。
- フェーズ2のキャプションが「出来事の順」に逆順投入を提示するため、学習者が入れる順序を「調べる順序」と取り違える可能性もある。フェーズ2側で「後で調べるために」という言い回し（ステップ3・6）で緩和したが、十分かは実装後の確認が要る。
