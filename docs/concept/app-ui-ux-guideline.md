# Engineer Quest アプリ UI/UX 方針

- 目的: 新フロー（7フェーズ教材）をアプリへ組み込むにあたり、アプリ全体の UI/UX について確定した決定を集約する。
- 適用範囲: アプリ本体の画面設計・演出・色・進捗表示・報酬まわり。新フロー組み込み（Issue #78）と旧フロー削除の設計前提になる。状態: 正本。最終確認日: 2026-11-05。
- 経緯: 検討項目リスト（Google Drive「2026-11-05_EngineerQuest-UIUX方針-検討項目リスト」）の9論点を、2026-11-05 に1件ずつ検討して決定した。
- 対象外の正本: 教材の内容と学習フローは [教材指針](learning-materials-guideline.md)、学習プレイヤーの UI は [プレイヤー UI 定義](learning-player-ui.md) が正本であり、本方針はそれらを変更しない。

## 1. 情報設計と入口導線

- 学習単位は「コース＝単元」とする。コース詳細（ロードマップ画面）は、フェーズ一覧・進捗・開始ボタンを持つフェーズ型に作り替える。ミッション階層は学習者の導線から外す。
- 旧フローは混在させない。旧コースは、中身（seed・DB）もコード（ミッション画面・Activity 実行まわり）も一括で削除する。削除前に、対比用のアーカイブとしてブランチを切り、残す機能（作る・コース試験・フィードバック等）と共有している部品の棚卸しを行う。なお、現在デプロイされている旧コース形式に実利用者はいないため、利用者の進捗保全や移行配慮は前提にしない。
- フィードバック v1 のトリガー場面の1つである「Mission 完了」は、旧フロー削除に伴い新フロー側で定義し直す前提とする（判断自体は研究設計側、§9）。
- ホームは学習中心とする。「続きから始める」（進行中の単元・フェーズ）を最上位に置く。

## 2. 進捗の見せ方

- フェーズ進捗の表示は、グラフィカルなアイコンボタン方式とする。イラストのボタンが主で、文字は補助。状態（未着手・進行中・完了）は色で判別でき、完了が一目で分かること。
- 「次にやるもの」の上にはマスコットを置き、文字を読まずに次の行動が分かるようにする。
- 再開の粒度はフェーズ単位とする（未完了フェーズの先頭から再開）。例外として、フェーズ7のコード下書きだけは保存する。他フェーズの途中状態は保存しない。

## 3. 知識カード

- カードの設計は現行の関連概念方式を維持する（学んだ概念そのものではなく周辺の関連概念を扱い、説明・つながり・活用例を載せる）。
- プールはアルゴリズム（単元）単位とし、目安は1単元5枚。カテゴリ（経路探索など）単位のプールは候補として記録し、同系列の単元が増えたタイミングで再検討する。
- 出現の仕組みは、現行のテーブル方式を踏襲する。完全な確率にはしない（学習は繰り返し回す前提のコンテンツではなく、完全確率では揃わないケースが大半になるため）。テーブルは、ランダムに見え、ユーザー間で差が出るための仕組みであり、ミッション完了をフェーズ完了に読み替えて、付与のタイミング・順序・出現する部分集合をテーブルごとに変える。
- 1回の学習で出現するのはプールの約半分が目安（プール5枚なら3枚程度）。1回で全て揃うことは前提にしない。
- BFS の具体的なカードとフェーズの対応づけは、実装時に決める。

## 4. 獲得・完了の演出

- 知識カード獲得の演出は、前振り（何か出そうな気配）→出現→賞賛、の段階を踏むこと。小さくてもよいが、「特別な確率で出るものを見つけた」という達成感・レア感をユーザーに与える。レアリティに応じて演出の強さを変える。
- 前振りなく唐突に「見つけた」と表示する現行の形は採らない。
- 置き場所はフェーズの区切り（リザルト内／遷移前）とし、学習の流れを長く止めない。
- コレクション画面では、未所持カードをシルエット＋「？？？」で表示し、存在と残り枚数だけを示す。

## 5. ゲーム的な UI（定義と原則）

「ゲーム的な UI」は次の2層を指す。

1. 日常の動き: ページ遷移や状態変化にアニメーションを付け、画面が唐突に切り替わらないシームレスな体験にする。待ち時間をごまかすためのスケルトン表示や意図的な待ちはしない。
2. 賞賛の演出: 特別な場面（下記のホワイトリスト）では、演出によってユーザーを称える体験を強化する。§4 のカード獲得演出はその具体例である。

日常の動きの3原則（適用範囲はアプリ側の画面。教材フェーズ内はプレイヤー UI 定義が正本）:

1. 画面は切り替わらず「つながる」。遷移には短いアニメーションを必ず付け、無演出の瞬間切り替えをしない。
2. 状態変化は動いて見える。進捗・マスコットの位置・数値はジャンプせず、アニメーションで変化する。
3. 待ちを作らない。アニメーションのために表示を遅らせない。コンテンツが先、動きは追随する。

賞賛演出のホワイトリスト:

- 入れる場面: 知識カード獲得／実績獲得／単元完了（最終リザルト）／コレクション制覇（プールコンプリート）／フェーズ完了リザルトでの賞賛（教材内の褒め文言自体は教材指針が正本）。
- 入れない場面: 学習の最中（再生・回答・実装の途中）／実務画面（入力・設定・ログイン等）／エラー表示（静かに正確に伝える）。

横断原則として「賞賛の勾配」を置く。細かいリザルトで達成感は出しつつ、大きい賞賛は単元の最後に集中させる。賞賛演出のために学習のシームレス性を削らない。

## 6. 実績・報酬

- 新フロー用の実績条件を追加する。単元完了を軸に、意味のある節目（初めての自力実装クリア、確認フェーズの初回全問正解など）にも小実績を置く。フェーズごとの乱発はしない。
- 完了時の提示は最終リザルトに集約する。実績の獲得は最終リザルトの中で提示し、報酬ランという独立フローは新フローでは作らない（旧フロー削除と一緒に消える）。
- 道中の小実績は、知識カードと同様にフェーズの区切りで提示する。

## 7. 色・デザイントークン

- アプリ本体用のデザイントークンを新設する。導入は、作り替える画面（コース詳細・ホーム等）から始め、既存画面は次に触るタイミングで寄せる段階移行とする。全画面の一括トークン化はしない。
- プレイヤー用トークンとの関係: 学習の状態（進捗・完了・現在地）を表す色だけを共通化する。教材キャンバス内の色（処理中・キュー待ち等のアルゴリズム状態）は意味が別物なので、プレイヤー専用トークンのまま分離を維持する。

## 8. 共通ナビゲーションと画面の骨格

- 全体の骨格は維持し、差し替えるのは学習導線のみとする。周辺機能（作る・掲示板・コレクション・実績・プロフィール）の位置づけと導線は現行のまま変えない。

## 9. フィードバック提示の扱い（境界）

- パーソナライズド・フィードバックの提示場所・形式は、本方針では決めない。修論実験の操作面であり、判断は研究設計（フィードバック要件と、その新フローへの読み替え）側で行う。本方針の側から変更しない領域として明記する。

## 実施への申し送り

- Issue #78（アプリ組み込み）の設計前提は §1・§2 とする。他の節は、決まった論点から順に組み込みへ反映し、全節の確定を組み込みの前提にしない。
- 学習プレイヤーの UI 定義への適合（Issue #83）は本方針と独立に実施できる。
- 本方針に数値のない事項（テーブルの中身、演出の長さ、トークンの具体値）は、実装時に本方針の範囲内で決める。
