# アルゴリズムコース作成ガイドライン

## 1. 目的

本ガイドラインは、Engineer Questで新しいアルゴリズムコースを作成するときに、コース間で次の品質を統一するための基準である。

- 学習の流れ
- Mission・Activityの粒度
- 説明、可視化、問題、Pythonコードのつなぎ方
- Activity画面の情報構成と操作方法
- Course Missionの到達水準
- シードデータとレンダラーの実装方法

新規コースは本ガイドラインに従って設計・実装する。既存コースを修正するときは、本ガイドラインとは別に移行チェックリストを作成する。

## 2. 教材コンセプト、対象学習者、基本方針

### 2.1 全コース共通の学習者像

主な対象は、大学でプログラミングを学んでいる学生とする。対象アルゴリズムについては、名称を聞いたことがある場合も含め、処理を具体的に説明・追跡できない初学者として扱う。

標準的な学習者像は次のとおりとする。

| 項目 | 想定 |
| --- | --- |
| プログラミング経験 | 半年から2年程度を中心に想定する。ただし、年数より実際に扱える構文と学習行動を優先する。 |
| Python経験 | 変数、条件分岐、繰り返し、リスト、文字列、添字、簡単な関数などの入門内容を、授業または初心者向け教材で学んだ経験がある。 |
| コード作成経験 | 授業で出された課題や学習動画・Web教材の内容を実行し、見本を部分的に変更した経験がある。 |
| 自力制作 | 自分で考えたものも作ってみたいが、何を作ればよいか、処理をどう分解すればよいか分からないことがある。小規模なアプリを自力で完成させた経験は前提にしない。 |
| アルゴリズム経験 | 基本的なアルゴリズムを一部知っている場合はあるが、対象アルゴリズムは未経験として扱う。 |
| 学習方法 | 主に大学の授業、演習課題、初心者向け動画、Web教材、サンプルコード、AIへの質問を利用してきた。 |
| 専門的な文章への慣れ | アルゴリズムの専門書、形式的な定義、数式中心の説明を読み慣れていることは前提にしない。 |
| 用語・英語への慣れ | コンピュータ科学の専門用語、略語、英語の変数名から役割を推測できることは前提にしない。 |
| 分からないときの行動 | 説明や図を一度は見直すが、知らない用語や解釈できない表示が重なると、何を調べればよいか分からず離脱する可能性がある。 |
| 記憶の前提 | 前のActivityの考え方は学んでいても、具体的な値、変数名、図の状態を正確に覚えていることは前提にしない。 |

経験年数だけで教材の難易度を決めない。開発経験が長くても対象アルゴリズムや専門用語に不慣れな場合があり、反対に経験年数が短くても特定の構文を使える場合がある。コースごとに、実際に前提とするPython知識を明記する。

### 2.2 学習者の動機とEngineer Questが提供する価値

学習者がコースへ取り組む理由として、授業で必要になった、知らないアルゴリズムに興味を持った、Pythonで実装できるようになりたい、コーディング問題へ応用したい、コース完了による達成感を得たい、などを想定する。

強い学習意欲や、分からない内容を自分で外部検索し続ける粘り強さは前提にしない。教材だけで理解が進んでいると感じられず、用語・記号・UIの解読が続く場合は離脱し得るものとして設計する。

Engineer Questのアルゴリズムコースが提供する中心的な価値を、次のように定義する。

> 初めて見るアルゴリズムでも、専門用語や完成コードの暗記から始めず、現在のデータ、注目している対象、次に起きる変化を具体的に追うことで、その積み重ねがどのように問題の解決へつながるかをイメージできる。そのイメージをPythonコードと対応づけ、最終的に自分で処理を組み立てられる。

教材は外部サイト、専門書、検索エンジン、AIへの質問を利用しないと理解できない構成にしない。外部資料は任意の発展学習には利用できるが、コース完了に必要な前提を外部へ委ねない。

### 2.3 アルゴリズムを理解した状態

本ガイドラインでは、アルゴリズムを理解した状態を、用語の定義や処理理由を文章として暗記・説明できることだけでは判断しない。

学習者が、アルゴリズムの実行中に次を頭の中または画面上でイメージできることを重視する。

1. 現在のデータがどのような状態か読み取れる。
2. 現在どの要素、位置、範囲、状態に注目しているか分かる。
3. 次に行われる判断または更新を予測できる。
4. 処理後にデータの状態がどう変わるか予測できる。
5. 一連の状態変化によって、対象の問題がどのように解決されるかイメージできる。
6. 各判断・更新とPythonコードの行を対応づけられる。
7. 最終的に既習コードを組み合わせ、自分で実装できる。

言葉での説明は理解確認の一つとして使用できるが、表現力だけを測る問題にしない。状態の選択、次の変化の予測、STEP TRACE、コード対応、実装など、理解を直接確認できる方法を優先する。

### 2.4 コース設計票

新しいコースを作成するCodexは、Mission、Activity、シードデータ、専用可視化の実装へ着手する前に、コース設計票を作成する。利用者が事前に設計票を記入してプロンプトへ添付することは前提にしない。

コース設計票は、次の目的で使用する。

- Codexがアルゴリズムの知識をそのまま教材へ流し込まず、対象学習者に合わせて再構成するための設計契約
- Mission・Activityの途中で、対象、用語、到達状態、標準コードが変わらないようにする基準
- 作成者が、なぜその学習順序と表現を選んだか後から確認するための資料
- 教材レビューで見つかった問題が、設計、説明、問題、UI、コード接続のどこに由来するか判断するための基準

一つのプロンプトでコースを作成する場合、Codexは設計票の作成後に確認待ちを挟まず、設計票を基準として実装と検証まで進めてよい。設計票は`docs/course-designs/<course-id>.md`へ保存し、学習者向け画面には表示しない。

コース設計票には、少なくとも次を記載する。

- 対象アルゴリズム
- 主対象となる学習者
- 想定するプログラミング経験とPython前提知識
- 想定する過去の学習方法
- 専門書、専門用語、数式への慣れ
- 分からないときに想定する行動と離脱要因
- このコースへ取り組む主な理由
- 学習者がこのコースに期待する価値
- アルゴリズムが解決する問題
- コース開始時点と完了時点の理解
- 学習者の頭の中に作らせたい処理イメージ
- 初めて登場する概念、専門用語、略語、英語変数、記号
- 概念、用語、コード要素の依存関係と導入順
- 想定されるつまずきと、その予防・復習方法
- コース内で扱わない発展知識
- 理解できたと判断する方法
- 標準完成コード、スターターコード、テスト方針
- Mission構成と各Missionの到達状態
- 外部教材調査の記録と、採用した説明順の根拠
- 各Missionについて、開始時にできること、完了時にできること、次へ残す課題
- 各Activityについて、直前までに確立した事実、このActivityで生じる問い、その事実から結論へ進める理由
- アルゴリズム固有の各コード断片を、どのMissionで説明・可視化・練習・統合するか示すコード学習対応表
- 各ビジュアルで最初に見てほしい対象、補助的に見る対象、表示しない情報を定める視線設計

学習者向けの文章へ、設計票、ガイドライン、実装上の都合、採点方式を守っていることの説明を流用しない。

### 2.5 コース全体の原則

- 1 Activityでは1つの学習コンセプトを扱う。
- Activityを細かく分けること自体を目的にしない。
- 説明、図、マスコットの補足が同じコンセプトを扱う場合は、1つのActivity内に配置してよい。
- 採点を伴う練習は、説明Activityと分ける。
- 学習者の操作は、アルゴリズムの理解を進める場合だけ求める。
- 基本的な大小比較や単純計算だけを、独立した問題として出さない。
- 学習上の難しさはアルゴリズムの考え方から生じるものとし、未定義の用語、英語、記号、図の読み方、UI操作の解読を難しさにしない。
- コースの理解に必要な内容を、学習者自身による外部検索へ委ねない。
- 各Activityは、前のActivityの表示内容を覚えていなくても、その画面内の情報から目的と前提を理解できるようにする。
- 練習Activityでは、回答前に正解となる位置、範囲、状態、結果、理由を表示しない。
- 新しい処理を理解した後、対応するPythonコードへ接続する。
- Pythonコードは、コード行、アルゴリズム上の役割、画面上の状態変化を対応づけて説明する。
- アルゴリズム固有の主要なコード断片は、それを学ぶMission内でも穴埋め、並べ替え、対応づけなどで練習し、最終Missionだけへまとめて先送りしない。
- 同じ目的の操作には同じUIを使用し、画面幅が変わっても情報や操作が欠けないようにする。
- 最後の基礎Missionでは既習要素を統合し、Course Missionで自由実装する。

## 3. 標準のコース学習フロー

Mission数やActivity数を固定するのではなく、次の学習段階を共通化する。

### 3.1 Mission 1：コースを知る

Mission 1は、学習者がコースを受講するか判断するためのMissionとする。操作問題やPythonコードは置かない。

標準構成は次の4 Activityとする。

1. このアルゴリズムが解決する問題
2. 使われる場面
3. 関連するアルゴリズムと、このコースで扱う範囲
4. このコースで学ぶこと

原則として文章表示を使用する。目的の理解に必要な場合だけ簡単な図を使用し、アルゴリズムの詳細な動作や段階再生はMission 2以降で扱う。

利用場面や関連アルゴリズムの紹介では、受講判断に不要な知識を増やさない。名称と違いを簡潔に示し、このコースで何を学ぶかを明確にする。

「このコースで学ぶこと」には、学習者が理解できるようになる処理や到達状態を示す。「自由入力はCourse Missionだけ」「ガイドラインに沿って進む」など、教材制作側の規則を学習内容として表示しない。学習ロードマップは表示領域から見切れないよう、画面幅に応じて折り返し、縦積み、または操作可能だと分かる内部スクロールを使用する。

### 3.2 Mission間の接続

各基礎Missionの開始時には、前Missionとのつながりを明示する。

Missionの最初の説明では、少なくとも次を示す。

1. 前Missionで理解・実行できるようになったこと
2. その知識だけでは、まだ解決できない具体的な場面
3. 今回のMissionで新しく学ぶこと
4. 新しい内容が、未解決の場面をどのように解決するか

Mission内のActivity間にも同じ基準を適用する。各Activityは、直前までに確立した事実から生じる問いに答える構成にする。「次はこれを見ます」「ここではこの値を使います」だけで話題を切り替えない。次の内容が必要な理由を、次の形で一文にできることを確認する。

> ここまでにXが分かった。しかしYはまだ判断できない。Xを使ってYを判断するため、次にZを調べる。

この文を作れない場合は、説明文を増やして押し切らず、前提となる具体例、問題提起、または橋渡しActivityを追加して学習順を組み直す。

前Missionの最後に次の内容を予告していても、次Missionの導入を省略しない。時間を空けて再開した場合や、Mission画面を直接開いた場合でも、今回学ぶ理由が分かるようにする。

次のいずれかに当てはまる場合は、Missionの最初に独立した橋渡しActivityを配置する。

- 扱う対象が変わる
- 使用するデータや図の表現が変わる
- 処理の目的が変わる
- 新しい補助データ、表、前処理が登場する
- 前Missionの内容だけから、次の概念が必要な理由を推測できない
- 前Missionで扱った問題から一時的に離れ、内部構造や準備処理を学ぶ

橋渡しActivityでは、専門用語やコードから説明を始めない。前Missionで使用した具体例を必要最小限に再掲し、「何に困るのか」「何を再利用・改善・判断したいのか」を図や日常的な日本語で示す。

橋渡しActivityは説明用とし、原則として採点問題を置かない。接続が1〜2文で十分に理解できる場合は、独立Activityを作らず、最初のActivityの冒頭へ含めてよい。

Mission間の接続は、学習者向けに「前Missionとの接続を説明します」と書くのではなく、具体的な未解決場面を提示することで自然に示す。

### 3.3 中間の基礎Mission：概念を積み上げる

1つのMissionでは、関連する1つの処理単位を扱う。

基本的な学習順序は次のとおりとする。

1. 既習の方法で解ける具体例を確認する
2. 既習の方法では手間が大きい、または判断できない具体的な場面を示す
3. 「何を分かれば解決できるか」という問いを置く
4. すでに確立した事実を使い、新しい判断規則が成り立つ理由を説明する
5. 必要に応じて図や段階再生で、規則による1回の変化を確認する
6. 学習者が同じ規則で判断・操作する
7. 対応するPythonコードを説明する
8. 穴埋め、並べ替え、対応づけなどでコードを短く練習する
9. 別データで理解を確認する

これは学習上の順序であり、各項目を必ず別Activityにするという意味ではない。

- 説明と図が同じコンセプトを扱う場合は、1つの説明Activityにまとめる。
- 図を見るだけのActivityを機械的に追加しない。
- 採点を伴う判断・操作・コード練習は、説明Activityから分ける。
- Pythonコードが既習構文による直接的な表現であれば、概念説明の最後に短く示してよい。
- 新しいPython構文や複数行の処理を導入する場合は、独立したコード接続Activityにする。
- 不要な段階は省略してよい。

### 3.4 最後の基礎Mission：既習コードを統合する

最後の基礎Missionでは、新しいアルゴリズム概念や新しいPython構文を増やさない。これまでに学んだ処理とコードを統合する。

必要に応じて次のActivityを配置する。

- 処理とコードの対応確認
- コードブロックの並べ替え
- コード穴埋め
- 誤ったコードの修正
- 完成コードの役割説明

すべてを必須にはしない。アルゴリズムの理解確認に必要な形式を選択する。

このMissionでは自由入力式のPythonエディターを使用しない。タイトルも「実装しよう」ではなく、「コードを組み立てよう」「コードを完成させよう」など、既習要素の統合だと分かる表現にする。

### 3.5 Course Mission：自分で実装する

自由入力式のPythonエディターはCourse Missionだけで使用する。

Course Missionは次を備える。

- 関数名、引数、戻り値の明確な仕様
- 必要最小限のスターターコード
- 基本ケース、主要な分岐、境界ケースを含むテスト
- 未通過テストの表示
- 概念単位の段階的ヒント
- 全必須テスト通過による完了判定

テストケースは5〜7件程度を目安とする。ただし、件数よりも必要なケースを網羅することを優先し、件数だけでエラーにはしない。

## 4. Activityの設計

### 4.1 1 Activity 1コンセプト

1 Activityには、原則として次のうち新しいものを1つだけ入れる。

- 新しい用語
- 新しい状態
- 新しい判断規則
- 新しい状態更新
- 新しいPythonコード要素
- 既習内容を統合する1つの課題

同じ規則に属する対になる分岐は、1つのコンセプトとして扱ってよい。

例：

- 探す値が中央より小さい場合と大きい場合
- 発見時と未発見時の終了
- 交換する場合と交換しない場合

ただし、各分岐に別の新しい構文や複雑な処理が含まれる場合は分割を検討する。

新しい学習負荷は、アルゴリズム上の概念だけを指さない。次も新しい要素として数える。

- 専門用語と略語
- 英語の変数名
- 添字、数式、記号
- 新しい図の読み方
- 色、枠、ラベルが表す新しい状態
- 初めて使う回答操作
- Pythonの新しい構文

アルゴリズム上の話題が一つでも、これらを説明なしに複数追加している場合は、1 Activity 1コンセプトを満たしたと判断しない。原則として、1 Activityで新しく導入する主要な正式用語は1つまでとする。意味上切り離せない対の用語は同時に導入してよいが、具体例の中で両者の違いを見分けられるようにする。

### 4.2 Activity画面の情報構成

Activityは、実際の画面に合わせて次の要素で構成する。

1. **タイトル**：このActivityで理解・実行することを短く示す。
2. **要約・指示**：学習者が何に注目するかを1〜2文で示す。
3. **説明**：新しいコンセプトを簡潔に説明する。
4. **グラフィカル部分**：状態や変化の理解に必要な場合だけ表示する。
5. **操作・回答部分**：練習Activityでのみ表示する。
6. **マスコットのセリフ**：そのActivityで学習者に残したい要点を、短い日常的な言葉でまとめる。
7. **フィードバック**：回答後に結果、理由、次の行動を示す。

マスコットのセリフは、学習者からの疑問や教材への反論へ回答する欄として使わない。「つまり何ができるようになったか」「次から何を判断できるか」を1〜2文で要約する。本文と同じ長い説明を繰り返さず、未説明の根拠や新しい用語も追加しない。

### 4.3 Activity単体での理解

Activityは順番に学ぶことを前提とするが、画面を直接開いた場合や、時間を空けて再開した場合でも、そのActivityで必要な情報が分かるようにする。

- 使用する配列、探索対象、変数、現在の状態を画面内に示す。
- 前Activityで定義した変数を使う場合も、必要な定義または短い再掲を行う。
- 「前のActivityで説明したから」という理由だけで、問題を解くために必要な情報を省略しない。
- 既習内容を長く再説明せず、「この画面で使う前提」として必要最小限に示す。
- タイトル、要約、表示データ、操作対象の間で、異なる配列や変数名を混在させない。

これは教材制作者向けの設計基準である。「この画面を直接開いても分かるように」「前のActivityを覚えていなくても解けるように」など、ガイドラインを守っていること自体を学習者向け本文へ書かない。必要な前提を自然に再掲することで満たす。

例えば`numbers`と`n`を使うActivityでは、必要に応じて次のように有効なPythonコードとして再掲する。

```python
numbers = [6, 3, 5, 2]
n = len(numbers)
```

`n = len(numbers) = 4`のように、説明上の等式をPythonコード欄へ混在させない。値の説明はコード欄の外で「この例では`n`は4」と示す。

### 4.4 説明Activityと練習Activity

- 説明Activityには採点問題を入れない。
- 前へ・次へ・再生など、理解のための閲覧操作は説明Activityに含めてよい。
- 採点を伴う選択、並べ替え、穴埋めは練習Activityとして分ける。
- 知識定着のために複数問を解かせる場合は、説明Activityと練習Activityを分ける。

### 4.5 Activity設計時に明確にする項目

Activityを実装する前に、少なくとも次を明確にする。

- このActivityで新しく扱う1コンセプト
- 学習者がすでに知っている前提
- この画面内に再掲する必要があるデータ、変数、状態
- 学習者に見せる説明または求める操作
- 使用する標準問題型と、その問題型を選ぶ理由
- グラフィカル部分が「考えるための補助」か「回答を入力する操作対象」か
- 練習の場合、回答前に見せる情報と回答後に見せる情報
- 正解によって確認したい理解
- Pythonへ接続する場合、対応するコード行、処理の役割、状態変化
- 結果を導くために複数の候補や状態を調べる場合、学習者へ示す候補の範囲、判断基準、除外条件
- 最終結果だけでなく、学習者がその結果へ至る過程を追える情報
これらを説明できないActivityは、目的が曖昧か、複数コンセプトが混在している可能性があるため再設計する。

### 4.6 用語、記号、英語変数の導入

専門用語やコード上の名前を、学習者が意味を推測するための入口にしない。新しい概念は原則として次の順序で導入する。

1. 具体的なデータと状況を示す。
2. 注目する部分を色、位置、囲みなどで示す。
3. 日常的な日本語で、その部分の役割や変化を説明する。
4. 学習者が、同じ役割を別の例でも見分けられるか確認する。
5. 必要になった時点で正式名称を付ける。
6. Pythonコードへ接続するときに、英語の変数名と対応づける。

「正式名称の定義文を一度表示した」だけでは、その用語を既習として扱わない。具体例の中で何を指す言葉か区別できる状態になってから、その後の説明で使用する。

次を守る。

- 初出の専門用語、略語、英語変数は、同じ画面内で対象と役割を示す。
- 略語は正式名称を展開するだけでなく、教材内で何を表す値・表・状態なのか説明する。
- 英語変数名を導入する前に、日本語でその変数の役割を理解させる。
- 一度決めた日本語名、正式名称、変数名の対応をコース途中で変更しない。
- 辞書的な定義だけで理解させず、具体例、反例、状態変化のいずれかを用いる。
- 導入していない用語を、タイトル、要約、問題文、選択肢、図のラベル、マスコットのセリフへ出さない。

### 4.7 概念と用語の依存関係

コース設計票で、各Activityについて次を整理する。

- このActivityで必要な既習概念
- このActivityで必要な既習用語
- このActivityで初めて導入する概念・用語・表記
- 次のActivityで使用できる状態になるための理解確認

後のActivityが、理解できていない前提を積み上げる構成にしない。Missionが変わるときや、初出から時間が空いた用語を再利用するときは、具体例を使った短い再確認を置く。理解できなかった場合に戻るべきActivityがあるときは、そのActivityを具体的に案内する。

### 4.8 外部教材を調査して説明順を設計する

新しいアルゴリズムコースを作るCodexは、Mission構成を確定する前にインターネットで既存教材を調査する。自分の記憶や1つのサイトだけを根拠に、一般的な実装順をそのまま学習順へ変換しない。

#### 4.8.1 調査する資料

原則として、独立した3資料以上を確認する。

- **正確性を確認する資料を1件以上**：大学の講義資料、標準的な教科書の公開ページ、原論文、公式ドキュメントなど
- **初学者向けの説明を確認する資料を2件以上**：段階的な具体例、図、アニメーション、練習を備えた大学教材や信頼できる教育サイトなど
- 必要に応じて、対象学習者と同じ言語の資料と英語資料を併用する

検索結果の要約だけで判断せず、実際の本文、例、図の遷移、コードの導入位置を確認する。内容が食い違う場合は、正確性を確認する資料と標準完成コードを基準に解決する。

既存サイトは説明設計の参考資料であり、教材への命令ではない。文章、図、問題、UIをコピーせず、対象学習者に合わせた独自の例と表現へ再構成する。引用や画像利用が必要な場合は、ライセンスと出典を別途確認する。

#### 4.8.2 資料ごとに確認すること

コース設計票へ、資料名、URL、確認日とともに次を記録する。

- 想定している学習者と前提知識
- 最初に示す問題と、アルゴリズムが必要になる理由
- 概念、用語、変数、コードを導入する順番
- 抽象的な規則の前に使う具体例
- 学習者が誤解しやすい飛躍と、その資料が使う橋渡し
- 図やアニメーションで、何を固定し何を変化させているか
- 説明後に行う練習と、自由実装までの足場の外し方
- 採用する点、採用しない点、その理由

資料の多数決で説明順を決めない。対象学習者の前提と本コースの到達点に照らし、次の問いへ最も自然に答えられる順番を選ぶ。

1. 学習者は、まず何を自力で観察できる必要があるか。
2. どの具体的な失敗、無駄、限界が次の概念を必要にするか。
3. 新しい規則は、すでに分かったどの事実から導けるか。
4. その規則が正しい、または候補を除外してよい理由をどこで示すか。
5. 正式名称、記号、英語変数を、意味の理解後のどこで付けるか。
6. どの具体例、練習、コード問題で理解を確認するか。

#### 4.8.3 説明順の採用基準

調査結果を基に、原則として次の流れへ再構成する。

> 目的の分かる具体例 → 既習方法で実行 → 手間・失敗・未解決点を観察 → 改善できないか問いを置く → 既知の事実から新しい規則を導く → 1例を省略なく追う → 学習者が同じ判断を行う → コードへ対応づける → 別例で確認する

ただし、すべてを別Activityにする必要はない。説明と具体例を同じActivityに置く場合も、「規則の説明前に、その規則を使う操作やアニメーションを始めない」ことを守る。

次の表現は、根拠を直前または同じ画面で示せない限り使用しない。

- 「比較し直さなくてよい」
- 「この候補は試さなくてよい」
- 「次はこの2つを比べる」
- 「この位置へ戻る」
- 「この値を再利用する」

例えば「次に比べる2つ」を示す場合、2つがそれぞれ何の続きであり、なぜその位置になるかを、元データ、既知の一致範囲、今回追加された要素の関係から説明する。「次」という語だけで2つの位置をまとめない。

#### 4.8.4 設計レビューへの残し方

設計票には、最終的に採用したMission順だけでなく、少なくとも次を残す。

- 参考資料間で共通していた説明の骨格
- 本コースの学習者には難しいため変更した点
- 採用した各Missionの順番と、その順でなければ生じる理解の飛躍
- 主要な誤解ごとに、それを予防するActivityと確認問題

外部教材を調べた事実だけでは完了としない。調査結果がMission構成、Activityの接続、具体例、可視化、コード練習へ反映されていることを確認する。

## 5. 問題作成ルール

### 5.1 問題で確認する内容

問題では、アルゴリズム固有の理解を確認する。

適切な例：

- 現在の状態から次に調べる範囲を選ぶ
- 次に比較する要素を選ぶ
- どの状態更新が必要か判断する
- 処理とPythonコードを対応させる
- 既習コードを正しい順番に並べる

避ける例：

- 単純な大小比較だけを答えさせる
- 対象とする大学生にとって容易な四則演算だけを答えさせる
- 説明文をそのまま選び直すだけの問題
- アルゴリズムの理解に影響しない操作

### 5.2 複数問と逐次表示

- 同じ判断を反復する場合は、1問ずつ逐次表示する。
- 独立した反復問題は1 Activityあたり2〜4問程度を目安とする。
- 5問以上の独立問題が必要な場合はActivityの分割を検討する。
- すべての問題を縦に並べて一括表示しない。

ここでいう問題数は、異なる入力や異なる状況を使う独立した設問数を指す。

1つのアルゴリズム実行を段階的に追うSTEP TRACEのステップ数は問題数に含めない。1つの配列を発見または終了まで追う課題は、必要なステップ数が5以上でも1 Activityとしてよい。

### 5.3 Mission最後の確認

- 必要なMissionでは、最後に別データを使った確認を置く。
- 説明と数値だけを入れ替えた完全な模倣ではなく、同じ規則を別の状態へ適用させる。
- Mission内ですでに十分な転移課題がある場合、確認Activityを機械的に追加しない。

### 5.4 回答前に正解を見せない

練習Activityは、回答前の`PROMPT`状態と、回答後の`FEEDBACK`状態を明確に分ける。

回答前に表示してよいもの：

- 問題を考えるために必要な入力データ
- 現在の状態
- 既習の規則や必要最小限の前提
- 学習者が選択・操作できる候補

回答前に表示しないもの：

- 正解となる要素、位置、範囲だけを強調する枠や色
- 正解後の配列や更新済みの状態
- 「交換する」「右側を探す」など、そのまま答えになる説明
- 正解のコードブロック配置や対応関係
- 正解である理由や結果を確定的に示すマスコットのセリフ

回答後は、選択結果に応じて正解箇所、状態変化、理由を表示してよい。

説明Activityでは完成した動きを見せてよいが、その表示をそのまま採点問題の上部へ再利用し、答えを先に見せない。閲覧用の表示状態と練習用の出題状態は、同じデータを利用する場合でも表示フェーズを分ける。

### 5.5 誤答と再回答

標準方針は「誤答時に考え方のヒントを示し、再回答させる」とする。

- 1回目の誤答：正解を開示せず、注目点を示す。
- 2回目の誤答：より具体的なヒントを示し、必要に応じて正解と理由を開示する。
- 正解時：正解である理由と、次の概念へのつながりを示す。

正解開示の詳細は共通`feedbackPolicy`で管理する。Activity固有の例外を作る場合は、その教育上の理由をコメントまたは仕様へ残す。

### 5.6 回答後の進行と確認時間

回答直後に次の問題や次のステップへ自動で移動しない。学習者が選択結果、正誤、状態変化、理由を確認してから、自分の操作で進めるようにする。

標準の進行は次のとおりとする。

1. 学習者が回答する。
2. 回答した内容を画面上に残す。
3. 正誤、理由、必要な状態変化を表示する。
4. フィードバックを表示したままにする。
5. 学習者が「次の問題へ」「次のステップへ」を押して進む。

逐次問題では、現在の問題番号、完了した問題、残りの問題が分かるようにする。ただし、回答直後にタブや問題番号だけを切り替えて、何が起きたか確認できない状態にしない。

「2段階の回答がそろいました」のようにシステム内部の構造を説明する文ではなく、「2問とも正解しました」「この確認は完了です」など、学習者が達成した内容を自然な日本語で伝える。

### 5.7 有効な位置と終了状態

配列、文字列、ポインター、添字を扱う問題では、アクセス可能な位置と、ループ終了を表す位置・状態を混同させない。

- 長さと同じ値の添字など、データへアクセスできない位置を通常の要素位置として表示・選択させない。
- 終了判定のためにポインターがデータ末尾を越える場合は、「次に調べる要素はない」「ここで終了」など、終了状態であることを明示する。
- コード上では有効でも、学習者が範囲外アクセスと解釈し得る状態は、何へアクセスする値か、何を判定する値かを区別して説明する。
- 問題の選択肢に境界状態を含める場合は、アルゴリズムの理解ではなく表記の曖昧さで迷わせていないか確認する。

## 6. グラフィカル表示

### 6.1 使用する基準

次のような状態変化を扱う場合は、グラフィカル表示を優先する。

- 値や要素が移動する
- 探索範囲が変わる
- ポインターや添字が移動する
- 比較対象が変わる
- ループで同じ処理が繰り返される
- 確定、未確定、除外などの領域が変わる

次は文章表示を基本とする。

- 利用場面
- 関連アルゴリズムの紹介
- コースロードマップ
- 用語の短い定義
- 完成コードの役割整理

装飾だけを目的とした図は追加しない。

ビジュアルを作る前に、その画面で学習者が答えるべき問いを1つ定める。最初に見る対象だけを主強調し、既知の範囲、現在の比較、結果、未使用部分を同時に強く見せない。色、枠、矢印、ラベル、添字は「あると親切そうだから」ではなく、その問いへ答えるために必要なものだけを置く。

- 配列や文字列の一部を扱う場合、元の全体を必要な範囲で示し、今回使う部分をその中で強調する。
- 添字は位置の区別が学習目標または判断根拠になる場合だけ表示する。
- 同じ意味を、見出し、吹き出し、枠内説明、凡例で重複させない。
- 既知の一致範囲と今回比較する要素には、コース全体で異なる一貫した状態表現を使う。
- 2つの範囲や要素を比較する場合、対応する位置が縦または横に自然に追える配置にする。
- 説明対象の値がどの表セル、文字、コード行を指すか、視線移動だけで特定できるようにする。

### 6.2 STEP TRACE

状態が連続的に変わるActivityでは、STEP TRACE相当の表示を使用する。

- 前へ
- 次へ
- 再生・停止
- 最初から
- 現在のステップ数
- 現在起きている処理の説明

説明とSTEP TRACEが同じコンセプトを扱う場合は、同じActivity内に配置してよい。

STEP TRACEでは、1回進めたときに起こる意味上の操作を1つに統一する。「次の比較」「候補を短くする」「交換する」など、ボタンを押す前に何が進むか予測できるラベルを使う。単なる1画面の表示に再生UIを付けない。

- 各ステップで固定する情報と変化する情報を決め、途中で進行軸を変えない。
- 説明していない規則を、再生操作によって先に実行させない。
- ステップ番号だけでなく、「何を計算中か」「どの候補を確認中か」など現在状態の意味を示す。
- Activityが変わったときは、再生位置、選択中ステップ、自動再生状態を必ず初期状態へ戻す。
- 前後移動できる場合も、同じステップが常に同じ状態を表すようにする。

## 7. Pythonコードへの接続

### 7.1 完成コードを先に決める

コース設計前に、Course Missionで到達させる標準Pythonコードを1つ決める。

あわせて次を定義する。

- 関数名
- 引数
- 戻り値
- 入出力例
- 前提条件
- 境界条件
- 使用する変数名

### 7.2 コードの分解

完成コードを、アルゴリズムに応じて次のような処理単位へ分解する。

- 入力と状態変数
- 判断条件
- 状態更新
- 繰り返し
- 終了条件
- 戻り値

各処理を学んだ後に、対応するコード断片を説明する。

コース設計票には、各コード断片について次の4段階をどこで扱うか記録する。

| 段階 | 学習者が行うこと |
| --- | --- |
| 説明 | コードなしで処理の目的と判断を理解する |
| 対応 | コード行と画面上の状態変化を結びつける |
| 練習 | 穴埋め、並べ替え、ドラッグ＆ドロップ、誤り修正のいずれかで使う |
| 統合 | 既習断片を組み合わせて標準完成コードへ近づける |

アルゴリズム固有の主要な分岐、状態更新、ループ更新を、説明と対応だけで済ませない。各Missionで理解した単位を短いコード問題にし、最後の基礎Missionでは新しいコードを教えるのではなく、それらを統合する。

### 7.3 概念理解からコードへ移る条件

コードは概念を理解するための最初の説明として使用しない。学習者がコードを見なくても、具体的なデータについて次を判断できる状態になってから、対応するコードを示す。

- 現在どこに注目しているか
- 次に何を判断するか
- 判断後にどの状態が変わるか
- その変化が問題解決のどこにつながるか

一つのコード要素を導入するために、未説明の完成コード全体を先に表示しない。必要なコード断片だけを示し、日本語で理解した役割、画面上の状態、Pythonの変数名を同じ順序で対応づける。

学習者が具体的な処理を理解できていない場合は、コードの説明を増やして先へ進めず、概念説明、可視化、具体例を見直す。

### 7.4 コード、概念、状態変化を対応づける

コードを表示するだけで、アルゴリズムとの対応を学習者に推測させない。コードを説明するActivityでは、少なくとも次の3点を直接対応づける。

1. **コード行**：実際に実行されるPythonコード
2. **処理の役割**：アルゴリズム上で何を担当するか
3. **状態変化**：配列、範囲、ポインター、確定領域などがどう変わるか

例：

| コード行 | 処理の役割 | 画面上の変化 |
| --- | --- | --- |
| `for i in range(n - 1):` | 周回を繰り返す | 周回番号が進み、確定範囲が広がる |
| `for j in range(n - 1 - i):` | 比較位置を左から右へ動かす | 比較中の2要素が右へ移動する |
| `if numbers[j] > numbers[j + 1]:` | 交換が必要か判断する | 比較対象を強調し、交換するかを示す |
| `numbers[j], numbers[j + 1] = ...` | 隣り合う値を交換する | 2つのカードの位置が入れ替わる |

対応を示すときは、次を守る。

- コードと説明を別々に置くだけでなく、同じ色、番号、ラベル、選択状態などで対応箇所を特定できるようにする。
- コード行を選択すると対応する説明と状態が強調されるなど、視線移動だけで関係が分かる表示を優先する。
- ビジュアル内の記号やラベルを孤立させず、どのコード行に対応するか明示する。
- 複数行をまとめて説明する場合も、各行の役割を個別に確認できるようにする。
- コード欄には実行可能なPythonだけを表示し、補足や計算結果はコード欄の外へ出す。

### 7.5 前提知識と学習対象を分ける

コースごとに次を区別する。

- **Pythonの前提知識**：すでに理解しているものとして扱う構文。
- **このコースで学ぶコード要素**：アルゴリズム理解と対応づけて説明するもの。
- **スターターコード**：Course Missionで最初から与え、学習者が変更しない部分。

関数定義などをスターターコードとして与える場合、必ずしもアルゴリズムコース内の採点対象にしなくてよい。

一方、学習者がCourse Missionで自ら記述するアルゴリズム固有のコード要素は、最後の基礎Missionまでに説明する。

### 7.6 コードの一貫性

- 変数名を途中で変更しない。
- 同じ処理に複数の書き方を混在させない。
- まだ説明していないアルゴリズム固有のコードを突然出さない。
- 途中で示したコード断片が、標準完成コードへつながるようにする。
- 最後の基礎Missionでは既習コードを統合する。
- Course Missionで初めて自由入力させる。

## 8. ActivityデータとUIの実装契約

この章は、コース間で同じ形式のActivityを同じUIで表示するための実装規約である。

### 8.1 フィールドの責務

| フィールド | 役割 |
| --- | --- |
| `type` | 回答保存・採点方式。既存のPrisma enumを利用する。 |
| `learningRole` | 説明、練習、確認、コード接続、統合など、教材上の役割を表す。 |
| `rendererKey` | 実際に使用するUIを明示する。 |
| `feedbackPolicy` | 誤答、再回答、正解開示の方針を表す。 |
| `data` | renderer固有の表示・回答データを格納する。 |

新しいActivityでは`content.activityType`と`activityPattern`を使用しない。共通ActivityContentへの変更時に既存データも一括して変換し、旧形式を読み取る互換処理は残さない。

### 8.2 データ例

```ts
content: {
  learningRole: "GUIDED_PRACTICE",
  rendererKey: "ARRAY_REGION_SELECT",
  feedbackPolicy: {
    mode: "RETRY_WITH_HINT",
    revealAfterAttempts: 2,
  },
  data: {
    values: [3, 6, 9, 12, 15, 18, 21],
    target: 18,
    leftIndex: 0,
    rightIndex: 6,
    midIndex: 3,
    correctRegion: "RIGHT",
  },
}
```

`rendererKey`ごとに`data`の型を定義し、Zodなどで実行時にも検証する。

### 8.3 learningRole

標準の`learningRole`は次を基本とする。

- `ORIENTATION`
- `EXPLANATION`
- `GUIDED_PRACTICE`
- `INDEPENDENT_PRACTICE`
- `CODE_MAPPING`
- `SYNTHESIS`
- `MISSION_CHECK`
- `COURSE_EXAM`

### 8.4 rendererKeyと登録制

標準のrenderer例：

- `TEXT`
- `LEARNING_ROADMAP`
- `ARRAY_TRACE`
- `ARRAY_REGION_SELECT`
- `INDEX_SELECT`
- `SINGLE_CHOICE`
- `BLOCK_ORDER`
- `CODE_FILL`
- `CODE_REPAIR`
- `MATCH`
- `CODE_EDITOR`

一覧は固定ではない。新しいrendererが必要な場合は、用途、必要データ、操作方法、既存rendererで代用できない理由を定義し、レジストリへ明示的に登録する。

コース名、`sceneType`のプレフィックス、JSONキーの有無からrendererを推測しない。未登録rendererは開発時エラーにし、無関係な配列や画面をフォールバック表示しない。

### 8.5 共通UI部品

可能な限り次を共通部品として使用する。

- 配列カード
- index表示
- 任意ラベルを表示できるポインター
- 比較中、選択中、有効範囲、除外範囲、確定範囲の状態表示
- コード行表示
- STEP TRACEの操作
- 正解・誤答フィードバック
- コードブロックの並べ替え、穴埋め、修正

`left`、`right`、`mid`を部品名へ固定せず、任意のポインター名を表示できるようにする。

### 8.6 練習rendererの表示フェーズ

採点を伴うrendererは、少なくとも次の表示フェーズを区別する。

- `PROMPT`：回答前。判断に必要な情報と操作対象だけを表示する。
- `FEEDBACK`：回答後。選択結果、正解箇所、状態変化、理由を表示する。

正解データを採点のために`data`へ保持していても、`PROMPT`では正解を示す強調、結果、説明を描画しない。マスコットのセリフも表示フェーズに従う。

閲覧用TRACEと回答付きTRACEで状態データを共有してよい。ただし、閲覧用の完成状態を回答前の練習画面へそのまま表示しない。

### 8.7 操作方法の一貫性

同じ学習課題には、コースやMissionが異なっても同じrendererと操作方法を使用する。

- 同じ選択、範囲指定、位置指定、並べ替え、穴埋め、対応づけで異なる操作方法を混在させない。
- 異なる課題でUIを分ける場合も、カード、コードブロック、ドラッグハンドル、選択状態、削除、フィードバックなどの共通部品を再利用する。
- ドラッグ操作だけに依存せず、クリックやキーボードでも操作できるようにする。
- 押した直後に、何がどこへ移動・配置・削除されたかを視覚的に示す。
- 上下移動ボタンは、並べ替え対象として配置済みのブロックにだけ表示し、「上へ移動」「下へ移動」のラベルまたはツールチップを付ける。
- 移動後はブロックの位置変化が分かるようにし、フォーカスを失わせない。
- 同じ`rendererKey`では、正解確認、リセット、再回答、完了までの操作順を統一する。

コードブロックを扱う課題でも、処理を順番に組み立てる`BLOCK_ORDER`と、処理の役割へ分類する`MATCH`は異なる課題なので別UIでよい。ただし、ブロックの見た目と基本操作は共通化する。

### 8.8 画面幅への対応

ActivityはPC幅とモバイル幅の両方で、情報と操作が欠けないようにする。

- 横並びが収まらない場合は、左右の領域を縦積みに切り替える。
- コード、図、回答欄を含む各子要素が親コンテナを押し広げないようにする。
- 長いコードの横スクロールはコード領域の中だけで行う。
- ページ全体に横スクロールを発生させない。
- 正解確認、リセット、次へなどの主要操作を画面外へ見切れさせない。
- コードや比較表示の一部を切り取って情報を失わせない。
- 横スクロールが必要な領域には、スクロール可能であることが分かる表示を用意する。
- PCでは横並び、狭い画面では縦積みを基本とし、単純な縮小だけで対応しない。

### 8.9 コース間・Mission間で統一する範囲

問題UIはアルゴリズム名やコース名ではなく、学習者に求める回答操作によって決定する。同じ回答操作には、コースやMissionが異なっても同じ`rendererKey`と同じ共通コンポーネントを使用する。

コース間・Mission間で統一するもの：

| 項目 | 統一内容 |
| --- | --- |
| Activityの外枠 | タイトル、要約、説明・ビジュアル、回答、マスコット、フィードバック、下部操作の配置順 |
| 問題の型 | 選択、位置指定、範囲指定、並べ替え、対応づけ、穴埋め、修正などの標準renderer |
| 操作方法 | 選択方法、ドラッグ、クリック、キーボード操作、リセット、回答確認、再回答 |
| 表示状態 | 通常、hover、focus、選択中、正解、誤答、disabledの意味と見た目 |
| フィードバック | 回答前後の切り替え、誤答時のヒント、正解開示、完了までの流れ |
| ビジュアル外枠 | 横幅、余白、枠線、背景、最小高さ、内部要素の基準サイズ |
| 共通部品 | 配列カード、index、ポインター、コード行、コードブロック、TRACE操作 |
| レスポンシブ | 横並びから縦積みへ切り替える基準、内部スクロール、主要操作の表示 |
| データ契約 | `learningRole`、`rendererKey`、`feedbackPolicy`、rendererごとの`data`型 |

コースやActivityごとに変更してよいもの：

| 項目 | 変更可能な内容 |
| --- | --- |
| 教材内容 | タイトル、要約、説明、問題文、マスコットの補足、フィードバック文 |
| 入力データ | 配列の値、探索対象、グラフ、文字列、コード断片、テストデータ |
| 状態ラベル | そのアルゴリズムで必要な対象と役割を表す日本語。コード接続後は、対応づけ済みの`left`、`right`、`mid`、`i`、`j`なども使用できる。 |
| 状態遷移 | 比較、交換、探索範囲の更新、確定、除外など、アルゴリズム固有の変化 |
| 表示する情報 | 学習コンセプトの理解に必要なポインター、範囲、比較対象、コード行 |
| 使用する問題型 | 標準rendererのうち、そのActivityの学習目標に適したもの |
| 問題数・ステップ数 | 学習目標に必要な独立問題数とTRACEの状態数 |

次はコース固有に変更してはいけない。

- 共通rendererのボタン配置、操作順、フィードバックの流れ
- 同じ状態を表す色や枠線の意味
- 共通配列カードやコードブロックの基本サイズと操作方法
- 同じ問題型の回答方法
- 同じrendererの外枠サイズ、余白、レスポンシブ規則
- コース専用の都合による共通コンポーネントの見た目の上書き

同じMission内だけでなく、別Missionの定着問題、Mission最後の確認、別コースの同じ問題型にもこの規則を適用する。例えば、説明時と異なるデータを使う確認問題でも、確認する行為が同じならrendererを変更せず、propsまたは`data`だけを変更する。

### 8.10 標準問題型の選択

問題型は、アルゴリズムの見た目ではなく「学習者に何を回答させるか」で選ぶ。

| 学習者に求めること | 使用する標準renderer | グラフィカル部分の扱い |
| --- | --- | --- |
| 判断結果や分岐を1つ選ぶ | `SINGLE_CHOICE` | 配列やグラフは考えるための読み取り専用表示 |
| 配列上の1位置を選ぶ | `INDEX_SELECT` | index付き配列自体を回答対象にする |
| 連続した範囲を指定する | `ARRAY_REGION_SELECT` | 範囲を選ぶこと自体が学習目標の場合だけ使う |
| 処理やコードを順番に並べる | `BLOCK_ORDER` | ブロックの順序だけを回答対象にする |
| コードと役割などを対応づける | `MATCH` | 同じ共通カードと配置操作を使う |
| 既習コードの空欄を補う | `CODE_FILL` | 標準コード表示と共通の穴埋め操作を使う |
| 誤ったコードを修正する | `CODE_REPAIR` | 誤りの選択・置換方法を全コースで統一する |
| 状態変化を順に観察する | `ARRAY_TRACE`など | 原則として採点せず、標準TRACE操作を使う |

選択基準は次のとおりとする。

1. まず「学習者に何を判断・指定・並べ替えさせるか」を動詞で定義する。
2. 既存の標準問題型で表現できる場合は、そのrendererを使う。
3. グラフィカル部分が考えるための補助なら、そこへ独自のクリック操作を追加せず、標準の回答UIを別に表示する。
4. グラフィカル部分を操作すること自体が学習コンセプトの場合だけ、`INDEX_SELECT`や`ARRAY_REGION_SELECT`などの直接操作を使う。
5. 学習者が説明なしに操作方法を理解できない場合は、専用UIを追加する前に標準問題型へ置き換えられないか見直す。

二分探索の場合：

- 「次に探すのは左側・発見・右側のどれか」を答える問題は、読み取り専用の配列表示と`SINGLE_CHOICE`を使う。
- 「次の`mid`はどのindexか」を答える問題は`INDEX_SELECT`を使う。
- 「更新後に残る連続範囲そのもの」を指定させる場合だけ`ARRAY_REGION_SELECT`を使う。

### 8.11 専用rendererを追加できる条件

コースごとに分かりやすそうな操作UIを個別実装してはならない。既存rendererで学習目標を表現できない場合だけ、新しい共通問題型として追加を検討する。

追加時は次を満たす。

- 既存rendererで代用できない理由を説明できる。
- 回答操作自体が学習コンセプトと直接結びついている。
- 特定のアルゴリズム名やMission番号をrenderer名へ含めない。
- 別のコースでも利用できる汎用的な`data`型と操作契約を定義する。
- `PROMPT`、`FEEDBACK`、誤答、再回答、キーボード、モバイルの各状態を定義する。
- 共通のActivity外枠、ビジュアル外枠、フィードバック、操作部品を再利用する。
- レジストリ、スキーマ、自動検証、代表テストへ追加する。

コース固有の可視化が必要な場合も、可視化は標準問題rendererの`visualization`領域へpropsまたは`data`として渡す。可視化コンポーネントに独自の採点、回答確認、再回答処理を持たせない。

### 8.12 ビジュアル領域のサイズ統一

バブルソート、二分探索などで内容が異なっても、同じ役割のビジュアルは共通の`VisualFrame`を使用する。

- 横幅、内側余白、枠線、背景、角丸は共通トークンで管理する。
- 同じrendererでは配列カード、index、ポインター、コード行の基準サイズを統一する。
- 高さは内容に応じて伸縮させ、コースごとの固定値を持たせない。
- 情報が少ないActivityで不必要な巨大な空白を作らない。
- 情報量が多いActivityでも、外枠を横へ拡張してページ幅を超えない。
- コース固有コンポーネントから外枠の幅、余白、基準カードサイズを上書きしない。

表示内容まで同じ大きさへ無理に固定するのではなく、外枠と共通部品の基準を統一し、内容量に応じて縦方向へ伸縮させる。

### 8.13 回答領域の共通表現

練習Activityでは、回答する領域を背景色だけで区別しない。全コース・全問題型で共通の`AnswerPanel`相当の外枠を使用し、次によって回答領域だと分かるようにする。

- 「問題」「あなたの回答」などの見出し
- Activity本文との間隔と境界
- 共通の枠線、余白、配置
- 回答候補と「答えを確認する」の一貫した位置
- キーボードフォーカスと選択状態

回答前の背景は白または薄いグレーなどの中立色を基本とする。黄色はヒントや注意、緑は正解後、赤は誤答後など、意味のあるフィードバックへ限定し、回答領域全体を常時黄色にしない。色だけで状態を伝えず、見出し、アイコン、文章、枠線を併用する。

### 8.14 学習者向けラベルと文言

画面上のラベルは、システム内部の状態名や操作名ではなく、学習者が理解すべき対象と教材上の役割を示す。

次のような抽象語を、対象を示さず単独で使用しない。

- 選択
- 比較
- 現在位置
- 対象
- 候補
- 処理中

「いま注目している文字」「次に比べる文字」「これから調べる範囲」のように、何を示し、何のために存在するかが分かる表現にする。ラベルは原則として「対象＋役割」または「対象＋現在の動作」で構成する。

内部データで`selected`、`comparison`、`pattern`、`length`などを使用していても、それを未導入のまま学習者向けラベルへ表示しない。コード接続後に英語変数を表示する場合も、対応する日本語の役割を同じ画面で確認できるようにする。

文言は次を満たす。

- 初めて読んでも、何を見て何をすればよいか分かる。
- 実装、データ構造、ガイドライン上の都合を説明しない。
- 不自然な直訳や、システム内部の段階数・回答状態をそのまま読み上げない。
- 同じ意味にはコース間で同じ日本語を使用する。
- マスコットのセリフだけを読まないと操作や前提が分からない構成にしない。

## 9. Course・Mission・シード作成ルール

新規コースでは、`docs/course-designs/<course-id>.md`のコース設計票を先に作成し、その内容からMission・Activity・標準コード・テストを導出する。設計票とシードデータの対象学習者、前提知識、用語の導入順、到達状態が矛盾してはならない。

### 9.1 命名とID

- Course名は原則としてアルゴリズム名とする。
- Course説明には、解決する問題、学習方法、最終到達点を含める。
- Course説明には、ガイドラインや内部実装を守っていることではなく、学習者が得られる価値を書く。
- IDは表示順ではなく、内容を表す安定した名前にする。
- 並び順は`order`で管理し、1から連番にする。

### 9.2 時間とEXP

- Missionの`estimatedMinutes`は、Activityごとの想定時間を積み上げて決める。
- 同程度の時間と難易度のMissionでは、同程度のEXPを付与する。
- 現在の暫定基準は、基礎Missionを1分あたり10 EXPとして10単位に丸め、Course Missionを150 EXPとする。
- 報酬方針を変更する場合は、特定コースだけでなく全コースを同時に見直す。
- ロードマップ表示、完了画面、実際の付与値を一致させる。

### 9.3 画像とpreview

- `goalImg`は作成段階では内容の分かる仮URLでよい。
- コース作成時に画像生成を行わない。
- 本番公開時にplaceholderを残す場合は警告する。
- `preview`が不要な場合は`preview: null`を省略できる型にする。
- `preview`がない場合、空の表示枠を出さない。

## 10. シード同期

- Course、Mission、Activityを共通処理でupsertする。
- シードから消えたActivityを全コース共通で検出する。
- 共通ActivityContentへの変更時に旧形式のActivityを残さない。
- 教材内容、Activity構成、ID、orderを変更した場合は、開発・テスト用のMission進捗、Activity進捗、回答ログをリセットしてからシードを入れ直す。
- 旧ActivityContentや旧回答形式を読み取る互換処理は作らない。
- シード同期はトランザクション内で行う。
- バブルソートの未使用`generatedMissions`のような旧定義を残さず、Mission定義を1系統にする。
- 実験開始時点で使用するコードとシードデータを確定し、実験中はCourse、Mission、Activityの内容とIDを変更しない。
- 実験で使用した状態を再現できるよう、実験開始時点のGitコミットとシードデータを記録する。

## 11. 検証

### 11.1 自動検証

シード投入前に、機械的に判定できる項目を検証する。

- `rendererKey`が登録されている
- `type`と`rendererKey`の組み合わせが正しい
- `content`がrendererごとのスキーマに一致する
- MissionとActivityの`order`が連番である
- IDが重複していない
- 新規コースに対応するコース設計票が存在する
- 説明用Activityに採点データが含まれていない
- 最後の基礎Missionに自由入力エディターがない
- Course Mission以外に自由入力エディターがない
- Course Missionにテスト、ヒント、完了条件がある
- STEP TRACEのステップ数を独立問題数として数えていない
- placeholder画像が本番公開対象に残っている場合は警告する
- 練習rendererが回答前と回答後の表示状態を持つ
- 代表的な練習rendererで、回答前に正解用の強調や説明が表示されない
- 主要なActivityコンテナでページ全体の横スクロールが発生しない
- renderer名にコース名やMission番号を含む新規定義がない
- 同じ標準問題型がコースごとの別コンポーネントへ重複実装されていない
- コース固有コンポーネントが共通rendererの回答処理やフィードバック処理を独自実装していない

独立問題が4問を超える場合と、Course Missionのテスト数が5〜7件の範囲外の場合は、即時エラーではなく警告とする。

### 11.2 教材レビュー

意味理解が必要な項目は、自動判定だけに依存せずレビューする。

- 1 Activity 1コンセプトになっているか
- 外部教材を3資料以上確認し、正確性確認用と初学者向け説明用を区別して記録しているか
- 参考資料の説明をコピーせず、対象学習者に合わせて採用・変更・不採用の理由を設計票に残しているか
- MissionとActivityの順序が、実装コードの順ではなく、学習者の問いと概念依存関係から決まっているか
- コース設計票の対象学習者、提供価値、到達状態と教材内容が一致しているか
- プログラミング経験年数だけで、用語、構文、専門知識を知っていると判断していないか
- 学習者が外部検索やAIへの質問をしなくても、コース内の情報だけで理解できるか
- 教材の難しさが、未定義の専門用語、英語、記号、図の読み方、独自UIの操作から生じていないか
- 説明と図を不必要に別Activityへ分けていないか
- 説明と採点問題が混在していないか
- Activityを直接開いても、使用するデータ、変数、現在の状態、求める操作が分かるか
- 前Activityの内容を覚えていないと解けない問題になっていないか
- 後のActivityで使用する概念、用語、表記が、依存関係どおりに導入・確認されているか
- 一つのActivityに、専門用語、略語、英語変数、新しい図、新しい操作、新しい構文が重なっていないか
- 新しい用語が、具体例、役割の理解、正式名称、コード上の名前の順で導入されているか
- 正式名称を一度定義しただけで、理解済みとして扱っていないか
- 問題がアルゴリズム固有の理解を確認しているか
- 対象学習者に対して簡単すぎる計算問題になっていないか
- 回答前の図、強調、説明、マスコットのセリフが正解を示していないか
- 回答後に初めて正解箇所、状態変化、理由が示されているか
- STEP TRACEの1シナリオを複数問題と誤認していないか
- Mission最後の確認が既習規則の応用になっているか
- Pythonコードが不自然に突然現れていないか
- コードを示す前に、コードなしで現在の状態と次の変化を判断できるようになっているか
- コード行、アルゴリズム上の役割、画面上の状態変化が対応づけられているか
- コード欄に無効なPythonや説明用の等式が混ざっていないか
- スターターコードと学習者が書くコードを区別しているか
- 最後の基礎Missionで新しい構文を追加していないか
- 同じ課題形式で異なる操作UIを使用していないか
- 問題型がアルゴリズム名ではなく、学習者に求める回答操作から選ばれているか
- 考えるための補助ビジュアルへ、不要な独自操作を追加していないか
- 直接操作させる場合、その操作自体が学習コンセプトになっているか
- 同じ問題型のActivityが、コースやMissionをまたいで同じrendererを使用しているか
- 変更点が問題文、データ、ラベル、状態遷移など、変更可能な範囲に収まっているか
- 同じrendererの外枠、余白、カードサイズ、状態表現が一致しているか
- 画面ラベルが「選択」「比較」などの抽象語だけでなく、対象と役割を示しているか
- 未導入の専門用語、略語、英語変数がタイトル、要約、図、問題、マスコットへ出ていないか
- 学習者向け文章に、ガイドライン、直接表示、自由入力の配置など、教材制作側の都合が書かれていないか
- 回答後に自動で次の問題へ移らず、フィードバックと状態変化を確認してから進めるか
- 有効な添字、終了位置、範囲外の状態が区別され、表記の曖昧さで迷わせていないか
- 回答領域が背景色だけに依存せず、共通の見出し、枠、配置で認識できるか
- 黄色、緑、赤などの色が、ヒント、正解、誤答といった共通の意味で使われているか
- 学習ロードマップが画面幅に応じて折り返しまたは縦積みされ、内容が見切れていないか
- ブロック移動や配置の結果が操作直後に理解できるか

- 結果だけが突然示されず、その結果を導く候補、判断基準、必要な過程を学習者が追えるか
- 各Missionの最初で、前Missionの到達状態、未解決場面、今回学ぶ理由が分かるか
- 扱う対象や表現がMission間で変わる場合、独立した橋渡しActivityがあるか
- 各Activityについて、「既知の事実→残る問い→次に調べる理由」を一文で説明できるか

- STEP TRACEの1回の操作が1つの意味上の変化に対応し、Activity変更時に再生位置が初期化されるか
- マスコットが疑問への長い回答ではなく、そのActivityで理解してほしい要点を短くまとめているか
- アルゴリズム固有の主要コード断片を、それを学ぶMission内で実際に操作・回答する問題があるか

### 11.3 初見学習レビュー

自動検証と作成者レビューだけで完成と判断しない。可能な限り、そのアルゴリズムを事前に理解していない評価者が、教材画面だけを使って最初から学習する。

評価者は、シードデータ、正解データ、標準完成コードを先に読まずに進める。正解できたかだけでなく、次を記録する。

- Activity名
- 何を理解する画面だと思ったか
- 問題を解くために不足していた前提
- 図や文章から正解が先に分かってしまった箇所
- 操作後に何が起きたか分からなかった箇所
- コード行と処理の意味を対応づけられなかった箇所
- 画面の見切れや読みにくさ
- 理解が止まったが、既知知識で補えた箇所
- 初めて見た用語、略語、英語変数、記号のうち、意味を理解できなかったもの
- 画面ラベルから、何を示しているのか分からなかった箇所
- 現在のデータ、注目箇所、次の変化を頭の中でイメージできなくなった箇所
- 回答後の変化やフィードバックを確認する前に画面が進んだ箇所
- Missionが変わったとき、前Missionとの関係や今回学ぶ理由が分からなかった箇所
- 最終結果は表示されたが、候補の範囲や選ばれた過程が分からなかった箇所

見つかった問題は次のどこを修正すべきか分類する。

1. コース固有の説明・問題
2. 本ガイドラインの不足
3. 共通renderer・UI部品
4. コース生成用プロンプト

既知のアルゴリズムでは説明不足を評価者自身の知識で補う可能性があるため、新規コース作成フローでは少なくとも1度、評価者が知らないアルゴリズムで初見学習レビューを行う。

## 12. 新規コースを作る順序

「〜コースを作って」と依頼されたCodexは、原則として次の順序で調査、設計、実装、検証する。

1. 本ガイドライン、学習体験コンセプト、既存renderer、既存コースの実装契約を確認する。
2. 標準完成コードを作り、代表例、主要分岐、境界条件、計算量を技術的に検証する。
3. 外部教材を3資料以上調査し、正確性、説明順、具体例、可視化、練習方法を比較する。
4. 対象学習者に合わせて、概念依存関係、つまずき、採用する説明順と理由をコース設計票へ記録する。
5. 各Missionの開始状態、未解決場面、到達状態、次へ残す課題を決める。
6. 各Activityの「既知の事実→問い→根拠→結論→確認方法」を設計し、理解の飛躍を監査する。
7. コード学習対応表を作り、各主要コード断片を説明・対応・練習・統合する場所を決める。
8. 各ビジュアルの問い、主強調、補助表示、非表示情報と、STEP TRACEの1操作を定義する。
9. Mission・Activity構成を実装し、専用rendererが必要な場合も既存の共通部品と状態表現を優先する。
10. シード検証、型チェック、関連テストを行う。教材内容やIDを変更した場合は、開発・テスト用進捗をリセットして再シードする。
11. 実際のシードデータから全Activityを順に開き、説明、図、問題、フィードバック、再生位置の初期化を確認する。
12. PC幅とモバイル幅で、視線誘導、情報量、見切れ、横スクロール、操作結果を確認する。
13. 教材レビューと可能な限り初見学習レビューを行い、説明不足を吹き出しやラベルの追加だけで補わず、必要なら学習順から修正する。
14. 修正後、別データでも規則を適用できることと、Course Missionを既習コードだけで実装できることを再確認する。

調査、設計、実装を一度で終わらせる必要はない。ただし、実画面で理解の飛躍が見つかった場合は、表示要素を増やす前に、問い、前提、説明順、Activity分割が正しいかへ戻る。

## 13. 新規コースの完成条件

新しいアルゴリズムコースは、次を満たした時点で完成とする。

- コース設計票が作成され、対象学習者、提供価値、前提知識、用語の導入順、到達状態が明記されている。
- 外部教材を3資料以上比較し、資料、確認日、採用・変更・不採用の理由がコース設計票に記録されている。
- 各MissionとActivityの順番を、直前までの理解と次に生じる問いから説明できる。
- 大学生のアルゴリズム初学者が、専門書や外部検索を利用しなくても学べる内容になっている。
- 強い学習意欲、専門用語への慣れ、前画面の暗記を前提にしていない。
- Mission 1だけで、コースの目的と学習内容を判断できる。
- 中間Missionが処理単位で分かれている。
- 説明、必要な可視化、練習、Python接続が自然につながっている。
- 各Activityを直接開いても、その画面で必要なデータ、変数、状態、操作が分かる。
- 学習者が、現在のデータ、注目箇所、次の状態変化、問題解決までのつながりをイメージできる。
- 「次に比べる」「戻る」「省略する」「再利用する」の対象と根拠が、元データと既知の状態から追える。
- 専門用語、略語、英語変数は、具体例と日本語の役割を理解した後に導入されている。
- 練習Activityの回答前に、正解箇所、正解後の状態、理由が表示されていない。
- 独立問題が逐次表示され、STEP TRACEのステップと混同されていない。
- Pythonの前提知識、スターターコード、学習対象が区別されている。
- Pythonコードの各行が、処理の役割と画面上の状態変化に対応している。
- アルゴリズム固有の主要コード断片を、各Mission内の穴埋め、並べ替え、対応づけ、誤り修正などで練習している。
- 最後の基礎Missionでは既習コードだけを統合している。
- Course Missionだけで自由入力を行う。
- 共通rendererと共通UI部品を優先している。
- 同じ学習課題の操作方法がコース間で統一され、操作結果が直後に分かる。
- 問題型がコースやMissionではなく、学習者に求める回答操作から選ばれている。
- 同じ問題型が、コース間・Mission間で同じrendererと共通コンポーネントを使用している。
- コースごとの差が、教材内容、入力データ、状態ラベル、状態遷移などの変更可能な範囲に収まっている。
- 補助ビジュアルには不要な回答操作がなく、直接操作を使う場合は操作自体が学習コンセプトになっている。
- 同じ役割のビジュアルが共通外枠と基準サイズを使用している。
- 回答領域は共通の外枠・見出し・配置で示され、背景色だけに依存していない。
- 画面ラベルは対象と役割を示し、未導入の内部状態名や英語変数をそのまま表示していない。
- 回答後の結果と状態変化を、学習者が確認してから次へ進める。
- STEP TRACEは1操作1変化になっており、Activityを移動すると再生位置が初期化される。
- シード検証、型チェック、必要なテストが成功している。
- 実画面でPC幅とモバイル幅を確認し、ページ全体の横スクロールや内容の見切れがない。
- 可能な限り、アルゴリズムを事前に知らない評価者による初見学習レビューを通過している。
