# アルゴリズムコース作成ガイドライン

## 1. 目的

本ガイドラインは、Engineer Questで新しいアルゴリズムコースを作成するときに、コース間で次の品質を統一するための基準である。

- 学習の流れ
- Mission・Activityの粒度
- 説明、可視化、問題、Pythonコードのつなぎ方
- Activity画面の情報構成と操作方法
- Course Missionの到達水準
- シードデータとレンダラーの実装方法

新規コースは本ガイドラインに従って設計・実装する。既存コースを修正するときは、本ガイドラインとは別に移行チェックリストを作成する。

## 2. 対象と基本方針

### 2.1 対象学習者

- 主な対象は中学生から大学生までとする。
- アルゴリズムを初めて学ぶ人が、処理の意味とPythonコードの対応を段階的に理解できる内容にする。
- コースごとに、前提とするPython知識を明記する。

### 2.2 コース全体の原則

- 1 Activityでは1つの学習コンセプトを扱う。
- Activityを細かく分けること自体を目的にしない。
- 説明、図、マスコットの補足が同じコンセプトを扱う場合は、1つのActivity内に配置してよい。
- 採点を伴う練習は、説明Activityと分ける。
- 学習者の操作は、アルゴリズムの理解を進める場合だけ求める。
- 基本的な大小比較や単純計算だけを、独立した問題として出さない。
- 各Activityは、前のActivityの表示内容を覚えていなくても、その画面内の情報から目的と前提を理解できるようにする。
- 練習Activityでは、回答前に正解となる位置、範囲、状態、結果、理由を表示しない。
- 新しい処理を理解した後、対応するPythonコードへ接続する。
- Pythonコードは、コード行、アルゴリズム上の役割、画面上の状態変化を対応づけて説明する。
- 同じ目的の操作には同じUIを使用し、画面幅が変わっても情報や操作が欠けないようにする。
- 最後の基礎Missionでは既習要素を統合し、Course Missionで自由実装する。

## 3. 標準のコース学習フロー

Mission数やActivity数を固定するのではなく、次の学習段階を共通化する。

### 3.1 Mission 1：コースを知る

Mission 1は、学習者がコースを受講するか判断するためのMissionとする。操作問題やPythonコードは置かない。

標準構成は次の4 Activityとする。

1. このアルゴリズムが解決する問題
2. 使われる場面
3. 関連するアルゴリズムと、このコースで扱う範囲
4. このコースで学ぶこと

原則として文章表示を使用する。目的の理解に必要な場合だけ簡単な図を使用し、アルゴリズムの詳細な動作や段階再生はMission 2以降で扱う。

利用場面や関連アルゴリズムの紹介では、受講判断に不要な知識を増やさない。名称と違いを簡潔に示し、このコースで何を学ぶかを明確にする。

### 3.2 中間の基礎Mission：概念を積み上げる

1つのMissionでは、関連する1つの処理単位を扱う。

基本的な学習順序は次のとおりとする。

1. 新しい概念や状態変化を説明する
2. 必要に応じて図や段階再生で動きを確認する
3. 学習者が判断・操作する
4. 対応するPythonコードを説明する
5. 必要に応じてコードの短い練習をする
6. 別データで理解を確認する

これは学習上の順序であり、各項目を必ず別Activityにするという意味ではない。

- 説明と図が同じコンセプトを扱う場合は、1つの説明Activityにまとめる。
- 図を見るだけのActivityを機械的に追加しない。
- 採点を伴う判断・操作・コード練習は、説明Activityから分ける。
- Pythonコードが既習構文による直接的な表現であれば、概念説明の最後に短く示してよい。
- 新しいPython構文や複数行の処理を導入する場合は、独立したコード接続Activityにする。
- 不要な段階は省略してよい。

### 3.3 最後の基礎Mission：既習コードを統合する

最後の基礎Missionでは、新しいアルゴリズム概念や新しいPython構文を増やさない。これまでに学んだ処理とコードを統合する。

必要に応じて次のActivityを配置する。

- 処理とコードの対応確認
- コードブロックの並べ替え
- コード穴埋め
- 誤ったコードの修正
- 完成コードの役割説明

すべてを必須にはしない。アルゴリズムの理解確認に必要な形式を選択する。

このMissionでは自由入力式のPythonエディターを使用しない。タイトルも「実装しよう」ではなく、「コードを組み立てよう」「コードを完成させよう」など、既習要素の統合だと分かる表現にする。

### 3.4 Course Mission：自分で実装する

自由入力式のPythonエディターはCourse Missionだけで使用する。

Course Missionは次を備える。

- 関数名、引数、戻り値の明確な仕様
- 必要最小限のスターターコード
- 基本ケース、主要な分岐、境界ケースを含むテスト
- 未通過テストの表示
- 概念単位の段階的ヒント
- 全必須テスト通過による完了判定

テストケースは5〜7件程度を目安とする。ただし、件数よりも必要なケースを網羅することを優先し、件数だけでエラーにはしない。

## 4. Activityの設計

### 4.1 1 Activity 1コンセプト

1 Activityには、原則として次のうち新しいものを1つだけ入れる。

- 新しい用語
- 新しい状態
- 新しい判断規則
- 新しい状態更新
- 新しいPythonコード要素
- 既習内容を統合する1つの課題

同じ規則に属する対になる分岐は、1つのコンセプトとして扱ってよい。

例：

- 探す値が中央より小さい場合と大きい場合
- 発見時と未発見時の終了
- 交換する場合と交換しない場合

ただし、各分岐に別の新しい構文や複雑な処理が含まれる場合は分割を検討する。

### 4.2 Activity画面の情報構成

Activityは、実際の画面に合わせて次の要素で構成する。

1. **タイトル**：このActivityで理解・実行することを短く示す。
2. **要約・指示**：学習者が何に注目するかを1〜2文で示す。
3. **説明**：新しいコンセプトを簡潔に説明する。
4. **グラフィカル部分**：状態や変化の理解に必要な場合だけ表示する。
5. **操作・回答部分**：練習Activityでのみ表示する。
6. **マスコットのセリフ**：注目点、考え方、次の一歩を補足する。
7. **フィードバック**：回答後に結果、理由、次の行動を示す。

マスコットのセリフは本文を繰り返さず、学習者が迷いやすい点を補足する。

### 4.3 Activity単体での理解

Activityは順番に学ぶことを前提とするが、画面を直接開いた場合や、時間を空けて再開した場合でも、そのActivityで必要な情報が分かるようにする。

- 使用する配列、探索対象、変数、現在の状態を画面内に示す。
- 前Activityで定義した変数を使う場合も、必要な定義または短い再掲を行う。
- 「前のActivityで説明したから」という理由だけで、問題を解くために必要な情報を省略しない。
- 既習内容を長く再説明せず、「この画面で使う前提」として必要最小限に示す。
- タイトル、要約、表示データ、操作対象の間で、異なる配列や変数名を混在させない。

例えば`numbers`と`n`を使うActivityでは、必要に応じて次のように有効なPythonコードとして再掲する。

```python
numbers = [6, 3, 5, 2]
n = len(numbers)
```

`n = len(numbers) = 4`のように、説明上の等式をPythonコード欄へ混在させない。値の説明はコード欄の外で「この例では`n`は4」と示す。

### 4.4 説明Activityと練習Activity

- 説明Activityには採点問題を入れない。
- 前へ・次へ・再生など、理解のための閲覧操作は説明Activityに含めてよい。
- 採点を伴う選択、並べ替え、穴埋めは練習Activityとして分ける。
- 知識定着のために複数問を解かせる場合は、説明Activityと練習Activityを分ける。

### 4.5 Activity設計時に明確にする項目

Activityを実装する前に、少なくとも次を明確にする。

- このActivityで新しく扱う1コンセプト
- 学習者がすでに知っている前提
- この画面内に再掲する必要があるデータ、変数、状態
- 学習者に見せる説明または求める操作
- 使用する標準問題型と、その問題型を選ぶ理由
- グラフィカル部分が「考えるための補助」か「回答を入力する操作対象」か
- 練習の場合、回答前に見せる情報と回答後に見せる情報
- 正解によって確認したい理解
- Pythonへ接続する場合、対応するコード行、処理の役割、状態変化

これらを説明できないActivityは、目的が曖昧か、複数コンセプトが混在している可能性があるため再設計する。

## 5. 問題作成ルール

### 5.1 問題で確認する内容

問題では、アルゴリズム固有の理解を確認する。

適切な例：

- 現在の状態から次に調べる範囲を選ぶ
- 次に比較する要素を選ぶ
- どの状態更新が必要か判断する
- 処理とPythonコードを対応させる
- 既習コードを正しい順番に並べる

避ける例：

- 単純な大小比較だけを答えさせる
- 中学生以上なら容易な四則演算だけを答えさせる
- 説明文をそのまま選び直すだけの問題
- アルゴリズムの理解に影響しない操作

### 5.2 複数問と逐次表示

- 同じ判断を反復する場合は、1問ずつ逐次表示する。
- 独立した反復問題は1 Activityあたり2〜4問程度を目安とする。
- 5問以上の独立問題が必要な場合はActivityの分割を検討する。
- すべての問題を縦に並べて一括表示しない。

ここでいう問題数は、異なる入力や異なる状況を使う独立した設問数を指す。

1つのアルゴリズム実行を段階的に追うSTEP TRACEのステップ数は問題数に含めない。1つの配列を発見または終了まで追う課題は、必要なステップ数が5以上でも1 Activityとしてよい。

### 5.3 Mission最後の確認

- 必要なMissionでは、最後に別データを使った確認を置く。
- 説明と数値だけを入れ替えた完全な模倣ではなく、同じ規則を別の状態へ適用させる。
- Mission内ですでに十分な転移課題がある場合、確認Activityを機械的に追加しない。

### 5.4 回答前に正解を見せない

練習Activityは、回答前の`PROMPT`状態と、回答後の`FEEDBACK`状態を明確に分ける。

回答前に表示してよいもの：

- 問題を考えるために必要な入力データ
- 現在の状態
- 既習の規則や必要最小限の前提
- 学習者が選択・操作できる候補

回答前に表示しないもの：

- 正解となる要素、位置、範囲だけを強調する枠や色
- 正解後の配列や更新済みの状態
- 「交換する」「右側を探す」など、そのまま答えになる説明
- 正解のコードブロック配置や対応関係
- 正解である理由や結果を確定的に示すマスコットのセリフ

回答後は、選択結果に応じて正解箇所、状態変化、理由を表示してよい。

説明Activityでは完成した動きを見せてよいが、その表示をそのまま採点問題の上部へ再利用し、答えを先に見せない。閲覧用の表示状態と練習用の出題状態は、同じデータを利用する場合でも表示フェーズを分ける。

### 5.5 誤答と再回答

標準方針は「誤答時に考え方のヒントを示し、再回答させる」とする。

- 1回目の誤答：正解を開示せず、注目点を示す。
- 2回目の誤答：より具体的なヒントを示し、必要に応じて正解と理由を開示する。
- 正解時：正解である理由と、次の概念へのつながりを示す。

正解開示の詳細は共通`feedbackPolicy`で管理する。Activity固有の例外を作る場合は、その教育上の理由をコメントまたは仕様へ残す。

## 6. グラフィカル表示

### 6.1 使用する基準

次のような状態変化を扱う場合は、グラフィカル表示を優先する。

- 値や要素が移動する
- 探索範囲が変わる
- ポインターや添字が移動する
- 比較対象が変わる
- ループで同じ処理が繰り返される
- 確定、未確定、除外などの領域が変わる

次は文章表示を基本とする。

- 利用場面
- 関連アルゴリズムの紹介
- コースロードマップ
- 用語の短い定義
- 完成コードの役割整理

装飾だけを目的とした図は追加しない。

### 6.2 STEP TRACE

状態が連続的に変わるActivityでは、STEP TRACE相当の表示を使用する。

- 前へ
- 次へ
- 再生・停止
- 最初から
- 現在のステップ数
- 現在起きている処理の説明

説明とSTEP TRACEが同じコンセプトを扱う場合は、同じActivity内に配置してよい。

## 7. Pythonコードへの接続

### 7.1 完成コードを先に決める

コース設計前に、Course Missionで到達させる標準Pythonコードを1つ決める。

あわせて次を定義する。

- 関数名
- 引数
- 戻り値
- 入出力例
- 前提条件
- 境界条件
- 使用する変数名

### 7.2 コードの分解

完成コードを、アルゴリズムに応じて次のような処理単位へ分解する。

- 入力と状態変数
- 判断条件
- 状態更新
- 繰り返し
- 終了条件
- 戻り値

各処理を学んだ後に、対応するコード断片を説明する。

### 7.3 コード、概念、状態変化を対応づける

コードを表示するだけで、アルゴリズムとの対応を学習者に推測させない。コードを説明するActivityでは、少なくとも次の3点を直接対応づける。

1. **コード行**：実際に実行されるPythonコード
2. **処理の役割**：アルゴリズム上で何を担当するか
3. **状態変化**：配列、範囲、ポインター、確定領域などがどう変わるか

例：

| コード行 | 処理の役割 | 画面上の変化 |
| --- | --- | --- |
| `for i in range(n - 1):` | 周回を繰り返す | 周回番号が進み、確定範囲が広がる |
| `for j in range(n - 1 - i):` | 比較位置を左から右へ動かす | 比較中の2要素が右へ移動する |
| `if numbers[j] > numbers[j + 1]:` | 交換が必要か判断する | 比較対象を強調し、交換するかを示す |
| `numbers[j], numbers[j + 1] = ...` | 隣り合う値を交換する | 2つのカードの位置が入れ替わる |

対応を示すときは、次を守る。

- コードと説明を別々に置くだけでなく、同じ色、番号、ラベル、選択状態などで対応箇所を特定できるようにする。
- コード行を選択すると対応する説明と状態が強調されるなど、視線移動だけで関係が分かる表示を優先する。
- ビジュアル内の記号やラベルを孤立させず、どのコード行に対応するか明示する。
- 複数行をまとめて説明する場合も、各行の役割を個別に確認できるようにする。
- コード欄には実行可能なPythonだけを表示し、補足や計算結果はコード欄の外へ出す。

### 7.4 前提知識と学習対象を分ける

コースごとに次を区別する。

- **Pythonの前提知識**：すでに理解しているものとして扱う構文。
- **このコースで学ぶコード要素**：アルゴリズム理解と対応づけて説明するもの。
- **スターターコード**：Course Missionで最初から与え、学習者が変更しない部分。

関数定義などをスターターコードとして与える場合、必ずしもアルゴリズムコース内の採点対象にしなくてよい。

一方、学習者がCourse Missionで自ら記述するアルゴリズム固有のコード要素は、最後の基礎Missionまでに説明する。

### 7.5 コードの一貫性

- 変数名を途中で変更しない。
- 同じ処理に複数の書き方を混在させない。
- まだ説明していないアルゴリズム固有のコードを突然出さない。
- 途中で示したコード断片が、標準完成コードへつながるようにする。
- 最後の基礎Missionでは既習コードを統合する。
- Course Missionで初めて自由入力させる。

## 8. ActivityデータとUIの実装契約

この章は、コース間で同じ形式のActivityを同じUIで表示するための実装規約である。

### 8.1 フィールドの責務

| フィールド | 役割 |
| --- | --- |
| `type` | 回答保存・採点方式。既存のPrisma enumを利用する。 |
| `learningRole` | 説明、練習、確認、コード接続、統合など、教材上の役割を表す。 |
| `rendererKey` | 実際に使用するUIを明示する。 |
| `feedbackPolicy` | 誤答、再回答、正解開示の方針を表す。 |
| `data` | renderer固有の表示・回答データを格納する。 |

新しいActivityでは`content.activityType`と`activityPattern`を使用しない。共通ActivityContentへの変更時に既存データも一括して変換し、旧形式を読み取る互換処理は残さない。

### 8.2 データ例

```ts
content: {
  learningRole: "GUIDED_PRACTICE",
  rendererKey: "ARRAY_REGION_SELECT",
  feedbackPolicy: {
    mode: "RETRY_WITH_HINT",
    revealAfterAttempts: 2,
  },
  data: {
    values: [3, 6, 9, 12, 15, 18, 21],
    target: 18,
    leftIndex: 0,
    rightIndex: 6,
    midIndex: 3,
    correctRegion: "RIGHT",
  },
}
```

`rendererKey`ごとに`data`の型を定義し、Zodなどで実行時にも検証する。

### 8.3 learningRole

標準の`learningRole`は次を基本とする。

- `ORIENTATION`
- `EXPLANATION`
- `GUIDED_PRACTICE`
- `INDEPENDENT_PRACTICE`
- `CODE_MAPPING`
- `SYNTHESIS`
- `MISSION_CHECK`
- `COURSE_EXAM`

### 8.4 rendererKeyと登録制

標準のrenderer例：

- `TEXT`
- `LEARNING_ROADMAP`
- `ARRAY_TRACE`
- `ARRAY_REGION_SELECT`
- `INDEX_SELECT`
- `SINGLE_CHOICE`
- `BLOCK_ORDER`
- `CODE_FILL`
- `CODE_REPAIR`
- `MATCH`
- `CODE_EDITOR`

一覧は固定ではない。新しいrendererが必要な場合は、用途、必要データ、操作方法、既存rendererで代用できない理由を定義し、レジストリへ明示的に登録する。

コース名、`sceneType`のプレフィックス、JSONキーの有無からrendererを推測しない。未登録rendererは開発時エラーにし、無関係な配列や画面をフォールバック表示しない。

### 8.5 共通UI部品

可能な限り次を共通部品として使用する。

- 配列カード
- index表示
- 任意ラベルを表示できるポインター
- 比較中、選択中、有効範囲、除外範囲、確定範囲の状態表示
- コード行表示
- STEP TRACEの操作
- 正解・誤答フィードバック
- コードブロックの並べ替え、穴埋め、修正

`left`、`right`、`mid`を部品名へ固定せず、任意のポインター名を表示できるようにする。

### 8.6 練習rendererの表示フェーズ

採点を伴うrendererは、少なくとも次の表示フェーズを区別する。

- `PROMPT`：回答前。判断に必要な情報と操作対象だけを表示する。
- `FEEDBACK`：回答後。選択結果、正解箇所、状態変化、理由を表示する。

正解データを採点のために`data`へ保持していても、`PROMPT`では正解を示す強調、結果、説明を描画しない。マスコットのセリフも表示フェーズに従う。

閲覧用TRACEと回答付きTRACEで状態データを共有してよい。ただし、閲覧用の完成状態を回答前の練習画面へそのまま表示しない。

### 8.7 操作方法の一貫性

同じ学習課題には、コースやMissionが異なっても同じrendererと操作方法を使用する。

- 同じ選択、範囲指定、位置指定、並べ替え、穴埋め、対応づけで異なる操作方法を混在させない。
- 異なる課題でUIを分ける場合も、カード、コードブロック、ドラッグハンドル、選択状態、削除、フィードバックなどの共通部品を再利用する。
- ドラッグ操作だけに依存せず、クリックやキーボードでも操作できるようにする。
- 押した直後に、何がどこへ移動・配置・削除されたかを視覚的に示す。
- 上下移動ボタンは、並べ替え対象として配置済みのブロックにだけ表示し、「上へ移動」「下へ移動」のラベルまたはツールチップを付ける。
- 移動後はブロックの位置変化が分かるようにし、フォーカスを失わせない。
- 同じ`rendererKey`では、正解確認、リセット、再回答、完了までの操作順を統一する。

コードブロックを扱う課題でも、処理を順番に組み立てる`BLOCK_ORDER`と、処理の役割へ分類する`MATCH`は異なる課題なので別UIでよい。ただし、ブロックの見た目と基本操作は共通化する。

### 8.8 画面幅への対応

ActivityはPC幅とモバイル幅の両方で、情報と操作が欠けないようにする。

- 横並びが収まらない場合は、左右の領域を縦積みに切り替える。
- コード、図、回答欄を含む各子要素が親コンテナを押し広げないようにする。
- 長いコードの横スクロールはコード領域の中だけで行う。
- ページ全体に横スクロールを発生させない。
- 正解確認、リセット、次へなどの主要操作を画面外へ見切れさせない。
- コードや比較表示の一部を切り取って情報を失わせない。
- 横スクロールが必要な領域には、スクロール可能であることが分かる表示を用意する。
- PCでは横並び、狭い画面では縦積みを基本とし、単純な縮小だけで対応しない。

### 8.9 コース間・Mission間で統一する範囲

問題UIはアルゴリズム名やコース名ではなく、学習者に求める回答操作によって決定する。同じ回答操作には、コースやMissionが異なっても同じ`rendererKey`と同じ共通コンポーネントを使用する。

コース間・Mission間で統一するもの：

| 項目 | 統一内容 |
| --- | --- |
| Activityの外枠 | タイトル、要約、説明・ビジュアル、回答、マスコット、フィードバック、下部操作の配置順 |
| 問題の型 | 選択、位置指定、範囲指定、並べ替え、対応づけ、穴埋め、修正などの標準renderer |
| 操作方法 | 選択方法、ドラッグ、クリック、キーボード操作、リセット、回答確認、再回答 |
| 表示状態 | 通常、hover、focus、選択中、正解、誤答、disabledの意味と見た目 |
| フィードバック | 回答前後の切り替え、誤答時のヒント、正解開示、完了までの流れ |
| ビジュアル外枠 | 横幅、余白、枠線、背景、最小高さ、内部要素の基準サイズ |
| 共通部品 | 配列カード、index、ポインター、コード行、コードブロック、TRACE操作 |
| レスポンシブ | 横並びから縦積みへ切り替える基準、内部スクロール、主要操作の表示 |
| データ契約 | `learningRole`、`rendererKey`、`feedbackPolicy`、rendererごとの`data`型 |

コースやActivityごとに変更してよいもの：

| 項目 | 変更可能な内容 |
| --- | --- |
| 教材内容 | タイトル、要約、説明、問題文、マスコットの補足、フィードバック文 |
| 入力データ | 配列の値、探索対象、グラフ、文字列、コード断片、テストデータ |
| 状態ラベル | `left`、`right`、`mid`、`i`、`j`など、そのアルゴリズムで必要な名称 |
| 状態遷移 | 比較、交換、探索範囲の更新、確定、除外など、アルゴリズム固有の変化 |
| 表示する情報 | 学習コンセプトの理解に必要なポインター、範囲、比較対象、コード行 |
| 使用する問題型 | 標準rendererのうち、そのActivityの学習目標に適したもの |
| 問題数・ステップ数 | 学習目標に必要な独立問題数とTRACEの状態数 |

次はコース固有に変更してはいけない。

- 共通rendererのボタン配置、操作順、フィードバックの流れ
- 同じ状態を表す色や枠線の意味
- 共通配列カードやコードブロックの基本サイズと操作方法
- 同じ問題型の回答方法
- 同じrendererの外枠サイズ、余白、レスポンシブ規則
- コース専用の都合による共通コンポーネントの見た目の上書き

同じMission内だけでなく、別Missionの定着問題、Mission最後の確認、別コースの同じ問題型にもこの規則を適用する。例えば、説明時と異なるデータを使う確認問題でも、確認する行為が同じならrendererを変更せず、propsまたは`data`だけを変更する。

### 8.10 標準問題型の選択

問題型は、アルゴリズムの見た目ではなく「学習者に何を回答させるか」で選ぶ。

| 学習者に求めること | 使用する標準renderer | グラフィカル部分の扱い |
| --- | --- | --- |
| 判断結果や分岐を1つ選ぶ | `SINGLE_CHOICE` | 配列やグラフは考えるための読み取り専用表示 |
| 配列上の1位置を選ぶ | `INDEX_SELECT` | index付き配列自体を回答対象にする |
| 連続した範囲を指定する | `ARRAY_REGION_SELECT` | 範囲を選ぶこと自体が学習目標の場合だけ使う |
| 処理やコードを順番に並べる | `BLOCK_ORDER` | ブロックの順序だけを回答対象にする |
| コードと役割などを対応づける | `MATCH` | 同じ共通カードと配置操作を使う |
| 既習コードの空欄を補う | `CODE_FILL` | 標準コード表示と共通の穴埋め操作を使う |
| 誤ったコードを修正する | `CODE_REPAIR` | 誤りの選択・置換方法を全コースで統一する |
| 状態変化を順に観察する | `ARRAY_TRACE`など | 原則として採点せず、標準TRACE操作を使う |

選択基準は次のとおりとする。

1. まず「学習者に何を判断・指定・並べ替えさせるか」を動詞で定義する。
2. 既存の標準問題型で表現できる場合は、そのrendererを使う。
3. グラフィカル部分が考えるための補助なら、そこへ独自のクリック操作を追加せず、標準の回答UIを別に表示する。
4. グラフィカル部分を操作すること自体が学習コンセプトの場合だけ、`INDEX_SELECT`や`ARRAY_REGION_SELECT`などの直接操作を使う。
5. 学習者が説明なしに操作方法を理解できない場合は、専用UIを追加する前に標準問題型へ置き換えられないか見直す。

二分探索の場合：

- 「次に探すのは左側・発見・右側のどれか」を答える問題は、読み取り専用の配列表示と`SINGLE_CHOICE`を使う。
- 「次の`mid`はどのindexか」を答える問題は`INDEX_SELECT`を使う。
- 「更新後に残る連続範囲そのもの」を指定させる場合だけ`ARRAY_REGION_SELECT`を使う。

### 8.11 専用rendererを追加できる条件

コースごとに分かりやすそうな操作UIを個別実装してはならない。既存rendererで学習目標を表現できない場合だけ、新しい共通問題型として追加を検討する。

追加時は次を満たす。

- 既存rendererで代用できない理由を説明できる。
- 回答操作自体が学習コンセプトと直接結びついている。
- 特定のアルゴリズム名やMission番号をrenderer名へ含めない。
- 別のコースでも利用できる汎用的な`data`型と操作契約を定義する。
- `PROMPT`、`FEEDBACK`、誤答、再回答、キーボード、モバイルの各状態を定義する。
- 共通のActivity外枠、ビジュアル外枠、フィードバック、操作部品を再利用する。
- レジストリ、スキーマ、自動検証、代表テストへ追加する。

コース固有の可視化が必要な場合も、可視化は標準問題rendererの`visualization`領域へpropsまたは`data`として渡す。可視化コンポーネントに独自の採点、回答確認、再回答処理を持たせない。

### 8.12 ビジュアル領域のサイズ統一

バブルソート、二分探索などで内容が異なっても、同じ役割のビジュアルは共通の`VisualFrame`を使用する。

- 横幅、内側余白、枠線、背景、角丸は共通トークンで管理する。
- 同じrendererでは配列カード、index、ポインター、コード行の基準サイズを統一する。
- 高さは内容に応じて伸縮させ、コースごとの固定値を持たせない。
- 情報が少ないActivityで不必要な巨大な空白を作らない。
- 情報量が多いActivityでも、外枠を横へ拡張してページ幅を超えない。
- コース固有コンポーネントから外枠の幅、余白、基準カードサイズを上書きしない。

表示内容まで同じ大きさへ無理に固定するのではなく、外枠と共通部品の基準を統一し、内容量に応じて縦方向へ伸縮させる。

## 9. Course・Mission・シード作成ルール

### 9.1 命名とID

- Course名は原則としてアルゴリズム名とする。
- Course説明には、解決する問題、学習方法、最終到達点を含める。
- IDは表示順ではなく、内容を表す安定した名前にする。
- 並び順は`order`で管理し、1から連番にする。

### 9.2 時間とEXP

- Missionの`estimatedMinutes`は、Activityごとの想定時間を積み上げて決める。
- 同程度の時間と難易度のMissionでは、同程度のEXPを付与する。
- 現在の暫定基準は、基礎Missionを1分あたり10 EXPとして10単位に丸め、Course Missionを150 EXPとする。
- 報酬方針を変更する場合は、特定コースだけでなく全コースを同時に見直す。
- ロードマップ表示、完了画面、実際の付与値を一致させる。

### 9.3 画像とpreview

- `goalImg`は作成段階では内容の分かる仮URLでよい。
- コース作成時に画像生成を行わない。
- 本番公開時にplaceholderを残す場合は警告する。
- `preview`が不要な場合は`preview: null`を省略できる型にする。
- `preview`がない場合、空の表示枠を出さない。

## 10. シード同期

- Course、Mission、Activityを共通処理でupsertする。
- シードから消えたActivityを全コース共通で検出する。
- 共通ActivityContentへの変更時に旧形式のActivityを残さない。
- 教材内容、Activity構成、ID、orderを変更した場合は、開発・テスト用のMission進捗、Activity進捗、回答ログをリセットしてからシードを入れ直す。
- 旧ActivityContentや旧回答形式を読み取る互換処理は作らない。
- シード同期はトランザクション内で行う。
- バブルソートの未使用`generatedMissions`のような旧定義を残さず、Mission定義を1系統にする。
- 実験開始時点で使用するコードとシードデータを確定し、実験中はCourse、Mission、Activityの内容とIDを変更しない。
- 実験で使用した状態を再現できるよう、実験開始時点のGitコミットとシードデータを記録する。

## 11. 検証

### 11.1 自動検証

シード投入前に、機械的に判定できる項目を検証する。

- `rendererKey`が登録されている
- `type`と`rendererKey`の組み合わせが正しい
- `content`がrendererごとのスキーマに一致する
- MissionとActivityの`order`が連番である
- IDが重複していない
- 説明用Activityに採点データが含まれていない
- 最後の基礎Missionに自由入力エディターがない
- Course Mission以外に自由入力エディターがない
- Course Missionにテスト、ヒント、完了条件がある
- STEP TRACEのステップ数を独立問題数として数えていない
- placeholder画像が本番公開対象に残っている場合は警告する
- 練習rendererが回答前と回答後の表示状態を持つ
- 代表的な練習rendererで、回答前に正解用の強調や説明が表示されない
- 主要なActivityコンテナでページ全体の横スクロールが発生しない
- renderer名にコース名やMission番号を含む新規定義がない
- 同じ標準問題型がコースごとの別コンポーネントへ重複実装されていない
- コース固有コンポーネントが共通rendererの回答処理やフィードバック処理を独自実装していない

独立問題が4問を超える場合と、Course Missionのテスト数が5〜7件の範囲外の場合は、即時エラーではなく警告とする。

### 11.2 教材レビュー

意味理解が必要な項目は、自動判定だけに依存せずレビューする。

- 1 Activity 1コンセプトになっているか
- 説明と図を不必要に別Activityへ分けていないか
- 説明と採点問題が混在していないか
- Activityを直接開いても、使用するデータ、変数、現在の状態、求める操作が分かるか
- 前Activityの内容を覚えていないと解けない問題になっていないか
- 問題がアルゴリズム固有の理解を確認しているか
- 対象年齢に対して簡単すぎる計算問題になっていないか
- 回答前の図、強調、説明、マスコットのセリフが正解を示していないか
- 回答後に初めて正解箇所、状態変化、理由が示されているか
- STEP TRACEの1シナリオを複数問題と誤認していないか
- Mission最後の確認が既習規則の応用になっているか
- Pythonコードが不自然に突然現れていないか
- コード行、アルゴリズム上の役割、画面上の状態変化が対応づけられているか
- コード欄に無効なPythonや説明用の等式が混ざっていないか
- スターターコードと学習者が書くコードを区別しているか
- 最後の基礎Missionで新しい構文を追加していないか
- 同じ課題形式で異なる操作UIを使用していないか
- 問題型がアルゴリズム名ではなく、学習者に求める回答操作から選ばれているか
- 考えるための補助ビジュアルへ、不要な独自操作を追加していないか
- 直接操作させる場合、その操作自体が学習コンセプトになっているか
- 同じ問題型のActivityが、コースやMissionをまたいで同じrendererを使用しているか
- 変更点が問題文、データ、ラベル、状態遷移など、変更可能な範囲に収まっているか
- 同じrendererの外枠、余白、カードサイズ、状態表現が一致しているか
- ブロック移動や配置の結果が操作直後に理解できるか
- PC幅とモバイル幅のどちらでも、内容、回答欄、主要操作が見切れていないか
- 横スクロールがコードなど必要な領域内に限定されているか
- Course Missionのテストが基本、主要分岐、境界条件をカバーしているか

### 11.3 初見学習レビュー

自動検証と作成者レビューだけで完成と判断しない。可能な限り、そのアルゴリズムを事前に理解していない評価者が、教材画面だけを使って最初から学習する。

評価者は、シードデータ、正解データ、標準完成コードを先に読まずに進める。正解できたかだけでなく、次を記録する。

- Activity名
- 何を理解する画面だと思ったか
- 問題を解くために不足していた前提
- 図や文章から正解が先に分かってしまった箇所
- 操作後に何が起きたか分からなかった箇所
- コード行と処理の意味を対応づけられなかった箇所
- 画面の見切れや読みにくさ
- 理解が止まったが、既知知識で補えた箇所

見つかった問題は次のどこを修正すべきか分類する。

1. コース固有の説明・問題
2. 本ガイドラインの不足
3. 共通renderer・UI部品
4. コース生成用プロンプト

既知のアルゴリズムでは説明不足を評価者自身の知識で補う可能性があるため、新規コース作成フローでは少なくとも1度、評価者が知らないアルゴリズムで初見学習レビューを行う。

## 12. 実装と検証の順序

1. 本ガイドラインを確定する。
2. ロードマップの表示、共通ActivityContent、rendererレジストリ、危険なフォールバックを整備する。
3. 標準問題型を確定し、配列、ポインター、範囲表示、STEP TRACE、コード問題、フィードバックの共通部品を作る。
4. 練習rendererへ`PROMPT`と`FEEDBACK`の表示フェーズを導入し、回答の先出しを防ぐ。
5. Activity単体で必要な前提を表示できる共通のコンテキスト表現を整える。
6. コード行、処理の役割、状態変化を対応表示できる共通部品を整える。
7. コードブロックを含む同種操作のUIを統一し、コース固有の重複rendererを共通問題型へ置き換え、操作結果が分かるフィードバックを実装する。
8. PC幅とモバイル幅に対応し、ページ全体の横スクロールと内容の見切れを解消する。
9. バブルソートと二分探索の全Activityを、本ガイドラインの教材レビュー項目で調査・修正する。個別修正より共通renderer・共通部品の修正を優先する。
10. 二分探索の各Activityについて、1コンセプト、前提、回答前後の情報、Python接続、次の学習段階を整理し、問題生成の基準が機能しているか確認する。
11. 内容確定後に時間とEXPを再計算する。
12. シード同期を共通化し、開発・テスト用の進捗と回答ログをリセットして再シードする。
13. 自動検証、代表的なrendererのE2Eテスト、PC・モバイルの表示テストを追加する。
14. 本ガイドラインだけでコースを作成できる新規アルゴリズムコース作成用プロンプトを作る。
15. 評価者が知らないアルゴリズムを、アルゴリズム名、カテゴリ、本ガイドラインを主な入力として1プロンプトで作成する。
16. 評価者が教材だけで初見学習レビューを行い、問題をコース固有、ガイドライン、共通UI、生成プロンプトのいずれかへ分類する。
17. 必要な修正をガイドラインと共通基盤へ反映し、別のアルゴリズムでも再現できるか確認する。

## 13. 新規コースの完成条件

新しいアルゴリズムコースは、次を満たした時点で完成とする。

- Mission 1だけで、コースの目的と学習内容を判断できる。
- 中間Missionが処理単位で分かれている。
- 説明、必要な可視化、練習、Python接続が自然につながっている。
- 各Activityを直接開いても、その画面で必要なデータ、変数、状態、操作が分かる。
- 練習Activityの回答前に、正解箇所、正解後の状態、理由が表示されていない。
- 独立問題が逐次表示され、STEP TRACEのステップと混同されていない。
- Pythonの前提知識、スターターコード、学習対象が区別されている。
- Pythonコードの各行が、処理の役割と画面上の状態変化に対応している。
- 最後の基礎Missionでは既習コードだけを統合している。
- Course Missionだけで自由入力を行う。
- 共通rendererと共通UI部品を優先している。
- 同じ学習課題の操作方法がコース間で統一され、操作結果が直後に分かる。
- 問題型がコースやMissionではなく、学習者に求める回答操作から選ばれている。
- 同じ問題型が、コース間・Mission間で同じrendererと共通コンポーネントを使用している。
- コースごとの差が、教材内容、入力データ、状態ラベル、状態遷移などの変更可能な範囲に収まっている。
- 補助ビジュアルには不要な回答操作がなく、直接操作を使う場合は操作自体が学習コンセプトになっている。
- 同じ役割のビジュアルが共通外枠と基準サイズを使用している。
- シード検証、型チェック、必要なテストが成功している。
- 実画面でPC幅とモバイル幅を確認し、ページ全体の横スクロールや内容の見切れがない。
- 可能な限り、アルゴリズムを事前に知らない評価者による初見学習レビューを通過している。
