# 新学習フロー教材指針 v2（実装要約）

- 目的: 7フェーズで構成する新しいアルゴリズム学習単元を、既存 Engineer Quest 内へ実装するための要約と境界条件を示す。
- 適用範囲: 新規に作る7フェーズ単元と、その入口、学習プレイヤー、リザルト、関連ログ。
- 最終確認日: 2026-11-04
- 正本: [アルゴリズム学習教材・汎用設計ガイドライン（全フェーズ確定版）](https://docs.google.com/document/d/15LvKG7clbeb2j5P556jy7DfeqKc_H4ryiOkBlnTi_p4/edit)
- 位置づけ: 学習設計の全文は Google Drive の正本を正とする。この文書は、実装者がリポジトリ内だけで作業を始められるよう、確定事項と実装上の含意を抽出したものである。正本とこの要約が食い違う場合は正本を優先し、この文書を修正する。

## 1. 従来フローとの関係

新しい単元では、従来の「Mission を細分化し、Activity ごとに1概念を扱う」構造を使わない。1つのアルゴリズムを、図と文章が同期した連続ステップで理解し、確認、コード接続、応用、自力実装までを1単元として扱う。

従来フローは現行アプリで動作しているため、直ちに削除しない。

- `course-creation-guidelines.md` は従来フローの保守・修正にだけ使う。
- `visual-data-format.md` は従来 Activity の `MissionActivity.content` 形式にだけ使う。
- `docs/course-designs/` の各設計票は、現行コースの設計記録として保持する。
- 新フロー側のデータ形式、画面、進捗モデルは、この文書と正本に基づいて新規に設計する。従来の Mission / Activity へ無理に押し込まない。

## 2. 共通制約

- 1場面には、中央の濃い黒字による1文キャプションだけを置く。タイトル、補足説明、操作マニュアルを重ねない。
- 対象データ、内部状態、層・段階を1つのキャンバスへ集約し、視線移動を最小化する。
- 操作はプレイヤーバーに統一する。進捗タブや巨大な次へボタンなどのメタ UI を混ぜない。
- 専門用語は、視覚的に対象を理解したタイミングでラベルとして導入する。初出は「日常語（専門用語）」、2回目以降は専門用語を基本とする。
- 同一アルゴリズム内では用語を統一し、概念、日常語、専門用語、初出コマの対応表に従う。
- ビジュアル表現は全フェーズで統一するか、具体表現から抽象表現へ切り替える場合は対応関係を明示するコマを挟み、フェーズ境界で表現が突然変わらないようにする。
- 教材内の色は意味を持って使う。既存アプリの画面都合で、教材内の状態色を別の意味へ流用しない。

## 3. フェーズ構成

| フェーズ | 名称 | 役割と確定事項 |
| --- | --- | --- |
| 1 | 動機づけ | 問い、候補比較、実用性、入口を提示する。フェーズ2へは自動遷移せず、学習者がボタンを押して進む「意思確認の区切り」とする。コマ数は目安であり、内容に応じて増減してよい。 |
| 2 | アルゴリズム説明 | 同じデータの実行過程を、図と1文キャプションが100%同期した連続ステップで見せる。1コマの変化は最小単位に絞る。 |
| 3 | 理解度確認（概念） | コードなし。フェーズ2と同じ図・データで、取り出しと直後の変化を問う連動2問。正解するまでその場で再挑戦し、復習モーダルは任意とする。 |
| 4 | コード接続 | フェーズ2と同じデータ・同じ実行過程を、図とコードを重ねて再生する。実行行と変化する図の要素を同色で同時ハイライトし、非実行行は減光する。制御行もステップとして通過させ、スカラー変数はコード領域下部に表示する。変数、代入、インデント程度の最小限のリテラシーを前提とする。 |
| 5 | コード基本確認 | フェーズ4と同じコードで、状態変化行と条件判定行を中心に1〜2問の独立した穴埋め選択を行う。選択肢はすべて構文的に成立するものにし、インデントやコロン等の細部は出題しない。 |
| 6 | 応用・総括 | 3〜5問。異なるデータでの追跡、学んだ規則から推論できる境界ケース、Parsons 問題を組み合わせる。Parsons 問題はインデント済みの行の順序だけを問い、妨害行を入れない。初回回答で診断結果を表示するソフトゲートとし、弱点は論点タグ単位で示す。復習先はフェーズ4の基本例とする。 |
| 7 | 自力実装＆デバッグ | 骨組み付きテンプレートへコアロジックを自由記述する。補助チップは全員に提供し、トークンだけを扱う。テストは表示用と判定用を分け、判定用の入出力は公開しない。3段階ヒントを用意し、差分は閲覧のみで貼り付け不可とする。ヒント利用をログに残す。全テスト通過で完了とする。自分のコードの実行を同じキャンバスで再現する視覚的デバッグは、想定解法に沿うコードから段階的に対応する。 |

## 4. フェーズ遷移

遷移は次の3種類を使い分ける。

1. 意思確認の区切り: フェーズ1から2。学習者がボタンを押して進む。
2. シームレス接続: フェーズ2から3、フェーズ4から5。結果画面を挟まず、理解が新しいうちに確認へ入る。
3. リザルトによる区切り: フェーズ3、5、6、7の後。到達状況と次フェーズの予告を示す。

学習者は、原則として現在のフェーズから過去のフェーズへ自由に戻って復習できる。この導線は教材コンテンツではなく、アプリ側の UI / システム設計として実装する。

## 5. 実装時に必要な記録

少なくとも次の出来事を、参加者と単元に結び付けて記録できる設計にする。

- 各フェーズとステップの表示
- 確認問題の初回回答、再挑戦、正誤、論点タグ
- フェーズ4でのステップ移動と復習モーダルの利用
- フェーズ6の初回スコアと論点別結果
- フェーズ7の実行、テスト結果、ヒントのレベルと利用回数、視覚的デバッグの利用
- フェーズ完了、単元完了、リザルト表示と次アクションの選択

これは将来のフィードバック提示と着手率計測の前提である。画面が表示されていない推薦や生成だけの推薦を、提示済みとして数えない。

## 6. 未確定として扱うもの

次は、この要約だけを根拠に実装を決めない。

- 新フロー全体の UI 改革指針とデザイントークンの最終形
- 新フロー用データモデルのテーブル設計
- AI による教材生成パイプラインの入出力スキーマ
- 新フローへのフィードバック層の接続位置と提示方法
- 視覚的デバッグでトレース可能なコード範囲の最終仕様

これらは個別の設計文書または PR で決定し、決定後にこの文書と `docs/README.md` を更新する。
