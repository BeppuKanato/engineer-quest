## 1. アルゴリズムの確定事項

穴掘り法（スタックによる反復版）:

1. 盤面は一辺が奇数の正方形グリッド。最初は全マスが壁。
2. 座標が両方とも奇数のマスが「部屋」。開始マスは (1, 1) で、最初に掘っておく。
3. 現在マスから2マス先が盤内（外周を除く）かつ、まだ掘っていない（壁のままの）部屋である方向を候補とする。候補の提示順は 上・右・下・左 で固定。
4. 候補から1つ選び（実際のゲームでは乱数）、間の壁マスと2マス先の部屋を掘って進む。進んだ部屋をスタックに積む。
5. 候補がなければ、スタックから1つ戻る（バックトラック）。候補のある部屋まで戻って掘り直す。
6. 全ての部屋を掘り終えたら完成。出来上がりは完全迷路（輪がなく、全ての部屋がつながっている）になる。

### 棒倒し法との対比軸

- 棒倒し法は「通路の床に壁を立てていく」作り方、穴掘り法は「壁の塊から通路を掘っていく」作り方で、発想が逆。
- ただし完成した迷路はどちらも「輪がなく、全部がつながっている」完全迷路になる。言い換えると、どちらも部屋と通路のつながりが木（全域木）になっている。この対比はフェーズ1の導入とフェーズ6の性質問題で使う。
- 完成グリッドの符号化（0=通路、1=壁）は棒倒し法と同じなので、完成盤面の見た目と描画方法は共通化できる。

主教材は 9×9（部屋16、掘削15回）。転移・応用の確認には 7×7（部屋9、掘削8回）を使う。

## 2. 参照コード（契約）

契約ID: `maze-digging-v1`。棒倒し法と同じく、乱数は関数の外（choices）から与える決定論的な中核を実装対象とする。choices は「その時点の候補リストへの番号」の列で、消費する個数は 部屋の数 − 1（= 掘削回数）とちょうど一致する。未掘削かどうかの判定はグリッドの値（壁のまま = 1）で兼ね、訪問済み集合は持たない。

```python
def dig_maze(size, choices):
    grid = [[1] * size for _ in range(size)]
    directions = [(0, -1), (1, 0), (0, 1), (-1, 0)]
    grid[1][1] = 0
    stack = [(1, 1)]
    step = 0
    while stack:
        x, y = stack[-1]
        candidates = []
        for dx, dy in directions:
            nx, ny = x + 2 * dx, y + 2 * dy
            if 1 <= nx < size - 1 and 1 <= ny < size - 1 and grid[ny][nx] == 1:
                candidates.append((nx, ny))
        if candidates:
            nx, ny = candidates[choices[step]]
            step += 1
            grid[(y + ny) // 2][(x + nx) // 2] = 0
            grid[ny][nx] = 0
            stack.append((nx, ny))
        else:
            stack.pop()
    return grid
```

戻り値は grid（0=通路、1=壁の2次元リスト）。符号化は棒倒し法と共通。方向リストの並び（上・右・下・左）が候補の提示順そのもので、choices の意味を決める。

## 3. フェーズ別設計

### フェーズ1 導入

- 動機づけ: 棒倒し法と同じ「コンピュータに迷路を作らせる」必要性から入るが、作り方の逆転を体験させる。壁の塊を見せ、「掘れば迷路になる」発想につなげる（ARCS / 期待価値の型は共通）。用語（穴掘り法）はまだ出さない。
- 場面（7場面、棒倒し法フェーズ1と同型）: ①完成した 9×9 迷路にスタート (1, 1) からゴール (7, 7) までの一本道を示す ②別の完成迷路（7×7）で毎回違う迷路になることを示す ③全部が壁の盤面 ④開始マス (1, 1) を掘る ⑤最初の掘削（右へ2マス） ⑥掘り進めて行き止まりから戻る様子（主教材の最初のバックトラックを圧縮して見せる） ⑦完成＋出口。

### フェーズ2 動きの説明（21ステップ）

構成: 準備2 + 掘削15 + バックトラック3 + 完成1 = 21ステップ（上限25以内）。

1. 全部が壁の 9×9 を用意する。
2. スタートの部屋 (1, 1) を掘る。
3. 〜 掘削15回を §1 の表の順に1回1ステップで見せる（ステップID は `dig-<n>`）。キャプションは「(5, 3) から右へ掘ります」のように現在マス＋方向で一文。
   - バックトラックは発生した3回を各1ステップとして挟む（ステップID は `backtrack-<n>`、掘削6回の後・13回の後・14回の後）。キャプションは「行き止まりです。掘れる部屋があるところまで戻ります」のように、戻る理由と再開マスに触れる。複数マス戻る場合も盤面の現在位置が再開マスへ移る1ステップにまとめる。
4. 完成。「どの部屋からどの部屋へも必ずたどり着ける」ことと「輪がない」ことを示す。

### フェーズ3 動きの確認問題（連結2問）

場面: 主教材の途中（掘削3回目まで、現在マスは (5, 3)、掘られた部屋は (1, 1)・(3, 1)・(3, 3)・(5, 3)）。
- Q1（処理対象の特定）: 「(5, 3) から右へ掘ります。掘られる部屋はどれか」（グリッドをタップ）。正解は部屋 (7, 3)。候補には上 (5, 1)・下 (5, 5) も未掘削で存在するため、与えられた方向を使う必要がある。
- Q2（直後の変化）: 「そのとき通路になる、間の壁マスはどれか」（タップ）。正解は (6, 3)。
- 棒倒し法との違い: 棒倒し法は柱の処理順が固定だったが、穴掘り法は次の行き先が乱数（choices）で決まるため、方向を問題文で与えないと一意に答えられない。よって方向は Q1 の文中で提示する（要判断ポイント6）。

### フェーズ4 動きとコードの対応

フェーズ2と同じトレースを、参照コードの行ハイライトと同期して再生する。対応づけの要点: スタックの一番上が現在マスであること、候補の収集（方向リストのループ＋「盤内かつ壁のまま」の条件）、choices による選択、2マス分の掘削（間の壁と部屋）、候補が空のときの `stack.pop()`（バックトラック行がフェーズ2のバックトラックステップに対応する）。実装時は CPython トレースとフレーム列を照合する（他の単元と同じ手順）。

### フェーズ5 コードの確認問題（独立2問）

- Q1: 2マス先の部屋の座標。`nx, ny = x + □ * dx, y + □ * dy` の □ は 2（選択肢はいずれも文法的に正しい数値）。
- Q2: まだ掘っていない部屋の条件。`grid[ny][nx] == □` の □ は 1（壁のまま = 未掘削）。

### フェーズ6 応用問題（4問）

- Q1（転移・タップ）: 7×7 の途中（掘削5回目まで、現在マス (3, 5)）で、「左へ掘ります。掘られる部屋はどれか」。正解は (1, 5)。
- Q2（転移・選択）: 完成した迷路の性質として正しいものを選ぶ（すべての部屋がつながっている／輪ができていない、等。棒倒し法と同じ観点で、作り方が違っても性質は同じことを問う）。
- Q3（推論可能なエッジケース・選択）: 行き止まりでバックトラックが必要な理由（その部屋からは掘れる先がなく、戻らなければ残りの部屋にたどり着けない）。復習先はフェーズ4の `stack.pop()` に対応するステップ。
- Q4（Parsons）: 参照コードの行を並び替える（インデント提示あり、余分な行なし）。行の順序はすべて意味を持つため、順序自由な行は設けない。

## 4. グリッド描画基盤の再利用

- 描画コンポーネントは棒倒し法の `MazeGridDrawing` と幾何（mazeGridGeometry: viewBox 600×450、9×9 で1マス約48px）をそのまま使う。盤面データは参照コードの生成結果から決定的に作る（手書きの壁リストを持たない方針も棒倒し法と同じ）。
- ただし状態の意味は棒倒し法と逆になる点に注意: 穴掘り法では盤面は「全部壁」から始まり、壁が減っていく。キャンバス状態の使い方は、壁集合 = その時点でまだ壁のマス、processing = 現在マス（部屋なので通路側のマス）、target = 次に掘る部屋（まだ壁のマス）、highlights = 掘ったばかりのマス（間の壁＋部屋）、path = スタックの経路（戻りの説明に使える）、とする。
- 棒倒し法側のバリデータ（validateMazeGridCanvas）は「processing は壁でなければならない」「target は壁であってはならない」という前提で作られているため、そのままでは穴掘り法の状態（processing は通路、target は壁）と矛盾する。描画そのものは共有し、検証は単元側の意味に合わせた検証器を別に持つことを前提に設計する（要判断ポイント8）。
- 状態色はプレイヤートークンに従う: 壁はテキスト色（#111827、棒倒し法と同じ暫定）、現在マスはフォーカス青、掘る予定の部屋は待機ベージュ、掘ったばかりのマスは青い枠。完了した通路は地の色に落ち着く。
- スタート／ゴールの旗はフェーズ1と完成表示でのみ使う（開始マス (1, 1) とゴール (7, 7)）。

## 6. 要判断ポイント

各項目に推奨デフォルトと理由を記す。

1. フェーズ7の契約: 乱数を choices（候補リストへの番号列）として外から与える決定論方式（`dig_maze(size, choices)`）を採るか。
   - 推奨: 採用する。棒倒し法と同型で、テストが完全一致で書け、候補の提示順という規則もコードに残る。実際の乱数選択は「アプリ側が番号を振る」ものとして説明する。
2. 主教材の大きさ: 9×9（部屋16・掘削15回・21ステップ）を本案とするか。
   - 推奨: 採用する。棒倒し法と同じ盤面で完成迷路を対比でき、バックトラック3回を含めてもフェーズ2が21ステップに収まる。7×7 は短いが転移用に回す。
3. 未掘削の判定: 訪問済み集合を持たず、グリッドの値（壁のまま = 1）で兼ねる形を参照コードとするか。
   - 推奨: 採用する。コードが短く、「壁のまま = まだ掘っていない」という対応が学習者にも直観的。集合を持つ案は概念的には明示的だが、グリッドとの二重管理になり行数も増える。
4. 候補の提示順: 上・右・下・左 で固定するか。
   - 推奨: 固定する。choices の意味（何番目か）は提示順に依存するため、決定論には固定が必須。順序そのものは画面の読みの流れに近いこの順を推奨する。
5. フェーズ2のバックトラック表示: 発生した3回を各1ステップにまとめてすべて見せるか。
   - 推奨: すべて見せる。掘削だけでは「戻る」処理（スタックとバックトラック）が学べず、本単元の核心が抜ける。まとめても21ステップに収まる。複数マスの戻りも1ステップに圧縮し、戻る過程の1マスごとの再生はしない。
6. フェーズ3で方向を問題文に与える形にするか。
   - 推奨: 与える。棒倒し法と違い次の行き先は乱数依存で、方向なしでは正解が一意に定まらない。与えた上でも「2マス先の部屋」と「間の壁」を特定する学習は成立する。
7. J3（11×11）の判定: 性質検証ではなく、固定 choices による完全一致とするか。
   - 推奨: 完全一致とする。棒倒し法 J3 の実装時の扱いに合わせる。期待グリッドは参照コードで生成し、完全迷路の性質を満たすことを検証スクリプトで事前確認済みのため、判定としての妥当性は担保できる。
8. 描画基盤の状態検証: 棒倒し法のバリデータ前提（processing = 壁、target = 非壁）が穴掘り法と逆である点への対応。
   - 推奨: 描画コンポーネントと幾何は共有し、検証器は単元ごとに持つ。無理に共通の検証へ寄せると、どちらかの単元の状態表現を不自然に曲げることになる。
9. 用語: 教材名は「穴掘り法」で統一し、奇数座標のマスは教材内で「部屋」と呼ぶか。
   - 推奨: 統一する。「部屋」は掘削の対象を指す言葉として、壁マスとの区別がつきやすい。
