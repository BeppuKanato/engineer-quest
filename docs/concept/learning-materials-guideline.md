# アルゴリズム学習教材・汎用設計ガイドライン（全フェーズ確定版）

> **位置づけ**: 本書は教材指針の全文であり、新学習フローの実装が参照する正本である。要約は [learning-materials-v2.md](learning-materials-v2.md)。編集の正本は Google Drive の文書であり、確定した変更はこのファイルへ再取り込みする（取り込み情報はファイル先頭のコメント参照）。

本書は、任意のアルゴリズム（探索、ソート、グラフ、動的計画法等）を扱うWeb学習教材をAIが生成する際の共通プロダクト制約およびフェーズ1〜7の汎用設計指針である。

## 1. 共通プロダクトUI/UX絶対制約（全アルゴリズム共通）

学習者のワーキングメモリ（脳の処理容量）をアルゴリズムの構造理解だけに100%集中させるためのUI制約。

* **1場面 ＝ 中央の濃い黒字「1文キャプション」のみ**

  * **【根拠：認知的負荷理論（Cognitive Load Theory）】**
  * 大タイトル・小タイトル・サブラベル・操作マニュアル文は全画面から排除する。
  * アニメーションの動的変化と同期して切り替わる1文（濃い黒字 #111827 / 太字）のみに限定し、テキスト解読の認知負荷を最小化する。
* **1キャンバス集約レイアウト**

  * **【根拠：空間的近接の原則（Spatial Contiguity Principle）】**
  * 多重なカード枠や境界線・影を廃止し、1つの統合パネル上に「対象データ（図/配列/グラフ等）」「内部状態（データ構造/変数）」「層・段階」を物理的に近く配置する。
  * 視線移動を「中央の1文 ➔ 中央の図 ➔ 下部のデータ構造」の縦一直線のみに固定し、視線探訪のストレスを削ぎ落とす。
* **無駄なメタ指示・UIノイズの排除**

  * **【根拠：余分な処理の低減（Reducing Extraneous Processing）】**
  * 進捗丸タブ、作業目次、巨大な「次へ」ボタンなどを排除する。
  * コントロールはキャンバス下部の標準的なプレイヤー型バー [◀ ひとつ前] ●-○-○-○ (1/N) [ 次へ ▶ ] に統一する。
* **ジャストインタイム・ラベリング（用語導入原則）**

  * **【根拠：概念優先・事前知識の平滑化】**
  * 「〜とは…である」というテキストでの定義文説明を全廃する。既に視覚的に理解している要素に対し、必要なタイミングで小さなラベル（タグ）を図やコード上に付与する。
  * 初出時は「日常語（専門用語）」の併記とし、2回目以降は「専門用語」のみに移行する（例：「待ち行列（キュー）」➔「キュー」）。
  * 用語の一貫性：同一アルゴリズム内では、同じ概念に対して同じ日常語・専門用語を使い続けること。アルゴリズムごとに用語対応表（概念／日常語／専門用語／初出コマ）を作成し、生成時はそれに従うこと。
  * **ビジュアル表現の統一と橋渡し**
  * 【根拠：具体から抽象への段階的移行 / 表現間の対応付け】
  * フェーズ間で用いるビジュアル表現（図の種類とレイアウト）は、次のいずれかに統一する。
  * ・全フェーズで共通の表現を用いる。
  * ・フェーズ1では具体的な題材（地図・マス目など）を用い、フェーズ2以降で抽象的な表現（グラフなど）に切り替える。この場合は、①両者の対応関係（例: 場所＝ノード、つながり＝辺）を明示するコマを挟むこと、②フェーズ1の締め（入口の提示と名称の付与）はフェーズ2の表現側に置き、フェーズの境界で視覚が切り替わらないようにすること。対応の明示は、具体的な画面のまま各要素に抽象側の名前（ラベル）を付けた中間コマで行う。抽象表現へ切り替えた後は、応用場面（駅など）に移る前に、抽象表現のままで具体側と同じ進み方を一度再演し、同じものだと認識させる。具体表現のレイアウトは、抽象表現における相対的な位置関係（左右・上下）と対応させ、切り替え時に各要素が大きく移動しないようにする。
  * **テーマ切り替え時のクッション**
  * 【根拠：シグナリング（Signaling）/ 変化の明示による認知負荷の低減】
  * 場面のテーマ（表現・話題・課題）が切り替わる境界では、切り替わること自体を1文で知らせるクッションのコマを挟むこと。クッションでは新しい概念の説明や計算を始めず、「話が変わる」ことを認識させるだけに留める。表現と課題が同時に切り替わる場合は、両方の切り替えに触れて予告し、切り替え後の内容は次のコマから始める。
  * **解答要素の明示**
  * 【根拠：アフォーダンス / 操作の発見可能性】
  * 解答として選択できる要素（図の要素・選択肢ボタン等）は、静止状態でも選択可能だと分かる表示にすること。ホバーやフォーカスをしたときだけ手がかりを出す形にしない。何の操作が求められているかも、設問と併せて常時表示し、画面だけから操作が分かる状態にする。

## 2. フェーズ別・設計指標

### フェーズ1：動機づけ導入（Why / 全4〜5コマ程度）

**目的**: 初学者でも直感的に理解できる「目標の問いかけ」と「候補比較・実用性・入口の視覚化」を提示し、主体的学習モードを起動する。

* **1-1. 直感的問いかけによる目的共有（Attention & Goal Alignment）**

  * **【根拠：ARCSモデル「Attention（注意）」 / 課題の主体化】**
  * 専門知識がない段階でも「何を実現したいのか」が理解できる明確な目的意識を提示する。操作を伴わない場面で指示文（「〜しよう」）を使わず、思考を促す疑問文を置く。
  * **1文形式**: 「[対象オブジェクト] は、どうすれば [最適条件（例: 最も効率的/最短/最少）] に [目的達成] できるでしょう？」
  * **ビジュアル**: 初期状態の対象オブジェクトと達成目標を配置（途中の解法経路や処理はまだ可視化せず、目指す状態のみを共有する）。
* **1-2. 候補比較と実用性の提示（Relevance & Utility Value）**

  * **【根拠：ARCSモデル「Relevance（関連性）」 / 期待×価値理論「Utility Value（利用価値）」】**
  * 非効率な手順と効率的な手順を順に見せることで「最適なアルゴリズムを用いる必要性」を可視化し、それが身近な技術で使われていることを提示する。
  * **1文形式**:

    * コマA: 「たとえば、[解法案1] では [手数/時間] がかかります。」
    * コマB: 「こちらの [解法案2] なら、[より少ない手数/時間] で達成できます。」
    * コマC: 「[アルゴリズムが解決する具体的な課題] など、身近なテクノロジーで使われている仕組みです。」
    * ビジュアル: コマA・Bでは、2つの解法案の違いが一目で比べられるよう、同じ対象データの上で手順または結果を順にハイライト表示する。コマCでは、実用場面を表す具体的な対象（地図やネットワーク図など）を表示し、文だけの説明で終わらせない。
  * **留意事項**: そのアルゴリズムが保証する数学的・論理的条件（例: 辺の重みが均一な場合の最短経路、比較回数の削減等）に適合する正確な実用例を提示する。
* **1-3. 成功期待の芽生えと入口の可視化（Confidence & Expectancy）**

  * **【根拠：ARCSモデル「Confidence（自信）」 / 期待×価値理論「Expectancy（成功期待）」】**
  * アルゴリズム全体が成立する理由まで1コマで完全理解させようとせず、まず「処理の第一歩（探訪の入口）」が追えそうだという安心感を与える。
  * **1文形式**: 「仕組みはシンプルで、[アルゴリズムの最小処理単位（例: 初期状態から1ステップで到達できる範囲）] から順に調べるだけです。」
  * **ビジュアル**: 初期状態から「最初に処理対象となる要素（第一波/比較対象）」のみがハイライトまたは色づく1コマを見せる。
* **1-4. シームレスな本編接続（Flow State）**

  * 導入で選択クイズや画面遷移を挟まず、高い意欲と問いを保持したまま本編（連続アニメーション）へ直結させる。

### フェーズ2：アルゴリズムの流れの理解（Visual Execution / 連続コマアニメーション）

**目的**: 余計な割り込みなしで、連続アニメーションを通じてアルゴリズムの基本挙動（状態変化とデータ構造の連動）をストレスなく脳内にトレースさせる。

* **2-1. 100%同期したライブ実況キャプション**

  * **【根拠：デュアルコーディング理論 / 時間的・空間的近接の原則】**
  * そのコマで画面上の要素やデータ構造に起きている動的変化を直接言語化した「実況文」にする。
  * **1文形式（動作型ごとの例）：取り出し・追加型「[操作対象] から [次の処理単位] を取り出し、[データ構造/状態変化] に追加/更新します。」／比較・交換型「[要素A] と [要素B] を比べて、[条件に合う方] を [位置] へ移します。」／値の更新型「[対象] の値を、[根拠となる値] から求めて [新しい値] に更新します。」※骨格は例示であり、そのコマの変化を直接言語化することを優先する。**
* **2-2. 最小変化量の原則（Segmenting Effect）**

  * **【根拠：マルチメディア学習のセグメンテーション効果】**
  * 1コマ（ステップ）で伝える変化は「要素を1つ取り出した」「1つの比較を行った」「1つの状態を更新した」など、1つの最小事実のみに絞る。
* **2-3. 本質的データ構造と状態の一体可視化**

  * **【根拠：メンタルモデルの構築】**
  * アルゴリズムを支える主要なデータ構造（配列、キュー、スタック、木構造、スコア表等）と、メインビジュアル（グラフ、マップ、要素列等）の状態変化を常に連動してハイライト表示する。
* **2-4. 介入（問い）の限定設置（Guided Discovery）**

  * アニメーションの途中で流れを中断するクイズは挟まない。
  * 問いを置く場合は、可視化の一連の流れを見終わった「最後」にのみ、直感的な到達感確認として配置する。

### フェーズ3：アルゴリズム理解に対する到達感確認（Visual Concept Check）

**目的**: コードを一切出さず、可視化（フェーズ2）で見た図・データ構造ベースの直感的な問いを解かせることで、動的挙動の正しい脳内トレースを確認し、「理解できた」という到達感（手応え）を与えてテンポよく次フェーズ（フェーズ4：コード接続）へ送り出す。

#### 1. 設問構成・数量ルール

* **出題数: フェーズ3全体で【合計2問（1サイクル連動型）】に厳格に限定する。単一の要素選択だけでは「当たった」のか「理解した」のか区別できないため、「状態の取り出し」と「直後の状態更新/追加」をセットにした連動2問として出題する。画面遷移や連続テストによる認知的テスト負荷（学習ストレス）を与えない。**
* 連動2問の構成: 問1（取り出し/選択）「[データ構造] から次に取り出される/処理される要素はどれ？」に続き、問2（直後の変化/追加）「[問1の要素] を処理した直後、新たに [データ構造/図] に追加・更新される要素はどれ？」を出題する。
* 汎用形: 連動の抽象パターンは「処理対象の特定 ➔ それが引き起こす変化の特定」とする（例: ソートでは「次に交換・移動される要素 ➔ その結果として確定する位置」）。
* 完了の定義: 問2は問1で正解した要素について出題する。誤答時はその場で再挑戦し（任意で 3-4 のモーダル確認を使える）、問1・問2の両方に正解した時点でフェーズ3を完了とする。
* **対象領域**: フェーズ2のアニメーションで扱った例と**全く同じ図・全く同じデータ構造**から出題し、応用問題や例外ケース（別形状・コーナーケース）は一切混ぜない。
* **解答形式**: 「図またはデータ構造上の1タップ選択」のみ。テキスト入力や選択肢文の読解といった不要な負荷を完全に排除する。ただし状態変化の予測では「変化なし（何も追加・更新されない）」が正解になる場合があり、その場合は「どれも追加されない」等の選択肢を明示してよい（これも1タップ選択の範囲内とする）。

#### 2. 設計指標・学術的根拠

* **3-1. 低認知負荷・連動テスト（Low-Cognitive Load 2-Step Testing）**
  * **【根拠：認知的負荷理論（Cognitive Load Theory） / 流暢性の錯覚の解消】**
  * 受動的にアニメーションを見るだけで生じる「分かった気（受動的理解）」を、最小限の視覚的タップ問題で能動的な確認へと昇華させる。キューの先頭を見るだけで解けてしまうような視覚的ヒントによる誤った達成感を避けるため、「取り出し ➔ 周囲への影響」の1サイクルを2タップで確認させる。
  * **1文形式**: `「[直前のアニメーション文脈の提示]。次に [処理/操作] される [要素/データ] をタップしてください。」`
  * **問のパターン例（アルゴリズム共通）: 以下の2つを連動させて出題する。**
    * **次動作の予測**: 「次に [データ構造/処理領域] から取り出される/選択される要素はどれでしょう？」 ➔ 画面上の対象要素をタップ
    * **状態変化の予測**: 「[要素X] を処理した直後、[データ構造/状態] はどう変化するでしょう？」 ➔ 変化後の正しい状態図をタップ
* **3-2. ジャストインタイム・ラベリングの活用（Contextual Vocabulary Usage）**
  * **【根拠：状況的認知（Situated Cognition）】**
  * 設問文の中に、フェーズ2の図上でラベル付与された専門用語（例: 頂点、待ち行列、ピボット、親ノードなど）を自然に組み込む。
  * **狙い**: 用語の辞書的定義を解かせるのではなく、問いの文言として自然に触れさせることで、視覚対象と用語の意味を脳内で対応付け・定着させる。
* **3-3. 介入の限定と適正な到達感テキスト**
  * **【根拠：ARCSモデル「Confidence（自信）」 / 誇張のない達成感】**
  * 評価ストレスを与えず、「正しく追えている」という強い成功体験を与える。
  * 正解時は、大げさな評価（「完璧に理解しました」等）ではなく、確認したサイクルに即した具体的な肯定（例: 「正解！キューの基本動作（取り出しと追加）を正しく追えています」）を表示し、余計な解説を挟まず直ちにリザルト（タイプC区切り）を表示する。
* **3-4. ユーザー主導の任意ミニ復習（On-Demand Visual Remediation）**
  * **【根拠：自己決定理論（自律性） / 誤概念の自主的修正】**
  * 不正解時も画面を過去フェーズへ強制遷移させたり長文解説を出したりせず、正誤フィードバック（「おっと！もう一度考えてみよう」）とともに、**`[💡 該当ステップの動きを確認する]` という小さな任意ボタン**をその場に表示するにとどめる。
  * ユーザーが自らボタンをタップした場合のみ、根拠となるフェーズ2の1コマ（例: Step 11）の動く図とキャプションをモーダル等で再現表示する。見直すかどうかも学習者の意思に委ね、手戻り感（罰則感）をゼロにする。

#### 3. 完了時の遷移ルール（タイプC：評価リザルト＆次フェーズ予告）

* **【根拠：期待×価値理論（見通しの設計）】**
* フェーズ3完了時のリザルト画面では、到達感を提示すると同時に「次はコードへの接続（可視化とコードの対応）」と一言見通し（契約）を提示し、学習者が心の準備を持ってフェーズ4へ進めるようにする。

### フェーズ4：コード接続（Code Mapping / 既知の挙動とコードの照合）

**目的**: フェーズ2・3で完全に把握した「アルゴリズムの実行過程（既知の挙動）」を、フェーズ2と同じデータ・同じ実行過程をプログラムコードと重ねて再生する。タイピングや読解の負荷を与えず、「図のこの動き＝コードのこの1行」という1対1の照合（マッピング）に集中させ、メンタルモデルをコードへ接続する。

#### 1. 前提条件とUIレイアウト例外規定

* **受講前提の明確化**
  * **【指針上の事前条件】** 本フェーズは「変数」「代入」「インデント構造」程度の最小限の言語リテラシーを前提とする。構文文法そのものの初心者教育はカリキュラム前段に切り分け、本フェーズでは純粋にロジックとコードの照合に特化する。
* **左右対比レイアウト（共通制約の例外適用）**
  * 共通制約（縦一直線）の例外として、**「左：可視化キャンバス（フェーズ2と同じ図・同じ位置）」＋「右：コード領域」** の左右2カラム集約レイアウトを採用する。
  * **【同一コンテキスト維持原則】** コード表示は「図の差し替え」ではなく「領域の追加」である。左側の図はフェーズ2・3と同じ描画・配置関係を維持し、同一コンテキストを崩さない。ただしコード領域の文字の読みやすさが確保できない場合は、図を比率を保って縮小してよい（コードの文字サイズには下限を設け、下限を割る調整は図の縮小で行う）。

#### 2. コード領域の視覚制御（減光表示：Dim Effect）

* **非実行行の減光表示（dim化）**
  * **【根拠：認知的負荷理論 / 視覚的ノイズの低減】**
  * コード全体（全形）を表示して俯瞰性を保ちつつ、現在実行中（ハイライト行）以外のコード行はすべて薄いグレー（減光表示）にする。減光は視線誘導のためのものであり、薄さの下限は「コード全体が読み物として読める濃さ」とする。
  * 初学者に「コード全体をスラスラ読まなければならない」という圧迫感を与えず、視線を「今光っている1行」だけに強制的に誘導する。また、制御が上下に跳ぶ動きを見せることで「コードは実行順序に従って動く」という感覚を視覚的に伝える。
  * 同期ハイライト: 実行中のコード行と、その実行で変化する図の要素（ノード、キューの項目など）は同色で同時にハイライトする。【根拠：空間的・時間的近接の原則（Spatial & Temporal Contiguity Principle）】

#### 3. ステップとコード行の対応ルール（生成パイプライン共通仕様）

AIがどのアルゴリズムのフェーズ4を生成する際にも実装がブレないための、3つの同期実行ルール。

① 非描画行（制御・宣言・条件判定行）の扱い

* 図に直接変化を起こさない行（`while queue:`、`if visited:`、`for i in range:` など）も、**必ずスライダーの1ステップとしてハイライト通過**させる。
* この時のキャプションは「判定・確認」を言語化する（例: `「待ち行列に要素が残っているか確認します。」`）。裏側の処理を飛ばさずに見せることで、制御フローのメンタルモデルを完成させる。

② ループ行とキャプションの動的更新

* 同一のコード行が何度も繰り返し実行される場合、キャプションは単なる固定文ではなく、**現在のループ変数や対象要素を埋め込んだ動的実況文**を出力する。
* 例: `「[ループ1回目] ノードAの隣接ノード B を確認します。」` ➔ `「[ループ2回目] ノードAの隣接ノード C を確認します。」`

③ スカラー変数（インデックス・カウンタ等）の表示規則

* ループ変数（`i`, `j`）やカウンタ変数（`count`）など、図の中に描きにくい変数は、**【コード領域の最下部】に「`v = 'A'`, `dist = 2`」のように現在値をリアルタイム表示**する。図の中に無理に文字をねじ込まず、役割を分離する。そのステップで値が変化した変数はハイライトして示し、変化していない変数は通常表示のままにする。

#### 4. キャプションの3つの動作型分類（2-1からの伝播修正）

キャプション表現は「取り出し型」に限定せず、アルゴリズムの処理タイプ（動作型）に応じて以下の3パターンを使い分ける。実行行の特定はハイライトで行うため、キャプション本文では行番号に言及しない。

1. **データ構造操作型（キュー/スタック/木など）**:
   * `「[データ構造] から [要素] を取り出し/追加します。」`
2. **比較・評価型（ソート/検索/条件分岐など）**:
   * `「[要素A] と [要素B] を比較/判定します。」`
3. **状態更新・代入型（DP/スコア計算/グラフ更新など）**:
   * `「[配列/変数] の位置に [計算値] を書き込みます。」`

#### 5. フェーズ4の進行と遷移ルール

* **進行中（タイプB：シームレス接続）**:
  * アニメーションのコマ送りテンポを阻害しないよう、プレイヤースライダー操作と100%同期してコードと図を再生させる。無駄なボタンやモーダルは排除する。
* **フェーズ4完了時（タイプC：評価リザルト＆次フェーズ予告）**:
  * フェーズ2と同じ実行過程をコード付きで完走した段階でリザルトパネルを表示。
  * **【見通しの提示（契約）】**: `「可視化とコードの対応が確認できました！次はコードの基本確認（穴埋め・記法チェック）に進みます。」` と予告し、フェーズ5（コード基本確認）へと誘導する。

### フェーズ5：コード基本確認（Code Syntax & Operation Check）

**目的**: フェーズ4（コード接続）で全容を把握したコードに対し、要となる行（状態を変える行・条件判定の行）のコード表現を、1〜2問の穴埋め選択問題で確認する。「目的 ➔ コード」の逆方向の変換（役割と記法の結びつけ）を行い、自力実装に向けたコード表現の確信を得させる。

#### 1. 設問構成・数量ルール

* **出題数**: フェーズ5全体で【厳格に合計1〜2問（独立形式）】とする。
* **出題のカバー領域（独立2問の原則）**: フェーズ3のような連動形式ではなく、アルゴリズムの異なる本質をカバーする以下の2種類の独立した問いから構成する。
  * **問1【状態変化行の補完】**: キュー/スタックへの追加・削除、ソートの要素交換（swap）など、状態を更新するコード行。
  * **問2【条件判定行の補完】**: 繰り返しを継続する条件、または訪問済み/到達判定を行うコード行。
* **解答形式**: **「コード上の穴埋め選択（1タップ）」**。自由記述（キーボードタイピング）は完全に排除する。
* **対象コード**: フェーズ4で提示されたコードと**全く同じコード・同じ行構成**を使用する。
* 対象行の限定: 穴埋めの対象は上記の本質的な行に限定し、インデントやコロン等の文法的な細部は対象にしない。

#### 2. 設計指標・学術的根拠

* **5-1. 完成問題効果（Worked-Example Effect）の適用**
  * **【根拠：認知的負荷理論（Cognitive Load Theory）】**
  * ゼロからコードを書かせるのではなく、9割完成されたコードの**残り1割（核心となる1行・1変数）を補完させる（完成形課題）**。
  * 文法エラーなどの本質的でない外在的負荷をゼロにし、「そのコード行が持つ意味」の理解だけに脳のワーキングメモリを100%集中させる。
* **5-2. 選択肢の構文的成立原則（消去法回答の防止）**
  * **【生成・実装ルール】** 穴埋め選択肢は、すべて「単体として文法（構文）的に正しく成立するもの」で構成しなければならない。
  * 文法エラーになる選択肢を混ぜて「消去法」で解けてしまうことを防ぎ、コードの役割・意味を理解していなければ正解できないように設計する。
  * **良い例**:
    * 状態変化: `[append / popleft / remove]`（すべてValidなメソッド）
    * 条件判定: `[not in / in / ==]`（すべてValidな演算子）
* **5-3. 目的 ➔ コードの逆方向問いかけ（1文形式）**
  * フェーズ4の「コード ➔ 動き」とは逆方向に、「目的（役割）➔ 記法」を結びつけさせる。
  * **1文形式**: `「[処理の目的] を行うために、[行番号] 行目の空欄に入る正しいコードを選んでください。」`
* **5-4. ユーザー主導の任意ミニ復習（On-Demand Remediation）**
  * **【根拠：自己決定理論（自律性） / 復習先の一貫性】**
  * 不正解時は長文解説を表示せず、正誤表示とともに **`[💡 この処理の動作（フェーズ4）をもう一度見る]`** という任意ボタンをその場に表示する。
  * タップした場合のみ、直前の**フェーズ4（コード接続）の該当行の可視化アニメーションとコードハイライト**をモーダル等で再現表示する。

#### 3. フェーズ5完了の定義および遷移ルール（タイプC：評価リザルト＆予告）

* **フェーズ5の完了定義**:
  * 誤答時はその場で再挑戦させ、すべての問題に正解することでフェーズ完了となる（復習モーダルの閲覧はユーザーの任意）。
* **リザルト画面での予告ルール（呼称の統一）**:
  * **【根拠：期待×価値理論（見通しの設計 / 数の非対称の開示）】**
  * 完了時の評価リザルト画面では、次フェーズの正式名称である「応用・総括」を明記し、3〜5問のテストがあるという見通し（契約）を提示する。
  * **リザルト表示テキスト例**:
    * `「基本コードの役割が確認できました！次は【応用・総括】（別パターンや例外ケースの3〜5問）で、自力実装に向けた最後の土台を固めます。」`

### フェーズ6：応用・総括（Consolidation & Application Check）

目的: 基本例とは異なるデータや境界条件での挙動追跡、およびコードの並べ替え（Parsons問題）による構造構築の練習を行い、フェーズ7（完全自力実装）へ滑らかに接続する。フェーズ7に向けた「弱点診断」としての役割も担う。

#### 1. 設問構成・数量・形式ルール

出題数: フェーズ6全体で【3〜5問】とし、以下の3つの形式を組み合わせる。フェーズ5のリザルトで「次は応用・総括（3〜5問）」と予告済みであり、学習者は心の準備をして取り組む。
転移の追跡問題（1〜2問）: 基本例とは異なるグラフ形状やデータ配列を提示し、動作順序や状態変化を視覚的・選択式で追跡させる。
推論可能な境界ケース問題（1〜2問）: 「ゴールなし」「孤立ノード」など、基本ルールの適用のみで推論可能なエッジケースの挙動を問う。
コード並べ替え問題（Parsons問題 / 1問）: フェーズ7への架け橋として、ランダムに崩されたコード行群をタップ操作で正しい順序に並べ替えさせる。タイピングの負荷なしに「コードの全体構造を組み立てる力」を訓練する。
Parsons問題の仕様: コード行は正しいインデントを付与した状態で提示し、並べ替えの対象は行の順序のみとする。不要な行・誤った行（妨害行）は混ぜない。
解答形式: 「コード選択」「データ構造上のマルチタップ」「トレース順序の選択」など、選択・視覚操作ベースとする。フェーズ7（自由記述）との違いとして、テキストタイピングは求めない。
論点タグ: 各問には出題時に論点タグ（例: 取り出し、条件判定、境界ケース、構造構築）を持たせ、リザルトの診断はタグ単位の正誤から生成する。

#### 2. 設計指標・学術的根拠

6-1. Parsons問題（コード並べ替え）による構造構築の訓練
【根拠：プログラミング教育研究（Parsons Problems）】
「コードを読む/選択する（フェーズ5）」と「ゼロから書く（フェーズ7）」の間に位置する学習形式。構文エラー（タイプミスやインデントミス）のストレスを与えず、アルゴリズムの制御構造（初期化 ➔ ループ ➔ 判定 ➔ 更新）を組み立てる認知力だけを鍛える。
6-2. 推論可能範囲への境界ケース限定ルール
【出題制約】 境界ケースとして出題して良いのは、「フェーズ2・4で学んだ基本規則から論理的に推論できる範囲」に厳格に限定する。
フェーズ2で解説していない新しい例外処理や別形式のルールを突然出題することを禁止し、初学者の理不尽な不快感を防ぐ。
6-3. 復習先の割り切り仕様（On-Demand Remediation）
【仕様定義】 不正解時に提示する任意復習ボタン [💡 基本例の動き・コード（フェーズ4）を見る] の参照先は、あくまで「基本例（フェーズ4）」のままとする。
新データ自体の答え合わせアニメーションをその場で作って見せるのではなく、基本例のルールを再確認させ、自分で新データへの適用を考えさせる仕様として割り切る。

#### 3. フェーズ6の完了定義およびソフトゲート型リザルト

完了定義（ソフトゲート方式）: フェーズ3・5のようなハードゲート（全問正解まで再挑戦）は行わず、1回目の全問回答が終わった時点で成績（スコア）を表示し、そのまま次へ進むことを許可する。
理由: フェーズ7（自力実装）へ入る前の「自分の理解度の診断」として機能させ、正解の消去法によるゴリ押しや、本番直前の離脱・挫折を防ぐため。
診断型リザルト画面の表示ルール: 事実通りのスコアと弱点箇所をフラットに提示し、結果全体への過度な到達感表現（「完璧に理解できました」等）は行わない。
表示テキスト例: 「応用・総括の診断結果：3問中 2問正解！」「【診断】キューからの取り出しと条件判定は正しくできています。境界ケース（孤立ノード）の理解をフェーズ7で確認してみましょう。」
フェーズ7への最終予告テキスト: 「理解の状況が確認できました。それでは【フェーズ7：自力実装】に進み、自分の手でコードを完成させましょう！」

### フェーズ7：自力実装＆デバッグ（Apply & Practice）

目的: フェーズ6（Parsons問題）までに獲得した「コード構造の組み立て力」をベースに、自由記述でアルゴリズムを完成させる。テスト駆動（TDD）形式の即時実行フィードバックとユーザー主導のデバッグ支援を提供し、「自分の手でアルゴリズムを実装できた」という達成感（Satisfaction）とともに学習を完結させる。

#### 1. 実装形式と環境ルール

コード記述形式: 骨組み（関数定義や入出力処理など）が用意されたテンプレートコードに対し、アルゴリズムのコアロジックを自由記述させる。
コード補助チップ: 常時表示はしない。ヒントのレベル1（使う部品）の中で、予約語や変数名・メソッド名（queue, popleft(), visited 等）のトークン一覧を提示し、1タップでカーソル位置に挿入できるようにする。チップはトークン単位に限定し、ロジックの断片は含めない。（課題固有のトークン集合を最初から見せること自体がヒントになるため、必要な学習者が自分で開く形にする。）
テスト駆動形式の評価環境: 自力実装の評価は、文章の採点ではなく「複数テストケースの自動実行」によって行う。テストケースは表示用と判定用に分ける。表示用（基本ケース）は入力と期待出力・実際の出力を表示し、デバッグに使える。判定用（境界ケースを含む）は種別と成否のみを表示し、入出力は非公開とする（場合分けによるハードコードの防止）。
実行回数: 実行（テスト）の回数に上限は設けない。

#### 2. 設計指標・学術的根拠

7-1. スモールステップ・テスト駆動評価（TDD-Style Immediate Feedback）
【根拠：即時フィードバック原則 / 成功体験の可視化】
［コードを実行する］ボタンを押した際、複数のテストケース（基本ケース、境界ケース等）に対する実行結果を表示する。「テストケース 1/3 通過 ➔ 2/3 通過」とプログレスバーで見せることで、修正のプロセス自体に手応えを感じさせる。
7-2. ユーザー主導の組み立てヒント（On-Demand Scaffolding）
【根拠：自己決定理論（自律性） / 段階的支援（Progressive Disclosure）】※本構成は試行中。理論的裏付け（完成課題・段階的ヒント開示など）の原典確認は今後の課題とする。
エラーやテスト不合格時に、長文の正解コードや自動解説をいきなり突きつけることは禁止する。ヒントは「直す」ためではなく「組み立てる」ための支援とし、段階的にアクセスできる4段階の「ユーザー主導ヒント」を配置する（前のレベルを開くと、次のレベルが開ける）。正解コードとの差分（Diff）表示は行わない。
レベル1（使う部品）: その課題で必要になる変数（役割の説明つき）と、予約語・変数名・メソッド名のトークン一覧を示す。トークンは1タップでエディタのカーソル位置に挿入できる。
レベル2（処理の流れ）: 必要な処理の手順を日本語で番号付きに示す。コードは見せない。
レベル3（条件とループの骨格）: 条件判定とループの制御行だけを、正解コードから元のインデントのまま引用して示す。本体行は見せない。
レベル4（並び替え前のコード）: 最終ヒントとして、フェーズ6のParsons問題と同じ盤面（並び替え前のコード）を、練習モード（採点なし）で提示する。
エラー種別の言語化（ヒントには含めない）: 実行結果には、失敗の種別（文法エラー / 実行時エラー / 結果の不一致 / タイムアウト）を言葉で常に併記する。生の例外メッセージやトレースバックは表示しない。
ヒント利用のログ: 使用したヒントのレベル（1〜4）と回数を記録する（自力で通過したか、支援を受けて通過したかを後から区別できるようにする）。
7-3. デバッグ時の視覚再現（Visual Debugging）
【根拠：メンタルモデルと実行結果の結合】
自身の記述したコードが失敗した場合、「自分のコードを実行した結果、図（グラフやデータ構造）がどう動いてどこで止まったか」をフェーズ2と同じキャンバス上で再現再生できるようにする。テキストのエラーメッセージだけでは分からない「論理バグ（ロジックの勘違い）」を視覚的に発見させる。
段階的対応: 実装は、まず想定解法に沿ったコードのトレース再現から対応する。トレースに対応できない実行については、停止位置と最終状態の表示に留める。コードの実行はサンドボックス内で行い、実行時間に上限を設ける。

#### 3. フェーズ7完了の定義および全達成リザルト

フェーズ7の完了定義: 提示されたすべてのテストケース（表示用・判定用の両方）をパスすることで「完全クリア」とする（ハードゲート）。ヒントは任意で何度でも使えるため、到達可能性はヒントによって担保される。
全達成リザルト画面（ロードマップ完結）:
【根拠：ARCSモデル「Satisfaction（満足感）」】
全フェーズ（1〜7）を完走し、自力実装を成功させた学習者に対し、達成感を最大化するエンディング演出と最終リザルトを表示する。
表示要素: 達成バッジ / 称号（例: 「幅優先探索（BFS）マスター！」）、全体の成果まとめ（可視化理解 ➔ 穴埋め ➔ 応用演習 ➔ 自力実装を完走した実績の可視化）、次のステップへの導線（［アルゴリズム一覧に戻る］または［関連アルゴリズム（例: ダイクストラ法）に挑戦する］のアクションボタン）。
