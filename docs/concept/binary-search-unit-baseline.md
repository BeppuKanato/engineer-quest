- コース seed `course-algorithm-binary-search-v1`（タイトル「二分探索」、カテゴリ SEARCH、難易度 EASY、公開・初期解放）は既に存在する。統合ではコースを追加せず、カード・実績・サムネイル・レジストリ登録のみを行う。
- §6 の判断ポイントは推奨デフォルトで進める（キュー委任）。後から変更可能。

## 1. アルゴリズムの確定事項

- 対象は「小さい順に並んだリストから目的の値を探し、そのインデックスを返す。無ければ -1」。
- 探索範囲は両端含む [lo, hi]。中央は `mid = (lo + hi) // 2`（切り捨て）。
- 比較のたびに、中央より小さい側か大きい側かの一方を丸ごと捨てる。範囲が空（lo > hi）になったら「無い」で終了。
- 主教材は「左を捨てる→右を捨てる→一致」と両方向の切り捨てが1回ずつ現れるケースにした。

### 主教材（検証済み）

- リスト `[3, 7, 12, 19, 25, 31, 42]`（7要素）、探す値 **25**
- トレース：(lo=0, hi=6, mid=3, 値19) → 19<25 で左を捨て lo=4 → (4, 6, 5, 31) → 31>25 で右を捨て hi=4 → (4, 4, 4, 25) → 一致、**インデックス 4** を返す（3回の比較）

### 不在ケース（フェーズ6で使用、検証済み）

- 同じリストで探す値 **20**：比較列は 19 → 31 → 25 と主教材とまったく同じ道をたどり、最後の1個まで絞った結果「無い」と分かり **-1**（lo=4 > hi=3 で終了）。「見つからなかった」ではなく「無いことを証明できた」が要点。

### 転移用（検証済み）

- リスト `[2, 5, 8, 12, 16, 23, 38, 56, 72, 91]`（10要素・偶数長）、探す値 **23**
- トレース：(0, 9, 4, 16) → (5, 9, 7, 56) → (5, 6, 5, 23) → **インデックス 5**（3回）。最初の mid=(0+9)//2=4 で、偶数長では中央が左寄りになる（切り捨て）を体験させる。

### 導入の数当て（検証済み）

- 1〜100 の数を「大きい／小さい」のヒントだけで当てる場合、二分探索のやり方なら最大 **7回** で必ず当たる（100→50→25→13→7→4→2→1 と半分以下に減る）。

## 2. 参照コード（契約 `binary-search-v1`）

```python
def binary_search(values, target):
lo = 0
hi = len(values) - 1
while lo <= hi:
mid = (lo + hi) // 2
if values[mid] == target:
return mid
elif values[mid] < target:
lo = mid + 1
else:
hi = mid - 1
return -1
```

- 12行。引数名は `values` / `target` で固定（フェーズ7のテンプレート・判定・トレース取得の契約）。
- 返すのはインデックス（int）。無い場合は -1。
- 入力リストは変更しない（読み取りのみ）。判定は戻り値の一致で足り、入力不変の検出は不要。

### フェーズ3 動きの確認問題（連結2問）

- 場面：主教材の途中——1回目の比較が終わり、左側を捨てた直後（lo=4, hi=6、19 は確認済み）。続きを学習者が決める。
- Q1：次に調べるのはどの位置か（配列セルのタップ、正解はインデックス 5 の 31）
- Q2：31 と 25 を比べたあと、次に残る範囲はどうなるか（4択：右側を捨てて範囲は 4 だけになる／左側を捨てて範囲は 6 だけになる／範囲は変わらない／探索が終わる）——正解は1つ目
- 誤答時のフィードバック文は「真ん中の決め方」「大きい側・小さい側のどちらを捨てるか」に言及する（バブルソート確認問題の文面水準に合わせる）

### フェーズ6 応用問題（4問）

- Q1 手シミュレーション：転移リスト `[2, 5, 8, 12, 16, 23, 38, 56, 72, 91]` で 23 を探すとき、最初に調べるのはどの位置か（タップ、正解はインデックス 4 の 16）
- Q2 不在ケース：主教材のリストで 20 を探すとどうなるか（4択）——正解は「最後の 1 個まで絞っても 20 はなく、探索範囲が空になって終わる」。比較列が 25 のときと同じ道になることを解説で示す

- Q4 前提の理解：並んでいないリスト `[25, 3, 42, 7, 19]` で同じやり方をすると壊れるのはなぜか（4択）——正解は「大きい側・小さい側を捨てる判断が、並んでいることを前提にしているから」

### フェーズ7 自分で実装

- テンプレート：関数定義 `def binary_search(values, target):` と docstring のみ与え、本文は自由記述。契約 `binary-search-v1`（§2）。
- テスト：表示用 D1 = 主教材（25 → 4）。判定用 J1 = 主教材（25 → 4）、J2 = 転移（23 → 5）、J3 = 不在（主教材のリストで 20 → -1）。
- ヒント（4段階ラダー、他単元の §7-2 型に合わせる）：

## 4. 配列描画基盤の再利用とトレース

- 描画：`ArrayDrawing` を共有し、状態は「範囲外（捨てた）／範囲内／中央（処理中）／発見（確定）」を持つ。バブルソートの状態語彙（処理中・確定・通常）と衝突しないよう、二分探索側の盤面型（types）で状態を定義し、色はプレイヤートークンに従う（処理中＝青、確定＝実績系の青、範囲外＝完了グレー相当、情報テキストは黒）。
- 結果画面の図：`BinarySearchResultFigure`（発見セルを確定表示した主教材の配列）を単元側に持つ（バブルソートの `BubbleSortResultFigure` の型）。
- トレース取得：学習者のコードの `values` は「array」種別として既存ハーネスで捕捉できる（平坦な数値リストが1つだけのとき）。ただし lo / hi / mid / target は現在のパススルー対象（size / choices / i / j / n / node / neighbor）に無いため、**共有ハーネスに int パススルーとして `lo` / `hi` / `mid` / `target` を加算**する（他単元への影響なし——対象名の変数が無ければ何も変わらない）。変換（convertTrace）は単元側で、array と lo/hi/mid から盤面スナップショットを作る。イベント上限は既定 500 で十分（D1 は数十イベント）。

## 6. 要判断ポイント（推奨デフォルトで進行）

1. **主教材**：[3, 7, 12, 19, 25, 31, 42] で 25 を探す（左捨て→右捨て→一致の3回）。対案：最初に一致する単純ケースは退屈なため不採用。
2. **契約**：返すのはインデックス、無ければ -1。真偽値や値そのものを返す案は、フェーズ7判定と「見つけた位置」の概念を弱めるため不採用。
3. **転移リスト**：10要素の偶数長にして、mid の切り捨て（左寄り）を体験させる。
4. **不在ケースの置き場**：フェーズ2は発見ケースに集中し、不在（-1 と終了条件）はフェーズ6で扱う。フェーズ2に入れるとステップが膨らみ、初回の成功体験が薄れるため。
5. **ハーネス拡張**：lo / hi / mid / target の int パススルーを共有ハーネスに加算する。単元側で変数名を i / j に寄せる案は、教材コードの可読性を損なうため不採用。
6. **カード**：RARE「探索範囲を半分にする」（フェーズ2）、COMMON「中央の値と比べる」（フェーズ5）、EPIC「対数時間」（フェーズ7）。
7. **コース**：既存 seed を使い、統合はカード・実績・サムネイル・レジストリのみ（コース総数は 9 のまま）。
