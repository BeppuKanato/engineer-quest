## 1. アルゴリズムの確定事項

- 貪欲法とは「その時点で使える最良の選択を繰り返し、後戻りしない」方針そのものである。本単元の学習目標は次の2点。
  1. 貪欲法の方針を理解し、硬貨問題（金額を硬貨の枚数最小で払う）に適用できること。
  2. 貪欲が常に最適とは限らないことを、反例を通して理解すること。
- 硬貨問題への適用は「残額以下で一番大きい硬貨を繰り返し選ぶ」。硬貨の額面は大きい順に与えられる前提とし、並べ替えは方法の一部に含めない（§6 決定事項2）。
- 主教材は全6額面をすべて使うケースにした（枚数の内訳に偏りが出て、額面を1つずつ進む様子が全部見える）。

### 主教材（検証済み）

- 硬貨 `[500, 100, 50, 10, 5, 1]`（日本の硬貨、降順）、金額 **786**
- 結果：`[500, 100, 100, 50, 10, 10, 10, 5, 1]` の **9枚**。残額の推移は 786→286→186→86→36→26→16→6→1→0

| 枚目 | 選んだ硬貨 | 残額の変化 |
|---|---|---|
| 1 | 500 | 786 → 286 |
| 2 | 100 | 286 → 186 |
| 3 | 100 | 186 → 86 |
| 4 | 50 | 86 → 36 |
| 5 | 10 | 36 → 26 |
| 6 | 10 | 26 → 16 |
| 7 | 10 | 16 → 6 |
| 8 | 5 | 6 → 1 |
| 9 | 1 | 1 → 0 |

- なお日本の硬貨では、0〜999円の全額について貪欲の枚数が DP で求めた最適の枚数と一致することを検証済み（この硬貨体系では貪欲が常に最適になる。フェーズ6の反例が「額面の組み合わせによっては崩れる」ことを際立たせる）。

### 転移用（検証済み）

- 同じ硬貨で **342**：結果 `[100, 100, 100, 10, 10, 10, 10, 1, 1]` の **9枚**（100×3・10×4・1×2）。残額の推移は 342→242→142→42→32→22→12→2→1→0。500 が使えない金額から始まる点が主教材との違い。

### 反例（フェーズ6の山場、検証済み）

- 額面 `[4, 3, 1]`、金額 **6**：貪欲は `[4, 1, 1]` の **3枚**。しかし最適は `[3, 3]` の **2枚**（DP で確認）。最初に一番大きい 4 を選ぶと、残り 2 を 1 の硬貨で埋めるしかなくなるのが敗因。
- 金額 6 は、この額面の組み合わせで貪欲が最適と一致しなくなる最小の金額であることも検証済み（1〜5 では一致する）。反例として最小で扱いやすい。

### 別額面の例（フェーズ7の J3、検証済み）

- 額面 `[25, 10, 5, 1]`、金額 **41**：結果 `[25, 10, 5, 1]` の **4枚**。残額の推移は 41→16→6→1→0。この額面では貪欲が最適とも一致する（DP で確認）。

## 2. 参照コード（契約 `greedy-coins-v1`）

```python
def greedy_coins(amount, coins):
    result = []
    remaining = amount
    for coin in coins:
        while remaining >= coin:
            result.append(coin)
            remaining -= coin
    return result
```

- 8行。引数名は `amount` / `coins` で固定（フェーズ7のテンプレート・判定・トレース取得の契約）。
- 戻り値は「選んだ硬貨のリスト（選択順）」。フェーズ2の選択ステップと1対1に対応し、判定は戻り値の一致で足りる（§6 決定事項1）。
- `coins` は降順（大きい順）に渡される前提で、関数内ではソートしない（§6 決定事項2）。引数は変更しない（読み取りと `remaining` への代入のみ）。
- 構造は「額面を大きい順に回す for」と「その額面を使える間くり返す while」の二重ループ。硬貨1枚の選択 = while 本体の1回実行、が本単元の実行単位。

## 6. 決定事項（2026-11-11 ユーザー承認済み）

1. **契約の戻り値**【決定】：選んだ硬貨のリスト（選択順）を返す。DFS の訪問順リストと同じ流儀で、判定が戻り値の一致で単純になり、フェーズ2の選択ステップと1対1に対応する。枚数形式は「どの順に選んだか」という貪欲の過程が見えなくなるため採らない。
2. **coins の前提**【決定】：降順で渡し、関数内ではソートしない。貪欲法の本質は選択の繰り返しであり、並べ替えは前提処理。教材コードも8行に収まる。降順は呼び出し側（教材データ・テスト）が保証する。
3. **判定用テストへの反例ケースの追加**【決定】：J1〜J3 に加え、額面 `[4, 3, 1]`・金額 6（期待値は貪欲の `[4, 1, 1]`）を **J4 として追加し、表示用には出さない**。契約は「貪欲の再現」なので、最適化ソルバを書くと不合格になることで、実装対象が貪欲であることを区別できる。フェーズ6で先に反例を学ぶため、混乱は限定的と考える。
4. **カード名**【決定】：RARE「貪欲な選択」／COMMON「残額を減らしていく」／EPIC「最適とは限らない」。COMMON は処理の実体（残額を更新し続ける）を表し、フェーズ5の穴埋め（残額の比較と更新）と対応する。
5. **主例の金額**【決定】：786。全6額面をすべて使い、内訳も 1・2・1・3・1・1 とばらつく。対案の 865 は 1円を、940 は 50・5・1円を使わないため、額面を進む様子が一部見えなくなる。
6. **ハーネス拡張**【決定】：`remaining` / `coin` / `amount` の int パススルーを共有ハーネスへ加算する。二分探索（PR #311）と同型の additive な変更で、他単元への影響はない。単元側で変数名を既存パススルー名に寄せる案は、教材コードの可読性を損なうため不採用。
7. **コースの追加**【決定】：新規 seed `course-algorithm-greedy-coins-v1` を追加し、統合時に `seed:preserve` を再実行する前提で進める（二分探索と違い流用できる既存コースが無いため）。
