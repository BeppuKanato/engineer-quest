# コース構成と学習目標案

このドキュメントは、全日程の講義資料をもとに、Engineer Quest のコース構成と学習目標を整理したもの。

ここでの `Base` / `Challenge` / `Create` は、現時点ではDB上の概念ではなく教材設計上の分類として扱う。

- Base: 講義理解の最低ライン。全員が迷わず進める本線。
- Challenge: Baseから枝分かれする任意の追加ミッション。コース完了には不要。
- Create: 別モードで扱う自由制作・AIレビュー。関連するBase/Challengeを推奨条件として表示する。

## 全体方針

日程別にコースを分けるのではなく、「Webアプリで何ができるようになるか」という機能・体験単位でコースを構成する。

講義日との対応は持たせるが、1つのコースが複数日にまたがってもよい。

## Course / Mission / Lesson / Activity / Exam の設計原則

現行アプリの学習構造は次の階層として扱う。

```text
Course
  └ Mission
      ├ Lesson
      │   ├ Activity
      │   ├ Activity
      │   └ Activity
      └ Mission Exam
          ├ easy
          ├ normal
          └ hard
```

各階層の役割は次の通り。

- Course: まとまった学習テーマ。例: Webアプリの全体像、Flaskでページ表示、HTML/CSS、DBなど。
- Mission: 1つの到達目標。ユーザーが「これができた」と感じられる小さな達成単位。
- Lesson: Mission内の段階的な学習ステップ。複数のActivityで1つの概念や操作を学ぶ。
- Activity: Lesson内の最小活動。説明、見比べ、選択、穴埋め、短い実践など。
- Mission Exam: Mission内のLessonをすべて終えた後に挑戦する、お手本再現型の確認テスト。

設計ルール:

- 1つのMissionには、原則として複数のLessonを置く。
- 1つのLessonには、原則として複数のActivityを置く。
- Mission Examは、Mission内のLessonで見た・触った・意味を確認した内容だけを出す。
- 1コースあたりのMission数は固定しない。内容の密度に合わせて自然な数にする。
- 1ミッションあたりのLesson数も固定しない。到達目標に必要な分だけ置く。
- 内容が薄い場合は無理に独立コース化しない。別コースのMissionとして扱う。
- 初見で解けない確認テストを出さない。
- 「なぜこの操作をするのか」が残らないよう、Activity内で理由を説明する。
- Main Missionはコース完了に必要な本線として扱う。
- Challenge Missionは任意のサブクエストとして扱い、コース完了条件には含めない。
- Challenge Missionは、関連するMain Missionのクリア後に枝として開放するのが自然。
- Createモードは通常コースとは別枠で扱い、関連するMissionの達成状況を推奨条件として表示する。

## コース一覧案

### 1. Webアプリの全体像を知る

目的:

ブラウザ、サーバ、URL、HTTP、フロントエンド、バックエンドの関係をざっくり理解し、FlaskやHTMLが何のために出てくるのかを把握する。

対応する講義日:

- 1日目
- 2日目のフロント・サーバ開発者の話
- 5日目のAPIの導入

学習目標:

- Webアプリはブラウザとサーバのやり取りで動くと説明できる
- フロントエンドとバックエンドの役割を区別できる
- URLへアクセスするとサーバが処理し、HTMLなどの結果を返す流れを理解する
- APIは、別のプログラムや外部サービスに処理を依頼する入口だと理解する

使用場面分類:

- 予習: とても向いている。講義で出る用語の初見感を下げる。
- 講義中: 向いている。操作で迷ったときに全体像へ戻る確認に使える。
- 復習: 向いている。各日の作業がWebアプリ全体のどこに当たるか整理できる。

Baseで扱うこと:

- ブラウザ、サーバ、URL、HTTPの最小説明
- フロントエンドとバックエンドの役割
- 「入力する」「送る」「処理する」「返す」「表示する」の順番
- Flaskがサーバ側、HTML/CSSが画面側に近い役割であること

Challengeで扱うこと:

- Webアプリの処理順を並べ替える
- 「フォーム送信」「DB保存」「API呼び出し」が流れのどこに入るかを考える
- エラー時に、ブラウザ側・サーバ側・DB側のどこを疑うか分類する

Createモードへの接続:

- 自分のアプリ案を「画面」「入力」「処理」「保存」「外部API」に分解するワークへ接続する。

### 2. Flaskでページを表示する

目的:

Flaskの最小構成を理解し、サーバを起動してブラウザでHTMLページを確認できるようにする。

対応する講義日:

- 1日目

学習目標:

- Flaskプロジェクトの基本的なファイル構成を理解する
- `app.py`、`views.py`、`templates/index.html` の役割を区別できる
- `render_template` がHTMLテンプレートを返すために使われると理解する
- サーバを起動し、ブラウザで表示確認する流れを理解する

使用場面分類:

- 予習: 向いている。ファイル名やフォルダ名を事前に見ておくと講義で迷いにくい。
- 講義中: とても向いている。作業が詰まった学生の確認用に使える。
- 復習: とても向いている。スライド通りに作った構成の意味を整理できる。

Baseで扱うこと:

- Flaskプロジェクトを開く
- `templates` フォルダの役割
- `views.py` のルート処理
- `app.py` でアプリを作ること
- サーバ起動とブラウザ確認

Challengeで扱うこと:

- ルートを1つ追加する
- 別のテンプレートを表示する
- URLと関数の対応を読み解く
- スマホからアクセスするためのホスト指定の意味を確認する

Createモードへの接続:

- 自分のトップページを作る
- 自己紹介サイトやサークル紹介サイトのテンプレートへ接続する

### 3. HTML/CSSで画面を作る

目的:

HTMLで情報の構造を作り、CSSで見た目を整える基本を学ぶ。

対応する講義日:

- 1日目
- 4日目のフロント改善

学習目標:

- `h1`、`p`、`a`、`img`、`div` など基本タグの役割を理解する
- `class` を使ってHTML部品に名前を付けられる
- CSSで色、余白、枠線、背景などを調整できる
- `static` フォルダがCSSや画像などの静的ファイルに使われると理解する

使用場面分類:

- 予習: 向いている。タグの役割を見ておくと講義の画面編集が理解しやすい。
- 講義中: 向いている。早く終わった学生の画面改造に使える。
- 復習: とても向いている。画面が変わるため達成感を作りやすい。

Baseで扱うこと:

- 見出しと本文を書く
- リンクや画像の役割を知る
- `div` と `class` でまとまりを作る
- 簡単なカードUIを作る
- CSSで余白や色を変える

Challengeで扱うこと:

- カードを複数並べる
- ナビゲーションを作る
- スマホでも見やすいレイアウトを考える
- 既存の画面を少しリデザインする

Createモードへの接続:

- 自己紹介ページ
- 作品紹介ページ
- 予約サイトのトップ画面
- フロント特化の自由制作テンプレート

### 4. PythonでWebの入力を扱う

目的:

Webアプリで必要になるPythonの基礎に絞り、フォーム入力をサーバ側で受け取る流れを理解する。

対応する講義日:

- 2日目

学習目標:

- Webアプリで使う範囲の変数、if、list、dict、関数の役割を理解する
- フォーム入力がサーバ側へ送られる流れを理解する
- Python側で受け取った値をHTMLに返せると理解する
- `GET` と `POST` の違いを初歩的に説明できる

使用場面分類:

- 予習: 一部向いている。Python文法そのものを厚くしすぎない方がよい。
- 講義中: とても向いている。フォーム送信の手順確認に使える。
- 復習: とても向いている。入力値がどこへ行ったのか整理できる。

Baseで扱うこと:

- 変数に値を入れる
- ifで処理を分ける
- list/dictで複数データを扱う
- formの入力値を受け取る
- 入力された値を画面に表示する

Challengeで扱うこと:

- 入力値が空のときの処理
- 複数項目のフォーム
- 簡単なバリデーション
- 入力内容によって表示メッセージを変える

Createモードへの接続:

- 診断アプリ
- 質問フォーム
- 名前を入力すると結果が変わるアプリ

### 5. データを保存して使う

目的:

DBを使って、入力されたデータを保存し、あとから一覧表示できるWebアプリの基本を学ぶ。

対応する講義日:

- 3日目

学習目標:

- DB、テーブル、行、カラムの意味をざっくり理解する
- Webアプリでデータを保存する必要性を理解する
- 予約データを登録し、一覧表示する流れを理解する
- 保存・取得・更新・削除の基本操作を知る

使用場面分類:

- 予習: 向いている。DB用語への抵抗を下げる。
- 講義中: 向いている。操作が多いため、詰まりポイント確認に使える。
- 復習: とても向いている。予約サイトの流れを整理しやすい。

Baseで扱うこと:

- DBとは何か
- テーブル、行、カラム
- 予約データを保存する
- 保存したデータを一覧表示する
- どの画面操作がDB操作につながるか

Challengeで扱うこと:

- 予約の削除
- 予約の更新
- 日付や名前で絞り込む
- DBの中身と画面表示を対応づける

Createモードへの接続:

- 予約サイト
- メモアプリ
- 持ち物リスト
- 出欠管理
- バックエンド特化の自由制作テンプレート

### 6. ユーザー機能を作る

目的:

ライブラリを使ってログイン機能を導入し、ユーザーごとに情報を扱うWebアプリの考え方を学ぶ。

対応する講義日:

- 4日目

学習目標:

- ユーザー認証がなぜ必要か理解する
- 外部ライブラリを導入して機能を増やす流れを知る
- ログイン状態によって表示や操作が変わることを理解する
- ユーザーごとのデータ管理の考え方を知る

使用場面分類:

- 予習: 軽めに向いている。認証の目的を知る程度がよい。
- 講義中: 向いている。ライブラリ導入やログイン画面作成の補助に使える。
- 復習: 向いている。なぜログインが必要か整理できる。

Baseで扱うこと:

- ログインとは何か
- ライブラリを使う理由
- ユーザーごとに表示を変える考え方
- 認証が必要な画面と不要な画面を区別する

Challengeで扱うこと:

- ログイン済みユーザー名の表示
- 自分の予約だけ表示する
- ログアウト導線
- エラーメッセージの改善

Createモードへの接続:

- 自分専用メモ
- 会員制予約アプリ
- マイページつきアプリ

### 7. APIとAIを使う

目的:

APIを使って外部サービスと連携し、AIなどの機能をWebアプリに組み込む体験をする。

対応する講義日:

- 5日目

学習目標:

- APIは外部サービスに処理を依頼する入口だと理解する
- リクエストとレスポンスの考え方を知る
- JSONがデータのやり取りに使われる形式だと理解する
- AI APIをWebアプリに組み込む流れを知る

使用場面分類:

- 予習: 向いている。APIやJSONという言葉への抵抗を下げる。
- 講義中: 向いている。処理の流れが見えにくいため図解問題が有効。
- 復習: とても向いている。AI連携で何が起きたか整理できる。

Baseで扱うこと:

- APIとは何か
- JSONとは何か
- フロント、サーバ、外部APIの流れ
- AIに送る情報と返ってくる情報

Challengeで扱うこと:

- APIの返答を画面に表示する
- プロンプトを少し変えて結果を比較する
- エラー時の原因を分類する
- APIキーを直接フロントに置かない理由を知る

Createモードへの接続:

- AI質問箱
- 文章要約
- 診断アプリ
- 予約内容のおすすめコメント生成
- API/AI特化の自由制作テンプレート

### 8. 自分のアプリを企画する

目的:

まだアプリ案がない学生でも、自分の興味や身近な困りごとからアプリの企画を考えられるようにする。そのうえで、企画を画面・入力・処理・保存・外部連携などの制作タスクへ分解する入口に立つ。

対応する講義日:

- 6日目
- 7日目

学習目標:

- 身近な困りごとや興味からアプリ案を考えられる
- 誰の、どんな場面の、どんな困りごとを助けるアプリか説明できる
- 作りたいアプリを、画面・入力・処理・保存・外部連携に分解できる
- 最初に作るべき最小機能を決められる
- チーム制作の場合に、画面担当・処理担当・データ担当などの役割をイメージできる

使用場面分類:

- 予習: 向いている。作れるアプリ例を見て、発想の材料を増やす。
- 講義中: とても向いている。企画ワークやチーム制作の補助に使える。
- 復習: 向いている。自分の案を具体化し、次に作るものを整理できる。

Baseで扱うこと:

- 身近な困りごとからアプリ案を出す
- 「誰が使うか」「いつ使うか」「何が楽になるか」を整理する
- 似たアプリを観察し、必要な画面や機能を考える
- 最小限作るべき機能を1つ決める

Challengeで扱うこと:

- 企画を複数案出して比較する
- ユーザーの行動フローを考える
- 必要な画面一覧を作る
- 必要な入力項目と保存データを考える
- AI/APIを活用した追加機能を考える
- チーム制作のタスク分解を行う

Createモードへの接続:

- Createモードそのものに接続する中心コース。
- 企画ができたら、フロント特化、バックエンド特化、フルスタック、AI/API特化などの制作テーマへ誘導する。
- Createモードでは、関連するBase/Challengeミッションの達成状況を推奨条件として表示する。

## 優先度

最初に教材化する優先度は次の順がよい。

1. Webアプリの全体像を知る
2. Flaskでページを表示する
3. HTML/CSSで画面を作る
4. PythonでWebの入力を扱う
5. データを保存して使う
6. APIとAIを使う
7. ユーザー機能を作る
8. 自分のアプリを企画する

理由:

- 初学者には最初に全体像が必要
- 画面が表示される体験は達成感を作りやすい
- 入力とDBを学ぶとWebアプリらしさが一気に増える
- 認証は重要だが、初学者には概念負荷が高いため後ろでもよい
- API/AIは興味を引きやすく、Createモードへの橋渡しとして強い
- 企画はCreateモードと強く結びつくため、通常学習の最後または制作前に扱う
