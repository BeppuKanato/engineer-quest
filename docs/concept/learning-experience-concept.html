学習体験コンセプト

目的

Engineer Quest は、Webアプリ開発への心理的ハードルを下げるための学習補助アプリとして設計する。

主な目的は次の通り。

  • 授業内容の理解を促進する
  • 学習の方向性を示す
  • 「自分でも何か作れそう」という感覚を持ってもらう
  • Webエンジニアを就職先や将来の選択肢として意識してもらう
  • 最終課題や自由制作で、自分の作りたいものを考えるための材料を増やす

単に講義内容をテストするのではなく、負担なく楽しくWebアプリ開発に良い印象を持ってもらうことを重視する。

対象者

想定する対象者は、情報工学科、情報通信系、システムマネジメント系などの大学2年生以上の学生。

前提として、PythonやWebアプリ開発は初見の学生が多い。情報系の学生ではあるが、Webアプリの仕組み、HTML/CSS、Flask、サーバ起動、ファイル構成などには不慣れな状態を想定する。

モチベーションは大きく次の2つに分かれる。

  • 単位取得が主目的
  • アプリを作ることに少し興味がある

そのため、強い自発性や高い前提知識を要求しすぎない設計にする。

ペルソナ

1. 単位目的・低モチベーション型

最小限の負担で授業についていきたい学生。

特徴:

  • PythonやWebアプリ開発に自信がない
  • 何をすればよいか明確なら取り組める
  • 自由度が高すぎると止まりやすい
  • エラーや不明点が続くと離脱しやすい

刺さる体験:

  • 短時間で終わる
  • 正解しやすい
  • 講義で出る単語を事前に見たことがある状態になる
  • 「今日の最低ライン」を完了できる

向く問題形式:

  • 選択式
  • 見比べ
  • 短い穴埋め
  • 直前に見た内容の確認

避けたい問題:

  • 空欄から長いコードを書く
  • 複数ファイルを同時に考える
  • 正解が曖昧な課題

2. ちょっと興味あり型

自分でもアプリを作れるかもしれない、と思えると前向きになる学生。

特徴:

  • プログラミングへの苦手意識は強くない
  • Webアプリ開発は初めて
  • 画面が変わる、自分の内容に変えられる体験を楽しめる
  • 自分の最終課題や制作物とのつながりが見えると伸びる

刺さる体験:

  • 自分の文章やテーマに変えられる
  • 完成物が画面に見える
  • 作れる部品が増えていく
  • 自分のアプリ案に使える知識だと分かる

向く問題形式:

  • 小さいコード修正
  • UI部品の追加
  • 既存コードの一部改造
  • 短い確認テスト

3. 進度が早い発展型

講義中に早く終わり、追加課題や発展に取り組みたい学生。

特徴:

  • Python経験がある、または自分で調べながら進められる
  • 全員向けの確認だけでは退屈になりやすい
  • 実用的な機能や自由改造に興味を持ちやすい

刺さる体験:

  • 任意チャレンジ
  • 発展課題
  • 複数ファイルを使う課題
  • 自由制作やAIレビュー

向く問題形式:

  • 発展ミッション
  • 応用的な確認テスト
  • Createモード
  • AIレビュー型の自由制作

使用場面

1. 講義前の予習

講義で出る単語、操作、考え方を先に見て、初見の不安を下げる。

重視すること:

  • 用語への抵抗を減らす
  • 講義中に聞く内容を事前に見たことがある状態にする
  • 正解できることより、見慣れることを重視する

向く問題:

  • 用語確認
  • ファイルの役割確認
  • 画面とコードの見比べ
  • 短い選択式

2. 講義時間中の暇な時間

講義の進度差を吸収する。

早く終わった学生には発展課題を、詰まっている学生には基礎確認を提供する。

重視すること:

  • 早く終わった学生が退屈しない
  • つまずいた学生が基礎に戻れる
  • 講義の流れを邪魔しない

向く問題:

  • 任意の追加チャレンジ
  • よくあるつまずき確認
  • 操作の意味を確認する短い問題

3. 講義後の復習

スライド通りに操作した内容の意味を再確認する。

重視すること:

  • 何を作ったのか分かる
  • なぜそのファイルを触ったのか分かる
  • 次回の内容につながる最低限の理解を残す

向く問題:

  • 講義で触ったコードの再現
  • ファイル構成の確認
  • お手本再現型の確認テスト

4. 最終課題・自由制作前

自分でアプリを考えるための材料を増やす。

できることの知識不足によって、発想が狭まらないようにする。

重視すること:

  • こういう機能が作れる、という見通しを持たせる
  • 自分のアイデアに使える技術を知る
  • 具体的な制作テンプレートや発想の入口を用意する

学習時間と粒度

1日の推奨学習時間は 20〜25分程度を目安にする。

ただし、PCブラウザで20分以上連続して取り組ませると負担が大きくなる可能性があるため、次の粒度を目安にする。

  • 1活動: 30秒〜2分
  • 1レッスン: 3〜5分
  • 1ミッション: 8〜12分
  • 1日の推奨: 2ミッション程度

途中離脱しても損しないよう、小さい単位で達成感を得られる設計にする。

現在の学習フローの位置づけ

ミッション確認テスト

ミッション確認テストは「お手本再現型」として扱う。

役割:

  • 基礎概念の定着
  • 講義内容の復習
  • 小さな達成感の提供
  • 難易度別チャレンジ
  • 自由制作前の型作り

合格条件:

  • ユーザーコードと answerCode の全文一致
  • クライアント側で即時確認する
  • 進捗更新前にサーバ側でも再判定する

この方式は自由制作の代替ではなく、型を身につけるための明確なクリア型問題として扱う。

easy / normal / hard の意味

easy / normal / hard は自由度の違いではなく、入力量・再現量の違いとして扱う。

  • easy: ほぼ完成コードから重要部分だけ埋める
  • normal: 骨組みから完成させる
  • hard: お手本を思い出して再現する

ミッション完了条件は、いずれか1難易度の合格で十分とする。

他難易度のクリアは、追加達成、称号、挑戦として扱う。

Createモード

完全自由制作やAIレビューは、ミッション確認テストとは別の Create モードとして扱う。

Createモードでは、正解が1つではない制作を扱う。AIは採点者というより、レビューや改善提案を行う支援者として位置づける。

開放方針:

  • 完全ロックではなく、ソフトロックを基本とする
  • Createモード自体は見える状態にする
  • 関連ミッションの easy クリアなどを推奨条件として表示する
  • 未クリアでも入れるが、「先にこのミッションをやると作りやすい」と案内する
  • 高度なテンプレートだけは条件付き開放を検討する

ゲーミフィケーション方針

競争よりも「できた感」を重視する。

相性が良い要素:

  • 今日の達成
  • 連続学習
  • ミッション完了
  • 難易度別クリア
  • 作れるようになった部品リスト
  • バッジ
  • 最終課題に使える技術カードの解放

相性が悪い可能性がある要素:

  • 細かい正答率ランキング
  • 失敗回数の強調
  • 作業速度の競争
  • hard を必須に見せる設計

目標は、低モチベーションの学生には安心して進める体験を、興味がある学生や進度が早い学生には追加で挑戦できる体験を提供すること。

今後の問題設計で守ること

  • 1活動では1つの判断だけを扱う
  • 初見で解けない問題を出さない
  • 確認テストで出すコードは、事前のレッスンで見た・触った・意味を確認したものにする
  • 完全一致型の問題では、理不尽な空白差分や説明不足を避ける
  • 予習では「正解できる」より「見たことがある」を重視する
  • 復習では「なぜその操作をしたのか」を確認する
  • 発展は任意にし、必須の負担にしない
