# バブルソート アプリ統合（カード・実績のシードと単元登録）（Issue #236）

目的: バブルソート単元（フェーズ1〜7は #227〜#233、視覚デバッグは #234、単元接続は #235）をアプリ全体へ統合し、コレクション・実績で BFS と同等に扱えるようにする。マスタデータの正本はバブルソート基準データ §5。最終確認日: 2026-11-07。

## 実装内容

- コースシード: 既存の `course-algorithm-bubble-sort-v2` に接続する方針（基準 §5）のため、新規コース追加は行わない。コースシード自体に変更はない。
- 知識カード（`back/prisma/seedData/knowledgeCardSeed.ts`）: 基準 §5 の3枚を追加。
  - 安定なソート（RARE、フェーズ2 `bubble-sort-execution` で配布）
  - 値の交換（COMMON、フェーズ5 `bubble-sort-code-check` で配布）
  - 計算量（EPIC、フェーズ7 `bubble-sort-implementation` で配布）
  - 配布スケジュールは、棒倒し法の統合（#215）と同じく BFS と同一のテーブル表（15テーブル、平均約6割出現）を単元ごとに生成する形へ一般化した（`buildCardPhaseSchedule`）。BFS 分のスケジュール ID・内容は変更していない（後述の検証でダンプ一致を確認）。
- 実績（`back/prisma/seedData/achievementSeed.ts`）: BFS と同じ構成の6件を追加。単元クリア（`ach-unit-bubble-sort-complete`）、フェーズ7クリア、確認問題の初回全問正解、応用問題の初回満点、ノーヒントクリア、カードコンプリート（`ach-bubble-sort-card-complete`）。
- 検証の汎用化（`back/src/scripts/verifyCollectionMasterData.ts`）: #215 と同じ形で、「BFS の3枚だけが現行プール」などの BFS 前提を、カードを持つ単元ごとの検証へ一般化した（カードは単元ごとにスロットと対応、スケジュール表は単元ごとに15テーブル、フェーズキーは実績のコース範囲で照合）。
- フロント側の登録は #235 系統で完了済みであり、本 PR での追加作業はない。単元サムネイル（`front/src/app/courses/component/courseThumbnail.tsx` の `BubbleSortFigure`）、unitRegistry 登録、単品プレビュー登録はいずれも既存分で足りることを確認した。

## 判断と留保

- カードの sortOrder は、全体の表示順として BFS の 1〜3、棒倒し法（#215）の 4〜6 に続く 7〜9 を割り当てた（本ブランチ単体では 4〜6 が欠番になるが、重複はなく表示順も壊れない）。実績の sortOrder も同様に、BFS の各値＋2（112 / 322 / 332 / 342 / 352 / 412）とし、#215 の＋1 と重ならないようにした。
- カードの label・本文（description / connection / useCase）と実績の説明文は、基準 §5 の「内容」欄を正本とし、BFS カードの文体に合わせて書き起こした。文言の最終確認はレビューに委ねる。
- 実績のうち全体カウント系（`ach-unit-count` の [1, 3, 7] 等）は既存実績の条件であり、本 PR では変更していない（#215 と同じ判断）。なお `ach-knowledge` の最終段階はカード総数から自動で決まるため、6枚に追随する。

## DB 適用の要否

- **マージ後に開発 DB へのシード再実行が必要**。CD はコードのみをデプロイし、シードは自動適用されない。本 PR のコードだけでは、バブルソートのカード・実績は付与されない。シードは既存マスタの upsert と新規分の追加であり、BFS 分の既存データは変更しない（`verify:seed-preservation` の保持ポリシーの対象範囲内）。

3. 単元完了時に「バブルソートを修得した」などの実績が解放されることを確認する。
4. 単元概要画面の実績プレビューにバブルソートの実績が並ぶことを確認する。
