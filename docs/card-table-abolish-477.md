# 知識カードの固定配布と未所持分の救済（D2）

- 目的: ユーザーのランダムな配布番号でカードが永続的に欠落する方式を廃止し、全員が21枚を取得できるようにする。
- 適用範囲: バックエンドの配布判定、スケジュールseed、登録時割当、コレクション取得時の救済。カードの内容・フロント・出現演出は変更しない。
- 最終確認日: 2026-11-19。
- 正本: [Issue #477](https://github.com/BeppuKanato/engineer-quest/issues/477)、[開発ガイド](../AGENTS.md)、現在のPrisma schemaと実行コード。
- 対象実装コミット: `85873730`。
- 状態: 実装・自動検証済み。seedは全環境で未適用。migration不要。

## 配布

7単元のフェーズ2・5・7に、従来のCARD_PHASE_SLOTSどおり1枚ずつ固定で配布する。スケジュールseedは189行の番号別生成を廃止し、各単元3行の21行だけを生成する。コースバージョンはcourseSeedから取得し、バブルソートのバージョン2にも一致させる。

付与時にはユーザーの番号を一切参照しない。新しい共通スケジュールを表す予約値 `FIXED_CARD_SCHEDULE = 0` を、単元ID・現在のコースバージョン・フェーズキーとともに明示的に問い合わせる。旧1〜15の行は残っていても選ばない。

付与はUserKnowledgeCardのuserId＋knowledgeCardId一意制約とcreateMany(skipDuplicates:true)で行う。挿入件数0なら獲得カードを返さず、すでに所持していたカードを二重付与・再提示しない。通常のフェーズ保存と同じトランザクション内にある付与判定だけを変更し、進捗・評価証拠の保存方式は変更していない。

## 既存ユーザーの救済

getCollectionByUserの先頭でrestoreCompletedPhaseCardsを実行する。

1. 本人のCOMPLETEDフェーズと現在のコースバージョンを読む。
2. 共通番号0・一致する単元／バージョン／フェーズ・公開カードのスケジュールだけを取得する。
3. カードIDを一意化し、skipDuplicatesで不足分だけ挿入する。再取得・同時救済・通常完了との競合でも重複しない。
4. 追加があった場合は既存の実績評価器を呼び、全カード収集等の実績を再評価してからコレクションを返す。

救済はカード所有と、それに伴う実績の再評価だけを行う。PhaseLearningProgress、UnitLearningProgress、summary.assessmentEvidence、学習イベント、実験割当、フィードバック生成には書き込まない。未完了のフェーズや他人の進捗は使わない。救済カードはコレクションに表示し、解除演出を新設・変更しない。

## 旧項目を残す理由

- User.knowledgeCardTableNumberは登録時のランダム指定を削除し、既定値1のみを使う。既存ユーザーの値は更新しない。
- この列は現在のauth APIレスポンスとfront/src/api/auth.api.tsの必須契約に残っているため、互換性を保って段階移行する目的で保持した。新旧値は配布には一切使わない。学習サービスは番号なしでも呼べる。
- KnowledgeCardPhaseScheduleEntry.tableNumberと複合uniqueも保持する。旧行を残すseed:preserve移行と、旧アプリのデプロイ期間中の互換性のためであり、新しい配布では0固定の移行用識別子としてのみ使う。
- Prisma schemaの変更は上記の説明コメントだけ。schema同士のmigrate diffは空であり、migrationは追加しない。旧列をdropする破壊的整理は今回不要。

## 検証

- back typecheck／lint／build／verify:static成功。
- staticにはverify:seed-preservation、verify:collections、verify:dfs-learningを含む。新設verify:fixed-card-distributionも追加した。
- 新設検証では旧番号1〜15の各ユーザーに全21配布フェーズと再完了を実行し、同じ21枚・重複なしを確認。番号なしユーザーも同じカードを取得できる。
- 誤ったカードを指す旧番号15のスケジュールを同居させても共通行だけが選ばれる。実サービスの問い合わせ条件で0固定を確認した。
- 完了済み・1枚所持のユーザーを同時救済し、合計20枚の追加で21枚へ揃い、再救済では0枚。未完了／進捗なしでは0枚。通常完了と救済の競合でも新規付与の報告は1回だけ。
- 救済前後でstatus・completedAt・summaryのdeep equalityを確認。コレクション取得からの救済と、カード追加時だけの実績再評価を確認。
- 既存DFS統合検証は、旧番号6でもフェーズ2のカードを取得する期待へ変更した。既存の進捗保存・カード再付与防止・実績条件も通る。
- 新規登録のcreateデータにランダム番号が含まれないことを検証。
- developのknowledgeCardSeedと全21枚の全項目をdeep equalityで比較し、一致。カードID、文章、レアリティ等は変更していない。
- prisma validate成功。オフラインmigrate diffはempty migration。
- 未実施: 実DBへのseed適用、実PostgreSQLでの救済／競合、実サーバー認証E2E。検証はメモリアダプターを用い、DB・外部サービスへ接続していない。
- フロント／画面構成・表示文言・演出に変更なし。UIスクリーンショットは対象外。

## 適用手順

**DBへのseed再適用が必要。全環境で未適用。migrationは不要。** 新しいコードだけを先にデプロイすると番号0の固定スケジュールが存在せず、カードを付与・救済できない。

1. 対象がlocal／dev／productionのどれかを明示し、接続先を確認する。資格情報は出力しない。
2. このPRのcheckoutでbackの `npm run seed:preserve` を先に実行する。通常seedを使わず、既存の進捗・実験割当・カード所有を維持する。
3. 番号0のスケジュールが21件あり、各コースのバージョンとフェーズ2／5／7のカードに一致することを確認する。バブルソートはバージョン2。
4. バックエンドをデプロイする。旧番号の行はそのままでよく、削除手順は不要。固定行のIDは `schedule-<単元>-v<version>-fixed-<phaseKey>`。
5. 既存ユーザーでコレクションを開くと、完了済みフェーズ分を救済する。新規ユーザーではフェーズ完了ごとに同じカードを取得する。繰り返し開いて重複・元の進捗変更がないことを確認する。

旧アプリは番号1〜15、新アプリは0を読むため、保持seedの先行適用中も共存できる。旧189行が残る場合、スケジュールの物理的な総数は210行になるが、利用される固定対応は21行だけである。カードマスターは常に同じ21枚。救済済み所有をコードの切り戻し時に自動削除しない。
