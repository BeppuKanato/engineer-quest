# 学習体験の再設計：全体仕様（2026-11）

目的: ミッション駆動への転換（2026-11-22 決定）と、それに伴う廃止・置換・実験前スコープを、実装者が迷わない形で定める。
適用範囲: 新フロー（7フェーズ単元）の学習体験全体。従来フロー（Course / Mission / Activity）には適用しない。
最終確認日: 2026-11-24。
状態: **正本（実装予定）**。確定日: 2026-11-22〜24（設計サンドボックス `engineer-quest-ui-brushup` での画面確定を含む）。
本書は、ミッション駆動への転換と、それに伴う廃止・置換の全体像を定める。画面ごとの提示仕様は [redesign-ui-policy-2026-11.md](redesign-ui-policy-2026-11.md) を正本とし、画面単位の実装仕様は各 Issue の仕様文書（`*-<Issue番号>.md`）に従う。本書と競合する旧文書（大目標系 #365〜#370、`unit-final-result-150.md` の提示決定、`feedback-dedicated-screen-369.md` の単独画面形）は、本書を優先する。

## 1. 根本の問題と方向

- 根本の問題は「課題先行」でないこと：現行は「アルゴリズムを学ぶ場所」であり、「解決したい課題があるから学ぶ」構造になっていない。学習フロー自体にゲームがなく、ゲーム要素はすべて学習の外側の報酬であり、「作る」は主流から切断されている。
- 方向：単元をミッション駆動にする。7フェーズの教材構造そのものは維持する（良い教材をゲーム性のために壊さない）。狙いは「ゲームとして遊んだ結果、アルゴリズムの使い方を理解できる」こと。

## 2. 構造の決定

### 2.1 2層構造

- **第1層（習得）**：単元の入口で単元ミッション（課題）を提示する（提示のみ。学習前の挑戦や初学者へのコード記述は強制しない）。中間は既存フェーズ1〜6。最後は、提示されたミッションの仕様（入出力・制約・成功条件）に対する**自由実装**で達成する。フェーズ7の「指定関数の穴埋め」は自由実装に置き換える。
- **第2層（活用）**：単元修了後の発展ミッション（使うアルゴリズムは事前に決まっていない）。ボス課題の概念は 2026-11-25 に畳んだ：本来の役割（単元より上に立つ、学習者が目標とする課題）は単元ミッションが、スコアと自己ベストによる再挑戦は発展ミッションが引き継いだため、独立した役割が残らなかった。
- 任意フェーズを置く：1.5「予測・実験」（実験型）、6.5「実装の橋渡し」（支援型）。任意であり必須にしない。6段階の進捗分母には数えない。

### 2.2 グルーピングは課題軸

- 単元のグループは「同じ課題への別解法」で編成する：グラフ探索＝BFS・DFS／配列の検索＝二分探索／迷路生成＝穴掘り法・棒倒し法／並び替え＝バブルソート（他解法は単元化された時点で追加）／貪欲法は表示カテゴリを「最適化問題」とし、すべて課題軸に揃える。
- グルーピングは分類ではなく内容そのもの（同じ課題への別解法であること自体が教材）として扱う。

### 2.3 大目標の撤去と、目標の再定義

- 既存の大目標システム（#365〜#370 で実装した LLM ペルソナによる目標提案・進捗・称賛の統合）は、学習者実験の**前に撤去**する。理由：ペルソナ生成の運用像が成立せず、HEXAD 効果が検証不能なまま防御側の論点になるため。
- HEXAD が入る場所はフィードバックの選択・合成のみに限定する（実験で検証可能な唯一の入口）。
- 「目標」は学習者側の語として再定義する：学習者がボタンで立てる。単元ミッションを自分の目標として採用する形と、発展ミッションでスコアの目標段階（ティア）を選ぶ形（自由入力ではなく、システムが既定値を提案するティア選択）。目標は重ね付けであり、ゲートにはしない。

### 2.4 「作る」の発展ミッションへの統合

- 独立セクションとしての「作る」は廃止し、発展ミッションに統合する：旧作るクエスト（テーマ付き実装課題＋得点）が発展ミッションに、作業画面が挑戦画面になる。作品は /my-works に残し、共有・掲示板投稿もミッション側へ移す。知識カードの行き先データは発展ミッションへ付け替える。

## 3. フェーズ7（自由実装）の仕様

- 提示：ミッションの仕様（入出力形式・制約・成功条件）を満たすことだけを求め、関数シグネチャは固定しない。
- 判定：網羅的なテストケース＋プロパティベースの検査で行う（決定済み）。
- 支援は設計されたエスカレーションとする：ヒント → 橋渡し（6.5）→ 穴埋め量の増加 → ワークド例（模範解答）。自由実装のままでは「詰まっても進める」が壊れるため、行き詰まりの検出（テスト失敗の継続、実行回数など）に応じたトリガー式の提示を基本とし、いきなり答えを見せない。
- 完了の定義が変わるため、単元完了の判定・評価エビデンス・フェーズ7連動の実績は、データ側の設計として合わせて変更する。
- 支援の2層構造と「答えの解放バルブ」（ステージ2で実装）：支援は次の2層に分ける。
  - 第1層＝理解支援：ヒント、橋渡し（6.5）、AI相談。常時使え、学習者が必要な分だけ選ぶ選択式とする。利用回数で罰しない。
  - 第2層＝答えの解放：解法例（お手本プログラム）の表示だけは、最終チャレンジ（フェーズ7）のテスト失敗が1試行内で累積して閾値に達したときに開く「進行保証の弁」とする。詰まったまま先へ進めなくなる事態を避けるための仕組みであり、理解支援とは性質が違うため、ここだけを失敗回数で開く。失敗回数は試行内で累積し、画面を閉じても消えない（下書きと同じ流儀で永続化）。完了するとその試行はリセットされる。
  - 閾値は仮置きで `x = 5` とする（2026-11-28 時点）。定数はフロント共通モジュール `front/src/features/learning/implementation/answerReveal.ts` の `SOLUTION_REVEAL_FAILURE_THRESHOLD` の1か所に集約し、全単元のプレビューがそれを参照する。値は学習者実験の観察で見直す前提であり、確定値ではない。
  - 解法例は既存のお手本データを表示に使うだけであり、内容は変えない。お手本データが存在しない単元（バブルソート、棒倒し法、穴掘り法、貪欲法、および関数形のダイクストラ／Aスター）はバルブ対象外とする。
  - 試行フラグの記録：フェーズ7の完了ごとに、フェーズ進捗 summary の `clears` 配列へ1件追記する（上限20件、古いものから落とす）。1件は `completedAt`（完了時刻）、`viewedSolution`（解法例を見たか）、`usedAiConsultation`（試行開始以降にその単元でAI相談を使ったか。ステージ1の相談履歴APIで判定）、`usedHint`（ヒントを使ったか）、`inputLevel`（開始時に選んだレベル）を持つ。LearningEvent `implementation_complete` の payload にも同じフラグを含める。この記録形式が、答えを見ずに再挑戦して通した場合の実績判定（ステージ4）の正本になる。再完了でも追記される。
- 実績の再構成（ステージ4で実装、2026-11-28 Kanato 決定）：単元ごとの実績は次の4種とする。既存の実績 id は変えない（付与済みの記録を孤児化させないため、変えるのはタイトル・説明・条件評価だけ）。
  - コモン「◯◯を修得した」（UNIT_COMPLETE）：単元完了で付く。
  - レア「最終ミッションクリア」（PHASE_COMPLETED、旧「自分で実装クリア」から改名）：フェーズ7（最終ミッション）の完了で付く。選んだ書き方レベルは不問。
  - エピック「ノーヒントクリア」（PHASE_NO_HINT_COMPLETE）：フェーズ7をヒント未使用で完了。AI への相談もヒントに数える（AI 相談未使用も条件に含める）。
  - エピック「ほぼ自力でノーヒントクリア」（PHASE_FULL_NO_HINT_COMPLETE、新設）：「全部書く」（inputLevel="full"）で始めて、ヒント・AI 相談なしで完了。
  - 答えを見たクリアの扱い：`clears` がある単元では、その単元の実績（上記4種すべて）は「解法例を見ていない clear（viewedSolution=false）」が存在する場合にだけ付く。単元数（UNIT_COMPLETED_COUNT）と系コンプリート（UNIT_GROUP_COMPLETE）も、解法例を見たクリアだけの単元を数えない。`clears` が無い単元・履歴は従来判定のまま（ヒント判定は hintUsage へフォールバック）とし、新設のエピックだけは判定材料が無いため獲得できない。評価は clear 単位であり、後から解法例を見ずに再完了すれば次回評価で通常どおり付く。単元の進行上の完了（発展ミッションの解放など実績以外の仕組み）には影響させない。付与済みの実績は再判定しないため剥奪も起きない。
- フィードバック入力への AI 相談ログの組み込み（ステージ3で実装）：これは **Kanato の 2026-11-28 の明示指示による入力仕様の変更**であり、§10.2 凍結範囲への例外として、変更は「入力の組み立て」に限る。Stage 1 / Stage 2 の生成ロジック・プロンプト文には一切触らない。
  - 対象は単元フィードバック（フェーズ／単元の2種）だけであり、「作る」経路には入れない。対象単元について、生成時点（cutoff）以前の当該ユーザーの相談ログを、フィードバック入力の `learning.aiConsultations` として含める。
  - 中身は要約ではなく発言の記録とする：各件は `phaseKey`（相談時のフェーズ）、`createdAt`（時刻）、`userMessage`（学習者の発言）、`assistantMessage`（相談相手の応答）、`blocked`（解法コードらしい応答を差し替えたか）を持つ。
  - 打ち切り規則（定数は `back/src/service/feedbackConsultationInput.ts` が正本）：直近20件まで、かつ各件の発言＋応答の合計で12,000文字まで。超過時は新しい方を優先し、残した分は時系列順に並べる。最新の1件だけは文字数上限を超えても残す。打ち切りの有無は `totalCount`（総件数）・`includedCount`（含めた件数）・`truncated` で入力側に残す。
  - 相談が無い単元・ユーザーでは `aiConsultations` フィールド自体を付けず、入力は従来と完全に同一になる。保存済み入力の変換（`prepareSavedFeedbackInput`）でも、フィールドがある場合は保持し、無い入力には付けない。
  - 位置づけ：AI 相談は全条件で常駐する第1層の理解支援機能であり、ログの有無は学習者の行動による。条件によって入力の形が変わるものではない（相談が無ければ全条件で従来どおり、あれば全条件で同じ形で入る）。
- 実装形（2026-11-25、設計サンドボックスで実装し確定）：学習者は関数ではなくプログラムを書く（標準入出力、競技プログラミングと同じ形式。入力＝標準入力から1行、出力＝並び替えた結果を1行）。入口の量選択ゲートはプログラム形のテンプレートで残し（レベル制は存続、2026-11-25 Kanato 決定）、問題文は作業画面の「問題」タブにも常駐させる。判定はケースごとに入力を差し替えて実行し標準出力を比べる（名前つきテスト＋自動チェック：小さい並びの網羅と、種を固定した乱数の性質ベース検査を1枠に集約）。書き方レベル（骨格・穴埋め）は削除せず、任意フェーズ6.5「実装の橋渡し」の中身としてプログラムの形で残す：通常は自由に書き、テストに2回つまずいたら橋渡しを提案し、お手本は橋渡しの中でのみ（つまずきが続いたとき）見せる。同日先行した「関数名だけ自由にする」形は Kanato が却下（自由実装とは言えないため）。旧・関数形の画面はサンドボックスの別ページに保存。

## 4. フィードバックの仕様（生成側と提示側の分離）

- 原則：文章の「意味」と「提示」を分離する。UI は文章の役割（スロット）だけを見て提示を決め、LLM の本文をフロントで解析しない。提示は実験条件間で均一にし、本文はそのまま出す（HEXAD 比較を汚さない）。
- 本文の構造は praise / strength / improvement / nextGoal / nextStep（+理由・行動）とする。人格への称賛はしない（Hattie の注意）。
- 注意：フィードバック生成（`back/src/service/` の feedbackV1/V2 等）は AGENTS.md §10.2 の凍結範囲である。本節の生成側の改修（見出しフィールドの契約、シーン参照の付与）は、凍結への例外として扱い、対象を明記した専用の Issue を立ててから変更する。提示側のみの変更は凍結の対象外。
- **見出しフィールドは生成側の契約**とする：各セクションは「常時読まれる要約層」として見出しを持ち、見出しは対象＋行動を含む自己完結した文にする（裸の感想文にしない）。強み・改善点の見出しは、学習記録（ログ）と照合できる内容にする。
- ログ連動シーン（学習者が直した問題の場面の再現）は、LLM 本文と照合せず、**コードが記録から組み立てる**。対象の選択規則は「初回に間違えて最終的に直した問題がちょうど1問のとき」。そのためフィードバック結果には、コード由来のシーン参照（questionId と試行番号）を持たせる（生成側の改修事項）。
- 統合フィードバック画面（フェーズ3・5）は、完了保存が 409 を返した場合に**自動で次へ進めない**（学習者を置き去りにしない）。
- 要約層（見出しのみ表示・本文は開閉）が既定であることと、詳細を開いた事実はログに残す。

## 5. 実験前スコープと対象外

- 実験前（〜2027-01-05 指導教員提出）に入れるのは：第1層×実験3単元（BFS・DFS・二分探索）、結果／フィードバック提示の統一（redesign-ui-policy）、大目標の撤去。
- 第2層（発展ミッション）は実験の対象外とし、画面も後回しにする。導線の置き場は発展ミッションができてから決める（2026-11-25）。
- 実績50件表・EXP／ランク表示の撤去・カード表の廃止・1日1問の復習など、2026-11-19 の強化計画で決定済みの事項は、本書の範囲外（各 Issue の仕様文書が正本）。

## 6. 実アプリ移植時の修正リスト（設計サンドボックスで確定した修正）

1. フェーズ1の最初のキャプションに、ミッション場面へつなぐ半文を入れる（全単元）。ストーリー提示の直後に学習世界へ切り替わる際の接続がないため。
2. 統合フィードバックは保存 409 で自動スキップしない（§4）。
3. フェーズ7の結果ボタンは、完了保存が終わるまで無効化し、保存中であることを表示する。
4. デプロイはコードのみを運ぶ。seed データの変更は別途 `seed:preserve` の手作業が必要であり、「マージ済み＝本番反映」と扱わない。
