# フロントエンド共通化・移行作業計画

- 目的: Bulletproof React採用方針に沿って重複と依存の逆転を減らし、学習画面の表示・操作・状態遷移を継続して揃えられる構成へ移す。
- 適用範囲: `front/` の構成、共通UI、学習フロー、関連する既存検証。バックエンド・DB・教材内容・モデル変更は対象外。
- 状態: 計画のみ。以下の作業は未着手。本書の作成でコードの移行は開始しない。
- 最終確認日: 2026-11-12。
- 現状確認: Engineer Quest `develop` `3de83c8597f21301ee005e1bb10975659cb9e240` と、文書採用ブランチ上の作業ツリー。
- 基準: [フロントエンド採用方針](frontend-architecture.md)、[実装ルール](development-rules.md)、[プレイヤーUI定義](concept/learning-player-ui.md)、[アプリUI/UX方針](concept/app-ui-ux-guideline.md)。
- 外部参考: [取り込み済みの公式Bulletproof React](references/bulletproof-react/README.md)。構成・UI分割・状態管理・検証の原則を参照する。以下の移行順・部品名・境界は本プロジェクト向けの計画であり、公式が規定した手順ではない。

## 1. 進め方と変更しない契約

最初に画面差を記録し、教材の枠を一つの画面で検証する。その後、表示を変えない配置整理、単元ごとの画面制御の統合、問題・実装画面の共通化へ進む。通常ページとapp層の整理は、責務を棚卸ししてから行う。

- ファイル移動だけのPRと、見た目・挙動を変更するPRを分ける。
- 一度に7単元を書き換えない。代表単元を一つ完了し、差分と確認結果を使って横展開する。
- URL、API、単元・フェーズ・設問ID、初回と直近の回答の区別、採点、ソフトゲート、保存キー、報酬、フィードバック条件、観測イベントは維持する。
- 一度開いたフェーズのマウント維持、再生位置・回答・入力途中の保持を壊さない。部品の移動に合わせてReactのkeyやコンポーネントの型を不用意に変えない。
- 新しい全体ストア、UIライブラリ、データ取得ライブラリは導入しない。必要性が出た場合は別の設計判断とする。
- 図・教材内容・Python実行・トレースの意味は固有部分に残す。似たファイル名だけを理由に処理を共通化しない。
- 共通化で違いが発覚した場合は「仕様差／修正漏れ／判断待ち」を分類し、元の挙動を維持するか、独立した変更として扱う。

## 2. 全体の順番

各項目はIssue相当の作業単位。PRの数は上限ではなく目安であり、大きい場合は表中の単位で分割する。

| 順 | 作業 | 先行条件 | PRの分け方 | リスク |
| --- | --- | --- | --- | --- |
| M00 | 現状の依存・表示・動作を記録 | なし | 棚卸しと基準記録で1件 | 低 |
| M01 | 教材レイアウトの契約と代表画面 | M00 | 共通枠抽出／表示改善を分ける | 中 |
| M02 | 学習共通部品を単元配下から分離 | M01 | 盤面・結果・共通型を分割して移動 | 中 |
| M03 | 残り5単元を共通画面制御へ移行 | M02 | 1単元1件、必要な基盤変更は先行PR | 高 |
| M04 | 確認問題・応用問題の枠と完了通知 | M03 | コード確認→動き確認→応用問題の順 | 中〜高 |
| M05 | 図とコードの配置・復習枠を共通化 | M02、M04 | 配置抽出／表示調整を分ける | 中 |
| M06 | 実装ワークスペースを単元から分離 | M03、M05 | BFS/DFS分離→他単元を個別移行 | 高 |
| M07 | app配下の共通基盤・機能接続を整理 | M00、学習側の契約が安定した時点 | セッション／音／ヘッダー／フィードバックを分割 | 高 |
| M08 | 通常ページを機能単位へ分割 | M07 | 画面群ごとに実施 | 中 |
| M09 | 依存検査・配置統一・残存例外の整理 | 各移行の完了範囲から順次 | 検査追加／残りの移動を分ける | 中 |

M07のうち単純な共通部品移動は必要な時点で先行してよい。セッション・providerの変更はレイアウト修正へ混ぜない。M09も最後まで待たず、移行済みの範囲へ段階的に適用する。

## 3. 作業ごとの対象と完了条件

以下のソースパスは特記しない限り `front/src/` 配下。新しい部品名は移行先の提案名であり、実装済みではない。

### M00: 基準・依存関係の記録

- 対象: `app/component/`、`features/learning/app/`、各単元の `unit/`・`check/`・`code-check/`・`consolidation/`・`implementation/`、`front/scripts/`。
- 成果物: 参照元と移行先の一覧、既存例外一覧、画面比較、関連するverifyの実行結果。auth・sound・feedbackの参照元も列挙する。
- 特に確認する差分: DFSの完了通知と表示、BFSの非表示プレイヤー再生、他5単元の個別制御、各単元の結果図・実績・大目標・フィードバック接続。
- 表示領域は `innerWidth/innerHeight` を記録する。実機のノート／デスクトップを優先し、比較用として1366×768、1536×864、2560×1440のCSS表示領域も使う。これらは検証用の提案値であり、画像から計測した実機viewportではない。
- スマートフォン対応の完成は本計画の約束に追加しない。ただし既存の幅800px未満・高さ640px以下の分岐を通る条件は回帰確認する。
- 完了条件: 現状で失敗する検証と未実施の実機確認が明記され、移行による差分と区別できる。基準記録だけで現状の見た目を承認済みと扱わない。

### M01: 教材レイアウトの契約と代表画面

- 対象: `unit/LearningUnitPreview.tsx`、各単元の `*UnitPreview.tsx`、`bfs/consolidation/ParsonsBoard.tsx`、`greedy-coins/consolidation/GreedyCoinsConsolidationPreview.tsx`。
- 移行先案: `features/learning/components/layouts/LearningContentLayout.tsx` と `AssessmentLayout.tsx`。必要な表示規格はlearning内のconfigへ置く。
- 最初に定義する契約: 教材の利用可能な幅・高さ、問題文と操作領域の差し込み口、縦横どちらをどの領域でスクロールさせるか、単品／組み込み／復習の違い。
- PR-A: 現在の表示を保つ枠を抽出し、貪欲法の並べ替え画面へ適用する。広い画面だけでなく短い画面も確認する。
- PR-B: 画像で確認した「横方向の間延び」「固定高のため内部スクロールと大きな余白が共存」を改善する。幅・高さの値を決める前に既存のUI正本と照合する。
- 注意: プレイヤーUI定義は教材占有率と、小さい固定最大幅を避ける方針を持つ。新しい最大幅がこれと衝突する場合、適用画面を限定するか設計文書の変更を同じPRで明示する。仮の数値を全画面へ強制しない。
- 完了条件: 代表画面でコード末尾へ到達でき、ドラッグ・上下ボタン・回答操作が使える。大画面の空きと短い画面の操作到達性を比較記録できる。実装エディタは変更しない。

### M02: 学習共通部品の配置整理

- 対象と移行先案:
  - `bfs/consolidation/ParsonsBoard.tsx`、`parsonsOrderFeedback.ts` → `learning/components/assessment/` と対応する純粋処理の配置。
  - `bfs/unit/PhaseBridgeScreen.tsx`、`UnitResultScreens.tsx`、`UnitResultCelebration.tsx` → `learning/components/results/`。BFSの結果図を既定値として使う部分は、BFS側から渡せる形にする。
  - `unit/unit.types.ts`、共通の報酬型など → `learning/types/`。図・教材文言の型がBFS配下から共有されている場合も、実際の共有範囲を確認する。
- 共通部品が `units/bfs/` へ逆向きに依存しないよう、必要な図・文言を引数で渡す。BFS/DFSで共有する図は、アルゴリズム差がない描画基盤だけを共有領域へ移す。
- 全参照元と、パスを直接読むverifyを同じPRで更新する。長期的な旧パス再exportを作らず、必要な一時互換は解消条件を記録する。
- 完了条件: 7単元の並べ替えと結果導線が従来どおり動く。単元共通部品からBFS教材への依存が解消される。画面寸法・文言・採点は移動だけのPRで変更しない。

### M03: 5単元の画面制御統合

- 基盤: 現在BFS・DFSが使う `unit/LearningUnitPreview.tsx` と `LearningUnitDefinition` を使う。新たな共通制御を二重に作らない。
- 対象順: バブルソート → 二分探索 → 貪欲法 → 棒倒し法 → 穴掘り法。バブルソートで基本形を検証し、配列・硬貨・迷路の違いを順に確認する。
- 各単元の `*UnitPreview.tsx` を、フェーズ定義・ビュー・結果図・文言を渡す薄いアダプターへ変える。
- 単元固有の `UnitResultScreens.tsx` の差分も比較する。必要な差を共通の引数へ表現してから、不要な重複を除去する。
- `firstAttemptResult`、非表示プレイヤーの動作、実績・大目標の描画口、保存待ち／失敗時の復帰、結果→フィードバック→次フェーズの経路を一覧で照合する。共通側に不足する機能は先行する小さなPRで補う。
- `useReducer` への変更が必要なら統合後の別PRにする。状態管理ライブラリの変更を混ぜない。
- 完了条件: 7単元が同じ画面制御を使用する。前フェーズへ戻っても入力・回答・再生状態が保持され、完了通知・保存・報酬・観測イベントが二重にならない。各単元で専用verifyと実ブラウザ確認が完了する。

### M04: 問題画面・完了通知の共通化

- 対象: 各単元の `check/*CheckPreview.tsx`、`code-check/*CodeCheckPreview.tsx`、`consolidation/*ConsolidationPreview.tsx`、`assessment/useAssessmentCompletion.ts`。
- 最初はバブルソートのコード確認問題で、問題文・コード・選択肢・回答後操作の配置をM01の枠へ寄せる。次に同系統の6単元へ展開する。
- DFSはコード全体の表示や横スクロールなど構造が異なる。6単元と同じ固定高へ変えるのではなく、枠の差し込み口で既存の動作を表現する。
- 完了通知は既存hookへ寄せる候補とし、初回正答の計算、証拠の形式、解き直し後の通知を比較する。二重通知防止と再完了の通知を両方確認する。
- その後、動きの確認問題と応用問題を分けて移行する。図・タップ判定・選択肢・並べ替えは個別部品を差し込む。
- 固定高320px等の変更は、枠の抽出と分けて比較する。M01の表示方針を利用し、個別に新しい数値を増やさない。
- 完了条件: 各問題種別で未回答／誤答／正答／再挑戦／次の問題／復習／結果の操作が従来どおり。問題文の読み上げ・フォーカスと空欄へのスクロールも維持する。

### M05: 図＋コードと復習領域の共通化

- 対象: 7単元の `code-mapping/*CodeMappingCanvas.tsx`、`review/LearningReviewDialog.tsx`、各単元の `trace/*TraceDialog.tsx`。
- 移行先案: `learning/components/layouts/CodeMappingLayout.tsx`。図、コード、変数表示を差し込み、領域配分とスクロールを共通側へ持たせる。
- 現在の最低620pxのコード幅、図の幅の下限、DFSの52%と他単元の48%の違いを記録してから抽出する。比率や縦並び切り替えは表示変更のPRとして扱う。
- 通常学習／復習／トレースの表示枠は共通化しても、再生内容の組み立てやトレース変換は単元固有のままにする。
- 完了条件: 実行行・図・変数表示の同期、コード末尾への到達、復習の開始ステップと閉じた後の元画面の状態が保たれる。

### M06: 実装画面の共通化

- 現状: `bfs/implementation/BfsImplementationPreview.tsx` は `ImplementationWorkspace` を公開し、DFSからも利用されている。他5単元には別の実装画面がある。
- PR-A: BFSの教材定義とworkspaceを分離し、共通部分を `learning/components/implementation/` へ置く。BFSとDFSでまず確認する。
- 続くPR: バブルソート → 二分探索 → 貪欲法 → 棒倒し法 → 穴掘り法を一つずつ接続する。既存workspaceの型が表現できない差は、外枠だけを共有するなど抽出範囲を見直す。
- 共通化候補: Monacoの外枠、実行中・実行準備、テスト／コンソール切り替え、ヒント操作、入力レベル選択、下書き保存の状態表示。
- 単元側に残すもの: Python実行条件、採点テスト、自由実行入力、図による結果表示、トレース取得・変換、教材テンプレート。
- 完了条件: 入力レベル別の下書きキー、再訪・単元切り替え・利用者切り替え、テスト中の操作抑止、ヒント使用記録、全通過後の完了通知、ランタイムの解放が保たれる。

### M07: app配下の共通基盤と機能接続

- 対象: `app/component/appHeader.tsx`、`actionButton.tsx`、`appBreadcrumbs.tsx`、`userSession.tsx`、`soundFeedback.tsx`、`feedbackV1.tsx`、`hexadRouteGuard.tsx`、`app/layout.tsx`、`learning/app/LearningScreen.tsx`。
- 移行先案: 純粋な共通UIは `components/layouts/`・`components/ui/`。Firebaseセッションと共通の音制御は機能に依存しない `lib/`・`hooks/` 等へ。機能固有の制御が混在する場合は分けてから移す。
- `AppHeader` はマスコット等の機能固有参照を持つため、単にcomponentsへ移すだけで完了にしない。共通の描画と、app側で機能を組み合わせる部分を分ける。
- フィードバック取得・候補表示・到達観測は `feedbackV1.tsx` 内で責務が分かれている。独立した `features/feedback/` とする場合、複数画面への利用を確認し、学習画面との接続はappの組み立てとコールバックで行う。大目標も同じく利用範囲を確認する。
- 既存providerの順序、認証ロード中の扱い、利用者別キャッシュ範囲を維持する。`app/providers.tsx` は必要な場合の接続点で、全状態を移す場所ではない。
- 完了条件: 移行対象featuresからの `app/component` 参照がなくなる。ログイン／ログアウト、利用者切り替え、ページ移動、音の設定、フィードバックの候補選択と到達イベントを確認する。

### M08: 通常ページを機能単位へ整理

- 対象順: コース一覧・ホーム → 履歴 → コレクション・知識カード・実績 → 掲示板 → 作る課題の一覧・詳細・実装。プロフィール・認証・HEXADも各責務へ配置する。
- `app/**/page.tsx` はURL・境界・画面の組み合わせへ絞り、機能のUIや取得制御を `features/<feature>/` へ移す。機能間の組み立てはapp層に置く。
- 現在の最大幅1440／1120／960などを調べ、一覧・詳細・文章・作業画面の必要な種類だけを `PageLayout` 等で共有する。すべて同じ幅やカードへ揃えない。
- エラー・読み込み・空状態・送信中ボタンは、意味と操作が同じ箇所から共通化する。API配置とキャッシュ方式は維持する。
- 完了条件: ルートを変えずページが開く。検索・絞り込み・権限・送信・再取得・候補到達の動作が保たれ、移行した画面群の余白と状態表示が揃う。

### M09: 依存方向の検査と残存整理

- 対象: `front/eslint.config.js`、移行済みのcomponents／features／appと、その検証。
- まず整理済みの共通領域から、共通→features/appのimportを禁止する。次に整理済みfeaturesからappへの参照を禁止する。独立feature同士の接続も対象範囲を決めて検査する。
- 未移行の例外は明示的な範囲と解消先の作業IDを持たせる。全体のルールを無効化したり、同じ例外を新規へ広げたりしない。
- `learning/units/` への単元フォルダ移動、screens/hooks/typesの整理は、責務が安定した単位で行う。全単元の一括移動と挙動変更を同じPRにしない。
- 完了条件: 計画対象の重複と旧参照が解消され、追加すると検査で検出される。残す固有コードと例外は理由が記録されている。APIや共通基盤からfeaturesへの依存も確認する。

## 4. 検証の組み合わせ

以下は今後の移行時に実行するもの。今回の計画作成で実行済みとは扱わない。コマンドは `front/` で実行する。

| 変更領域 | 主な既存検証・確認 |
| --- | --- |
| すべての実装PR | `npm run lint`、`npm run typecheck`、`npm run build`、変更対象のimport確認 |
| 学習の枠・画面制御 | `verify:learning-screens`、`verify:learning-player`、`verify:learning-rewards`、対象単元の `verify:<unit>-unit` |
| 問題画面 | 対象単元の `verify:<unit>-check`／`code-check`／`consolidation`、`verify:answer-feedback`、`verify:response-feedback` |
| 並べ替え | 7単元の `verify:<unit>-consolidation`、`verify:parsons-order-feedback`、ドラッグ・上下・回答の実操作 |
| 図＋コード・復習 | 対象単元の `verify:<unit>-code-mapping`／`trace`、`verify:learning-player`、ハイライト同期の実確認 |
| 実装画面 | 対象単元の `verify:<unit>-implementation`／`trace`、BFSは `verify:bfs-free-execution` も確認、実際のPython実行と下書き保持 |
| フィードバック接続 | `verify:feedback-candidates`、`verify:feedback-map`、`verify:learning-screens`、候補選択・到達の実確認。表示移行では実LLMを毎回呼ばずfixtureで検証する |
| 通常ページ | 該当する `verify:home-layout`／`unit-overview`／`app-breadcrumbs`／`mascot-presentation` と実画面確認 |

`<unit>` は `bfs`、`dfs`、`bubble-sort`、`binary-search`、`greedy-coins`、`wall-extension`、`maze-digging`。実行可能なコマンドの正は `front/package.json`。

既存verifyにはファイルパスやソースの断片を直接読むものがある。ファイル移動に合わせてパス・ローダーを更新するが、検証が通るように保護していた契約まで削らない。描画・操作を見ずに、文字列一致の成功だけでUI移行を完了にしない。

共通部品の移行は利用する7単元を最終確認する。各PRは対象単元＋BFS/DFSを比較し、横展開完了時に7単元を通して確認する。ブラウザや実DBを使えない場合、未実施を記録し、見た目や永続化まで完了と扱わない。

## 5. PR・切り戻し・進捗管理

- PRごとに対象作業ID、移動元／先、挙動変更の有無、利用先、検証、未実施項目、残る例外を記載する。
- 単元の統合は既存制御を削除するPR内で参照と検証を揃える。未使用の旧実装を恒久的な予備として残さない。
- 問題が出た場合は該当PRを戻せる範囲に保つ。教材ID・保存キー・APIを維持するため、コード移行の切り戻しにDB移行を要求しない。実運用の切り戻し操作は別途判断する。
