# フィードバックの学習フロー接続（Issue #202）

> 2026-11-11追記: 新フローの現行仕様（7単元の概念・回答証拠、1〜3候補、表示・計測）は [learning-feedback-402.md](learning-feedback-402.md) を参照。本書の1件推薦・従来文章構成の記述は変更当時の記録。

目的: フィードバックv1（2段階LLM生成・HEXAD条件・uptake計測）を、「作る」提出だけでなく新しい学習フロー（単元）にも接続する。設計は Issue #202 に記録した決定（2026-11-06、ユーザー承認）に従う。最終確認日: 2026-11-06。

## トリガー（提示の頻度）

単元完了のみでは参加者1人あたりの提示が1〜2件となり、uptake 率の分母が不足する。そのため提示は次の4箇所とする（単元あたり最大4回）。

- フェーズ3・5・6の結果画面：推薦範囲はフロー内の選択肢に絞る（次のフェーズへ進む／フェーズを復習する／関連カードで復習する）
- 単元最終結果：従来の広いカタログから推薦する

## バックエンド

- `feedbackV1` に種別 `phase` / `unit` を追加。イベントは進捗行ID＋完了時刻で同定し、同じフェーズ・単元を後で再完了した場合は別のイベントとして新しいフィードバックを生成する（提示の分母は完了イベント単位）。
- 学習入力はフェーズごとのサマリ（初回正解数、テスト実行回数、ヒント使用）から組み立てる。
- 行動カタログの1〜4を単元向けに読み替えた（新しい単元を始める／途中の単元を再開する／完了済み単元を復習する／単元のフェーズを復習する）。対象URLは進捗テーブルから供給する。行動IDは振り直していない。
- 行動23「次のフェーズへ進む」を追加した（フェーズ結果専用）。対象のフェーズはフロントがイベントIDで申告する。エンジンの選択スキーマの上限を23に拡張した。
- フェーズ種別は状態入力を単元まわりに限定し、生成プロンプトの量を減らした。
- 分析プロンプトの根拠IDの言及を「学習記録のID」に一般化し、プロンプト版を feedback-v1-2026-11-06 に更新した。

## 生成時間への対策

- 先行生成：フェーズ完了／単元完了の保存が終わった時点でフロントが生成開始を依頼する。結果画面の祝福と結果を読んでいる間に生成が進む。
- 入力の絞り込み：上記のとおりフェーズ種別は状態を限定する。
- 推論量（reasoning effort）の調整は、実キーでの生成時間と品質を見て別途判断する（本PRには含まない）。

## フロントエンド

- 既存の表示部品 `FeedbackV1` を結果画面に差し込む（確認フェーズの結果と単元最終のみ）。部品は種別 phase/unit に対応した。
- 実験の割当てがない利用者（409）と未完了イベント（404）ではカード自体を表示しない。生成失敗時は従来どおり警告のみで学習は続けられる。
- フェーズ内の対象（次のフェーズ・フェーズ復習）はリンク遷移ではなく学習フロー内の遷移で処理する。提示・閲覧・クリック・到達の記録は既存の観測部品が担う。

## 検証

- バック：`verify:feedback-v1` に行動23の検証（対象がある場合のみ妥当）を追加し、通過。型検査は develop とのエラーベースライン差分で新規カテゴリのエラーがないことを確認した（実判定はCI）。
- フロント：`verify:bfs-unit` に差し込み箇所と先行生成、409/404で出さない契約を固定。全 verify・lint・typecheck・build が通過する。
- DFS単元はコンテナ（#129/#130）の完成後に同じ仕組みで接続される。バックは単元非依存に作ってある。

## 確認方法

スクリーンショットは環境の都合で未取得のため、見え方はデプロイ後の実機確認に委ねる。実験割当てのあるアカウントが必要です。

1. BFSのフェーズ3の結果画面で、結果の下にフィードバック（現在の状態／次の目標／次の一歩＋行動ボタン）が出ること。割当てのないアカウントでは何も出ないこと。
2. 単元最終結果でもフィードバックが出て、行動ボタンが対象へ遷移すること。
