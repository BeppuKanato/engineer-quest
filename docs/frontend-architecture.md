# フロントエンド構成・Bulletproof React採用方針

- 目的: 機能の責務・依存方向・共通化の判断を揃え、単元や画面を追加しても表示と動作の一貫性を保つ。
- 適用範囲: `front/` の新規実装と、明示的に計画した既存コードの移行。バックエンドの構成は対象外。
- 状態: 採用方針に沿って段階移行中。完了範囲・未実施事項は[作業記録](frontend-migration-progress.md)を参照。
- 最終確認日: 2026-11-12。
- 正本: 本書、[開発ガイド](../AGENTS.md)、[実装ルール](development-rules.md)。教材内容・UIの規則は[教材指針](concept/learning-materials-guideline.md)、[プレイヤーUI定義](concept/learning-player-ui.md)、[アプリUI/UX方針](concept/app-ui-ux-guideline.md)に従う。
- 外部の基準: [Bulletproof React公式文書の固定版](references/bulletproof-react/README.md)。参照コミットは `9506629ed003a561c6627735480cce4994244bb4`。
- 現状確認の基準: Engineer Quest `develop` `3de83c8597f21301ee005e1bb10975659cb9e240`。以下の現状記述はこの時点のコード確認に基づく。

## 1. 採用の意味と優先順位

Bulletproof Reactを、機能単位の構成、依存方向、状態の配置、再利用可能なUIの設計に関する共通の参考基準として採用する。公式サンプルのコピーや、全ライブラリの導入を意味しない。

- 公式原文は `references/bulletproof-react/upstream/` に保持する。本書の補足を原文へ書き込まない。
- このプロジェクトでの具体的な判断は本書にまとめる。外部文書に書かれた推奨を、そのまま必須要件へ読み替えない。
- ユーザーの現在の指示、対象Issueの決定、学習・研究設計の正本を優先する。フロントエンドの配置・依存・状態管理については本書が実装ルール§2を補足する。
- 既存の教材の意味、採点、進捗、報酬、実験条件、観測イベントの仕様を、共通化を理由に変えない。
- 上流の更新は自動追従しない。固定コミットとの差分を確認し、採用判断と更新履歴を記録する。

## 2. 公式ガイドと本プロジェクトの判断

| テーマ | 公式原文 | 本プロジェクトで採用する方針 |
| --- | --- | --- |
| 機能単位の構成 | [Project Structure](references/bulletproof-react/upstream/docs/project-structure.md) | 機能固有のUI・状態・処理は `features/<feature>/` へ置く。必要なフォルダだけを作る |
| 共通部品と依存方向 | 同上 | importは `app → features → shared` の方向を基本とする。sharedは本書で定義する共通領域の総称で、必須フォルダ名ではない |
| 機能同士の接続 | 同上 | 独立したfeatureの内部を相互参照せず、原則app層で組み合わせ、propsやコールバックで接続する |
| API配置 | [Project Structure](references/bulletproof-react/upstream/docs/project-structure.md)、[API Layer](references/bulletproof-react/upstream/docs/api-layer.md) | 公式が認める集中配置を選び、既存の `src/api/` と `lib/fetcher.ts` を維持する |
| UIの分割 | [Components and Styling](references/bulletproof-react/upstream/docs/components-and-styling.md) | 重複と責務を確認して抽出する。巨大な万能コンポーネントにせず、childrenや差し込み口で組み合わせる |
| 状態管理 | [State Management](references/bulletproof-react/upstream/docs/state-management.md) | ローカル状態・共有状態・サーバーデータ・URL状態を分ける。Reduxは必須にしない |
| スタイル | [Components and Styling](references/bulletproof-react/upstream/docs/components-and-styling.md) | MUIを維持。意味のある表示規格を共通化し、教材の状態色とアプリ装飾色を分ける |
| 命名・検査 | [Project Standards](references/bulletproof-react/upstream/docs/project-standards.md) | 既存のTypeScript・ESLint・`@/` を活用。既存ファイルの一括改名や新ツールの一括導入は行わない |
| 検証 | [Testing](references/bulletproof-react/upstream/docs/testing.md) | 利用者から見た操作・統合を重視し、既存のverifyを維持。文書採用だけを理由にテスト基盤を入れ替えない |

## 3. 目標とする配置

以下は移行先の例であり、現在の実装済み構成を示すものではない。

```text
front/src/
├─ app/                         # Next.js App Router、画面組み立て、provider接続
├─ components/                  # 機能に依存しないアプリ共通UI
│  ├─ layouts/                  # ページ枠・ヘッダー
│  └─ ui/                       # ボタン・読み込み・エラー表示
├─ features/
│  ├─ learning/
│  │  ├─ components/            # 学習共通の枠・再生・問題・コード・結果表示
│  │  ├─ screens/               # 学習画面・単元概要
│  │  ├─ hooks/                 # 進捗保存・画面遷移などの制御
│  │  ├─ units/                 # 単元定義・問題・固有の図・実行処理
│  │  ├─ types/                 # 学習内で共有する契約
│  │  ├─ utils/                 # 採点などの純粋な処理
│  │  └─ config/                # 単元登録・学習用の共通規格
│  ├─ collection/
│  └─ ...                       # 必要な機能から整理する
├─ api/                         # APIクライアントとリクエスト・レスポンスの型
├─ hooks/                       # 機能に依存しない共通フック
├─ lib/                         # fetcher・Firebase・外部ライブラリの共通設定
├─ config/                      # 環境設定・アプリ全体の表示規格
├─ types/                       # 機能をまたいで共有する契約
├─ utils/                       # 機能に依存しない純粋な処理
└─ testing/                     # 共通の検証補助（必要になった時点で作る）
```

- Reactコンポーネントの新規ファイルは既存の主流に合わせ `PascalCase.tsx`、フックは `useXxx.ts` を基本とする。Next.jsの予約名は維持する。
- 既存の `<domain>.api.ts` と機能内の教材ファイルの命名は維持する。改名は独立した移行として扱う。
- 共通部品と機能固有部品の両方を `components/` の直下に集めない。学習専用の部品は `features/learning/components/` に置く。
- BFS・DFS・各アルゴリズムはlearning機能内の単元であり、独立したトップレベルfeatureとして分割する必要はない。
- フィードバック・大目標・認証の最終的な機能境界は、参照元と責務を確認して移行単位で決める。以前の会話のフォルダ案に合わせるだけの独立feature化はしない。
- 全featureの `index.ts` から一括再exportする構成は標準にしない。原則として必要なファイルを直接importする。

## 4. 依存・責務のルール

### 4.1 importの方向

- `app/` はfeaturesと共通領域を利用できる。URL・provider・認証境界・機能同士の組み合わせを担当する。
- featuresは共通領域を利用できる。移行済みのコードから `app/` の内部をimportしない。
- 共通領域（components/hooks/lib/config/types/utils/api）はfeaturesやappへ依存させない。機能に依存するものは該当featureへ置く。
- 独立したfeature同士の内部参照は増やさない。共有契約を共通領域へ置くか、app側で組み合わせる。
- 同一feature内でも、単元共通部品が特定の単元の実装へ依存する構造を避ける。図や教材は差し込み口として渡す。
- Next.jsのserver/client境界を維持する。部品移動だけを理由に広い範囲へ `use client` を追加しない。秘密情報やサーバー専用処理をクライアントへ持ち込まない。

### 4.2 UIと制御

- 共通レイアウトは幅・高さ・余白・スクロール・操作領域の配置を扱う。
- 問題・教材の定義は文言、設問、正答、フェーズ構成、固有の図・実行処理を提供する。
- 状態の更新・保存・遷移は機能のフックや制御コンポーネントにまとめる。図を描くだけの部品へ通信や進捗保存を入れない。
- 共通部品の内部に単元名で分岐する処理を増やさない。必要な違いを定義・props・childrenとして渡す。
- 同じ見た目だけを理由に採点や完了条件まで共通化しない。既存の単元差を調べ、契約を確認してから抽出する。

## 5. 状態・API・表示規格

### 状態とAPI

- 再生位置、回答途中、開閉状態は、必要な範囲の `useState` で管理する。連動する複数状態の遷移は `useReducer` を検討する。
- 認証など広い範囲の共有状態は既存providerを活用する。Redux等の新しいストアは、共有範囲と必要性を説明した別の判断で導入する。
- 進捗・保存結果などのサーバーデータは、APIクライアントと既存の取得・キャッシュ方式を利用する。ローカルUI状態との正本を曖昧にしない。
- URLに表すフェーズや検索条件は既存のルーティング契約を維持する。移行だけを理由にURL・API・保存キーを変えない。
- TanStack Query、Zustand、Redux、React Hook Form、Storybookなどは、公式で例示されていても今回の採用で導入決定したものではない。

### レスポンシブ表示

- 教材幅・高さ・スクロールの方針は学習用の共通レイアウトで管理する。文章、図＋コード、実装エディタには異なる配置が必要な場合がある。
- 固定幅・固定高はその目的を説明できる箇所に限る。繰り返す数値は、意味のある共通規格または部品へ集約する。
- 既存のプレイヤーUI定義§1は、教材の占有率と固定の小さい最大幅を避ける方針を持つ。本書はこれを変更しない。会話で挙げた最大幅追加案や368px／320pxの変更は、今後のUI検討候補であって承認済みの数値ではない。
- 実装画面は既存の例外規則に従い、編集面積を優先する。教材用の幅制限を一律に適用しない。
- 表示確認は物理的な画面サイズではなく、CSS上の表示領域を記録する。ノートPCとデスクトップで実際の `innerWidth/innerHeight`、OS倍率、ブラウザ倍率を残す。
- 将来のUI変更では、幅・高さの異なる表示領域と拡大時を確認し、不要な横スクロール、ボタンの到達不能、図やコードの欠け、過剰な内部スクロールを確認する。数値の基準はその変更で明記する。

## 6. 既存コードの例外と段階的な移行

具体的な作業順・対象ファイル・PR分割・完了条件・検証は [フロントエンド移行計画](frontend-migration-plan.md) で管理する。計画の作成だけで実装へ着手したものとは扱わない。

以下は現在の移行状況と残る例外。実装済みの範囲と未移行の範囲を区別する。

| 現在の状態 | 移行時の方向 |
| --- | --- |
| `app/component/` にヘッダー・セッション・共通部品があり、featuresからも参照される | 共通UIと機能固有の制御を区別し、参照元を一緒に移す |
| 全7単元が `LearningUnitPreview` を使用。単元固有の定義・ビュー・結果図を渡す薄いアダプターへ移行済み | 問題画面や実装画面などフェーズ内部はM04以降で共通化する |
| 並べ替え・結果・ブリッジ・共通型はlearning内の共有領域へ移行済み。実装WorkspaceなどはBFS内に残る | 残りはM03以降で差分を確認しながら移す |
| `84vw`、コード確認の固定高、図とコードの配分が複数箇所にある | 既存UI正本と整合する共通レイアウトへ整理する |
| 大目標・フィードバック・学習画面の接続に複数領域の参照がある | 機能境界を棚卸しし、appでの組み立てとコールバック接続を検討する |

推奨する移行順は次のとおり。各段階は別の作業として計画し、本書の追加だけでは開始しない。

1. 共通教材レイアウトの責務・表示基準を決め、代表画面で動作確認する。
2. 学習共通部品の置き場所を整理し、全利用先のimportを更新する。
3. 他5単元の画面制御を、差分を確認しながら一つずつ共通制御へ寄せる。
4. 問題画面・図＋コード・実装画面の重複を、表示と制御を分けて抽出する。
5. 通常ページやapp配下の共通部品を整理し、整理済みの範囲から依存方向をESLint等で検査する。

既存の境界違反を一括でエラーにする設定はまだ追加しない。未移行の参照は増やさず、やむを得ない変更は理由・範囲・解消方法を記録する。無関係なファイル移動や全面整形を混ぜない。

## 7. 移行時の確認と完了条件

- 変更範囲のlint・型チェック・buildと、対応する既存verifyを実行する。
- 共通部品を変更した場合、利用する全単元を対象に、回答・採点・初回と直近の区別・再挑戦・戻る操作・保存失敗・再表示・コード下書き保持を確認する。
- 学習ログ、候補ID、単元ID、保存キー、API契約を維持する。教材内容を変えた場合は構造移行と分けて明示する。
- レイアウト変更はノートPC／デスクトップ相当で確認する。構造検証だけで画面の見た目を確認済みと扱わない。
- 移行先だけでなく、移行前の重複・参照元・暫定例外が解消されたことを確認する。
- 確認できなかった実DB・実ブラウザなどの範囲は明記する。
- 今回は文書のみの変更なので、原文のハッシュ一致、文書間リンク、優先順位の整合、差分範囲を確認する。アプリのbuildや実行で移行完了を主張しない。

## 8. 上流更新の手順

1. 公式GitHubの新しいコミットを選び、固定版との差分を確認する。
2. 公式原文・画像・LICENSEを同じコミットから取得する。原文は改変しない。
3. 取り込みREADMEとmanifestの取得日・コミット・ファイル情報を更新する。
4. 本プロジェクトへ影響する変更だけを本書へ反映し、採用／保留／例外を明記する。
5. `AGENTS.md`、実装ルール、索引との整合を確認する。取り込みだけでライブラリやコードを更新しない。
