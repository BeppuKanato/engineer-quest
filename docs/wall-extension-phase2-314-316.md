# 棒倒し法フェーズ2/4の実行単位対応と説明専用ステップ導入（Issue #314, #316）

目的: 「図の変化はコードの実行単位に対応させる」という原則（2026-11-08 ユーザー確定）を、共有の仕組み・棒倒し法フェーズ2・フェーズ4・教材指針に実装する。最終確認日: 2026-11-08。

## 問題（レビュー #314 / #316 の指摘）

- フェーズ2は外周（32マス）と柱（9本）をそれぞれ一括表示しており、「1本ずつ立てる」というコードの反復が図に現れなかった。方向の決まり（最上段は4方向、それ以外は上を除く3方向）もフェーズ2では扱われず（フェーズ1は「フェーズ2で扱う」と予告）、ランダムに選ぶことへの言及もなかった。
- フェーズ4はフェーズ2の全ステップをチェックポイントとして要求していたため、フェーズ2に説明を足すとフェーズ4でも同じ説明が重複する構造だった。`choices` の意味（柱ごとに倒す方向を表す番号の並び）も言語化されていなかった。

## 原則と仕組み（コミット1）

- 教材指針（`docs/concept/learning-materials-guideline.md`）に §2-5「図の変化とコード実行単位の対応原則」、§2-6「説明専用ステップ」、フェーズ4 §3-④「チェックポイントと説明専用ステップ」を追加した。なお同ファイルの取り込み情報は「Drive で確定させて再取り込み」を原則とするが、本件はチャットでユーザーが確定した決定の記録であり、Drive 側への反映は別途行う。
- `LearningStep` に `explanationOnly?: boolean` を追加（共有の `player/content.types.ts`）。フェーズ4のチェックポイント対象は、共有ヘルパー `codeMappedSteps(content)`（説明専用を除いたステップ）で数える。他単元のフェーズ4定義は単元ごとの定義関数のままだが、棒倒し法の定義関数がこのヘルパーを使う形に改めたため、他単元も同じ印とヘルパーで移行できる。
- 棒倒し法フェーズ4の契約は「全13ステップ」から「コード対応29ステップを順序どおり」に変わった。

## フェーズ2の再構成（コミット2）

ステップ数は 13 → 32（コード対応29＋説明専用3）。自動再生は 3500ms/ステップで約112秒（従来約46秒）。

- 外周: ループ1周ごとの9ステップ（`border-0`〜`border-8`）。盤面は各周で端から広がる。
- 柱: 1本ごとの9ステップ（`pillar-2-2`〜`pillar-6-6`）。最初の柱のキャプションで「外側から1マス空けて2マスおきに立てる理由（間に壁を伸ばす場所と通路を残すため）」を説明し、残りは位置だけの短い文にした。
- 説明専用ステップを3つ追加した。
  - `directions-rule`（柱と伸長の間）: 方向の決まりをキャプションで提示。一番上の段の柱を処理中色で示す。
  - `loop-what-if`（完成後）: 仮定の盤面の実演。正本の生成過程で真ん中の段の右の柱（6, 4）だけが下ではなく上へ伸ばした状態にし、伸ばした壁（6, 3）が周りの壁とつながって間のマス（5, 3）が四方を壁に囲まれる（残り30マスの通路は連結したまま）。検証で囲まれと連結を機械確認している。バリデータの扱い: この盤面は既存の検証（処理中は壁マス、ハイライトは壁マス、target は null、path は空）をそのまま通るため、バリデータの拡張はしていない。囲まれた通路マス自体はハイライトできない（通路のハイライトは検証が禁止する）ため、印は付けず、白マスが黒に囲まれる見た目とキャプションで示す。
  - `another-maze`（完成後）: 別の choices `[0, 0, 2, 0, 0, 0, 2, 0, 2]` で生成した完成迷路（完全迷路であること・正本と壁が10マス違うことを検証済み）。キャプションで「倒す方向をランダムに選ぶと、作るたびに違う形の迷路になる」とし、フェーズ1の予告への回答とランダムへの言及をここで果たす。
- 伸長9ステップは従来どおり1本ごと（各ステップで増える壁がちょうど1マスであることを検証で維持）。

## フェーズ4の再構築（コミット3）

- フレーム総数は 137 のまま（チェックポイントは既存フレームの付け替えで増減なし）。実行行・変数の突き合わせ（CPython トレース）は従来どおり全フレームで通過する。
- チェックポイントの置き場所: 外周は各周の最後の書き込み行（border-right）で `border-i` を、柱は書き込む行（place-pillar）で `pillar-x-y` をチェックポイントにした。これによりフェーズ4でも盤面がループ1周ごと・柱1本ごとに切り替わる。柱のチェックポイント時点では `pillars` 変数にその柱はまだ入っていない（append は次の行）ことを検証で明示した。
- 説明専用ステップはフェーズ4に一切現れない（検証で明示）。
- `choices` の説明（#316）: 表示コードは契約 wall-extension-v1 で本文が凍結されているためコメントは足せず、フェーズ4の慣例（キャプションで言語化）に合わせ、`for-extension` フレームのキャプションを「柱（x, y）と、倒す方向を表す番号Nを choices から取り出して、壁を伸ばす処理を始めます。」とした。

## フェーズ7トレース再生への波及（コミット5）

- 当初「フェーズ7は無関係」と見ていたが、視覚デバッグの再生コンバータは外周・柱の追加を旧フェーズ2の一括コマに合わせて「同じ種類の追加を1コマに集約」しており、検証も「再生の壁列＝フェーズ2列」の一致を要求していた。新原則のままでは一括表示が残るため、集約を「外周は同じ i の間だけ（ループ1周単位）」に改め、再生列が新しいコード対応ステップ列と一致する状態を保った。柱は書き込みが1本1回のため実質変化なし。`i` が読み取れない学習者コードでは従来どおり外周全体を1コマにまとめる。
- 再生キャプションの外周・柱を完了形から進行形に直した（コマが分かれたため）。

## 参照の監査（フェーズ3/5/6）

- フェーズ3（check）は `extend-2-4` 盤面と `extend-4-4` 完了参照、フェーズ5（code-check）はコードフレーム ID、フェーズ6（consolidation）は `execution-extend-4-4` 等のフレーム ID と Parsons の reviewStepIds（フェーズ4ステップ数への動的参照）を参照しており、いずれも今回の変更で残存する ID のみを使うことを確認した。消えた旧 ID（`border-walls` / `pillars`）への参照はアプリコード内に存在しない。

## 既存ドキュメントとの差異

- 基準データ文書（`docs/concept/wall-extension-unit-baseline.md`）フェーズ2の「13ステップ」は本変更で supersede される。同文書は基準データの記録として書き換えず、差異は本報告書に残す。

## 検証

- `verify:wall-extension-execution`: 32ステップ・壁数の推移列・輪の実演の囲まれと連結・別の迷路の完全迷路性を追加検証し通過。
- `verify:wall-extension-code-mapping`: 137フレーム、CPython の全実行行・ローカル変数一致、チェックポイント29件と行対応を検証し通過。
- `verify:wall-extension-trace`: 再生列＝コード対応ステップ列の一致を検証し通過。
- 棒倒し法の全検証（motivation / check / code-check / consolidation / implementation / unit）と全単元の検証59本、front typecheck / lint / build: 通過。
- DB・seed の変更なし。実機の目視確認は未実施（マージ後に単品プレビュー `wall-extension-execution` / `wall-extension-code-mapping` と単元フローで確認可能）。フェーズ2の自動再生が約112秒に伸びた点は実機での体感確認が望ましい。
